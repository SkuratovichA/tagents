# The Rust front door of tagents-core

`tagents-core` was moved from node to Rust one verb group at a time, and the move is finished (stage S5, `openspec/changes/archive/*-rust-retire-node`): node no longer holds a copy of any verb the binary serves. This page explains the seam that is left: a Rust program that answers the verbs it has and runs the node CLI for the few it does not (`plugin list`, an unknown word, the verbs of plugins), the file that lists which program serves which verb, and the suites that prove the binary prints what node printed, which now read node's side from the oracle tag `v0.6.7` ("The parity suite" below). A machine with no Rust binary has no `session`, `sessions`, `doctor`, `plugin add|remove|new`, or `notify run`: node answers each of them with one line that names `tagents update` and `cargo build --release -p tagents-core`, and exit code 69. A managed install fetches the prebuilt binary when a GitHub release exists for the version it holds and never removes one it already has for want of a newer one ("How a release is made" and "How the installer fetches it" below). Passages below that say node answers a verb of the binary, or that a wrapper falls back to a node server, describe the time before S5.

## What is served in Rust today

`tagents-core sessions` (`recent [N]`, `search <words…>`, `show <id-prefix>`, and the bare `sessions` that means `recent`) is a port of `packages/core/src/transcripts.ts`, `tagents-core mcp --contract <file>` is the plugin's MCP server, a port of `packages/mcp` ("The MCP server"), `tagents-core notify run` is the notification daemon, a port of `packages/notify`'s service ("The notify daemon"), and `tagents-core plugin add <package-or-path> [--name <name>]` and `plugin remove <name>` edit the `plugins` tables of the config file, ports of `add` and `remove` in `packages/core/src/cli/plugin.ts`, `plugin new <name> [--dir <dir>]` writes the scaffold of a plugin package, a port of `new` in the same file, and `doctor` prints the four lines of its node twin ("The plugin verbs"), and `tagents-core session open`, `session list`, `session last`, `session prompt` and `session abort` print a session reference, the references of the sessions the state hook knows about and the last thing a session said, run one turn of `claude`, and send SIGKILL to the process a state record names, ports of the same five verbs of `session()` in `packages/core/src/cli/main.ts` ("The session verbs"). The knowledge server, its daemon, the relay a session runs in front of it and the verbs `index`, `search`, `show`, `list`, `usage`, `lint` and `toc` are not in `tagents-core` any more: since 0.8.0 they are the binary `okb` ("The knowledge server and its daemon"). `tagents-core` with no word prints the usage line and exits 2, and `help`, `--help` and `-h` print it and exit 0. Every other word is the node CLI's: `plugin list`, a bare `plugin`, a `plugin` word nobody knows, a plugin's own verbs and a word nobody knows. The node CLI itself does not know `mcp` (`unknown command: mcp`), so on a machine with no Rust binary the plugin's server is `packages/mcp/dist/main.js`, as before.

The decision is made by the first word, so a group of verbs belongs wholly to one program: `sessions rescent` is answered by Rust with the node CLI's usage line and exit code. Two words are not decided alone. `notify`: the arm matches exactly the two words `["notify", "run"]` (`NOTIFY_RUN`, `crates/tagents-core/src/front_door.rs`), and every other argument list that starts with `notify` (`notify status`, `notify install`, `notify run extra`) goes to the node CLI, which hands it to the plugin host, so a verb of the plugin keeps the word. `plugin`: its group (`GROUPS`, `src/front_door.rs`) is a function that may decline. It answers `plugin add`, `plugin remove` and `plugin new` whatever the arguments are, and returns `None` for `plugin list`, a bare `plugin` and a `plugin` word nobody knows, which the front door replaces itself with the node CLI for, since node hosts the plugins: that `None =>` arm is the only place of `front_door.rs` that execs node. `session`, `sessions` and `doctor` answer every argument list: a bare `session`, `session bogus` and `session --help` print `unknownCommand` for `session <verb>` and the usage line and exit 2. Every group reads its arguments with U+FFFD for each bad byte, as `process.argv` does.

The LaunchAgent runs `~/.local/bin/tagents-notify run` when that wrapper is on the `PATH` of the shell that ran `tagents notify install` and names this checkout's `packages/notify/dist/main.js`, and node on that file when no wrapper is on the `PATH` (`runSpecFor`, `packages/notify/src/plugin.ts`). The wrapper runs `tagents-core notify run` for the argument list `run` alone when a binary is installed, and node for every other call (`write_wrapper` and `install_commands` in `install.sh`). A LaunchAgent written before the wrapper existed still says `node packages/notify/dist/main.js run`: that `run` starts `target/release/tagents-core notify run` as a child with inherited stdio and passes SIGTERM and SIGINT on, or prints the needs-binary line and exits 69 when there is no binary.

## The front door

The binary is `target/release/tagents-core`. A contributor builds it with `cargo build --release`; a managed install gets the prebuilt, checksummed one of its own version from the GitHub release `v<version>` (`pnpm build` builds nothing of it, and `install.sh` never compiles it).

```sh
target/release/tagents-core sessions recent 3   # answered in Rust
target/release/tagents-core plugin list         # exec node packages/core/dist/cli/main.js plugin list
target/release/tagents-core --spec              # the verbs this binary serves, as JSON
target/release/tagents-core --version           # tagents-core 0.6.8: the workspace version it was built from
```

For a word it does not serve, the binary replaces itself with `node packages/core/dist/cli/main.js` of the checkout it sits in, with the same arguments, environment, working directory and stdio. There is no wrapper process left: the exit code, and a signal the call ends with, are the node CLI's own. The node is `$TAGENTS_NODE` when that is set (the wrappers `install.sh` writes set it to the node they pinned), and `node` on `PATH` otherwise.

When it cannot find the node CLI it prints `tagents-core: cannot find <relative>: <why>; this binary has to stay in <root>/target/<profile>/ of a root where it is built`, with the node CLI's path below the root and the reason it failed, and exits 2. A binary copied anywhere else does not find the node CLI. When the node cannot be started it exits 127 if there is no such file and 126 if there is one that cannot run.

## Which program a command goes to

The verbs live in `spec/cli/tagents-core.json`, described by `spec/cli/cli-spec.schema.json`. Each command says `"impl": "rust"` or `"impl": "node"`, and may carry an `effect` (`read`, `write`, `spawn`, `destructive` or `serve`) and `"tool": false`, which the plugin contract generator reads. The node CLI reads the file (`packages/core/src/cli/spec.ts`), the contract generator reads it through the node CLI, and the Rust crate `tagents-spec` embeds it, so moving a verb between languages is a one-word edit that leaves the generated plugin contract untouched. `pnpm plugin:gen` then shows no diff, and a test in `crates/tagents-core/tests/front_door.rs` checks that `tagents-core --spec` prints exactly the `rust` entries of the file.

Both loaders refuse the structural mistakes the schema forbids: a key the schema does not name, an empty `program` or `summary`, an empty `path`, an empty word in `path`, `positionals` or `required`, and a `null` where the schema says string or boolean. Both add the one rule a schema cannot state, that two commands never share a `path` (dispatch is by path, so the second would never run). The Rust loader is the stricter one: no input is known that it loads and the node loader refuses. It refuses three inputs the node loader accepts: an `exit` value written `1.0` (the number 1 to JavaScript, a non-integer to the `u8` the model holds), a key written twice in one object (`JSON.parse` keeps the last), and a lone surrogate escape in a string (`JSON.parse` accepts it); a unit test in `crates/tagents-spec/src/lib.rs` pins each. The path to the data file in `packages/core/src/cli/spec.ts` (`SPEC_FILE`) leads out of `packages/core`, so the package works from a checkout and from `$TAGENTS_HOME`, which is one, and would not work from a packed tarball (`files` is `dist`, which does not hold the data file). Nothing publishes or packs the package, and the repository installs from a clone; the package is not marked `private` because the plugin contract lists the public API of every package that is not.

The one-line summary of a command stays in the language catalogue (`packages/core/src/i18n/`), keyed by the `summary` field, so there is one source of the text. The texts a served verb prints (`added <name> → <from> to <file>`, `missing required option <option>`) are in that catalogue too and reach Rust through `spec/cli/messages.json`, a file generated from it ("The plugin verbs").

`"impl": "rust"` on a verb says that the binary answers every call of it: for every argument list the two programs give the same bytes, files and exit code, except where "Where the two are known to differ" says otherwise, and the parity suite marks each of its scenarios with the program that must answer. No call of such a verb reaches node.

## The MCP server

`tagents-core mcp --contract <file>` is the plugin's MCP server: JSON-RPC, one message per line, on stdin and stdout, with one tool for every command of the `cli` section of the contract. It is a port of `packages/mcp`, which stays in the tree as the oracle of the parity suite and as the server a machine without the Rust binary runs. The contract is read once, at start (`crates/tagents-core/src/mcp/contract.rs`), so a plugin update brings a new file and the next session sees the new tools. `plugin.json` is unchanged: it registers the wrapper `tagents-mcp`, which `install.sh` writes to start `tagents-core mcp --contract <contract.json>` when the Rust binary exists at install time and `packages/mcp/dist/main.js` otherwise.

```sh
target/release/tagents-core mcp --contract contract.json                    # serves until stdin ends or SIGTERM, SIGINT or SIGHUP arrives
target/release/tagents-core mcp --contract contract.json < requests.jsonl   # a request a line, an answer a line
```

The code is in `crates/tagents-core/src/mcp/`: `contract.rs` reads the file, `tools.rs` makes the tool of each command (name, description, annotations, input schema) and the command line a call stands for, `run.rs` turns one call into a program and an answer, `server.rs` is the loop and `rpc.rs` is the wire. The program is run by `child::run` and the ending is `ending::Stop` and `ending::on_signals`, which are modules of the crate and not of `mcp`, because whatever else spawns a program or ends on a signal uses them too (`crates/tagents-core/src/child.rs`, `crates/tagents-core/src/ending.rs`). Stdout carries JSON-RPC lines and nothing else: the module denies `print_stdout`, and `rpc::Out` is the only writer.

**What it answers.** `initialize` answers the protocol version the client asks for when the SDK of `packages/mcp` lists it (`2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`, `2024-10-07`; the suite reads the list from the SDK) and the newest otherwise, and tells `serverInfo.version` as the workspace version, where the node server's constant is `0.1.0`. Then `ping`, `tools/list`, `tools/call` and the notification `notifications/cancelled`. Any other method is -32601 `Method not found`, and a call of a tool nobody listed is -32602. A command is a tool unless its spec entry says `"tool": false` or its effect is `serve`, so `mcp` is not one. `contract.json` records the list the generator made from the specs, and a test (`crates/tagents-core/tests/mcp_server.rs`) pins the list `tools.rs` makes from the same file to it.

**Threads.** The main thread reads stdin and answers `initialize`, `ping` and `tools/list` itself. Each `tools/call` runs on a thread of its own, so a slow call does not hold up the next request, and the answers are written in the order the calls finish, not the order they came in. One writer behind a lock writes each message with a single `write_all`, so two answers never interleave. A thread of its own takes SIGTERM, SIGINT and SIGHUP from `signal-hook`'s iterator and starts the same ending as the end of stdin, so no signal handler runs arbitrary code.

**A call.** The program of the verb runs as a child with no stdin, the server's environment and a process group of its own. Each stream keeps its first 256 KiB: the rest is read and thrown away so that the program never blocks on a full pipe, and the cut falls before a character it would split, followed by `\n[output cut at 262144 bytes]`, with `"truncated": true` in the result. A call that has not ended in five minutes, a `notifications/cancelled` for its request, and the end of the server each stop the whole group: SIGTERM, then SIGKILL two seconds later. When the program exits by itself, whatever it left in its group is killed at once and the pipes get 250 ms to drain, because a process that left the group can hold them open for good. At the end of the drain a pipe that still holds bytes, or has lost its last writer, is read on in steps of 10 ms, for at most the drain plus the grace after the exit (`readable` and the timeout arm of `supervise`, `crates/tagents-core/src/child.rs:290-299` and `:344-356`): its reader thread has not run yet, which the machine's load can cause, and a reader thread that has not run is not a holder. A holder that keeps an empty pipe open is given up on at the drain, and so is a call that was stopped, since its answer is `cancelled` or its output is partial already. `a_program_that_exits_with_its_output_still_in_the_pipe_loses_none_of_it` in `crates/tagents-core/tests/mcp_run.rs` pins that nothing the program wrote before it exited is lost when no helper outside the group holds the pipes. Nothing a call starts in that group outlives the call. A process that called `setsid` has left the group, is not the call's to stop and keeps running, as it does under the node server; `a_holder_of_the_pipes_that_left_the_group_cannot_be_killed_and_still_does_not_hold_the_call_longer_than_the_drain` in `crates/tagents-core/tests/mcp_run.rs` pins that such a holder of the pipes still does not hold the call longer than the drain. The constants are pinned to the TypeScript sources by `crates/tagents-core/tests/mcp_pins.rs`, which reads `packages/mcp/src/run.ts` and `main.ts`.

**The result** is `{"content": [{"type": "text", "text": <body>}], "isError": <exit is not 0>}`. The body is the two-space pretty form of `exit`, `outcome` (the first name of the program's `exit` table that carries the code, else `exit <code>`), `stdout`, `stderr` and, when a stream was cut, `truncated`. A refusal has the same shape, with an empty stdout and the reason on stderr. When stdout, after leading JavaScript white space, starts with `{` or `[` and parses as JSON, the body holds the parsed value and not the escaped text; only JSON white space (space, tab, line feed, carriage return) may stand before the document, as in node, so a document behind a no-break space stays text. Node reads that document and writes it again, so the Rust server keeps the order of the keys (`preserve_order`) and tells every number as `JSON.stringify` tells the double it reads as: `1.0` is `1`, `1E2` is `100`, `-0` is `0`, `1e400` is `null` (`js::number_text`, `mcp/run.rs`).

**The ending.** The end of stdin, one of the three signals, or a write error on stdout (the client is gone) ends the server: every call in flight is stopped and answers with the outcome `cancelled`, the server waits until they have answered, for the two seconds of the grace plus two more at the most, and exits 0. A second signal during the ending is caught and ignored (`ending::on_signals`), so a program that ignores SIGTERM still gets its SIGKILL after the grace. A call stopped by `notifications/cancelled` gets no answer, as with the SDK, even if it had finished by then. The answer is written before the call leaves the registry the ending waits on (`Registry::settle` and `finish` in `server.rs`): a registry that empties first lets the process exit with the answer unwritten, which a test pins (`the_ending_returns_only_after_the_answers_of_the_calls_it_stopped_are_written`). A request line longer than 10 MiB, the SDK's `STDIO_DEFAULT_MAX_BUFFER_SIZE`, is treated as the end of the stream.

## The shared child, the ending and the file watch

Three modules of the crate belong to no verb: `child.rs` runs a program with a deadline, `ending.rs` ends a process on a signal, and `watch/` tells a thread that a file or a directory changed. `mcp` and `notify run` are the callers of the first two and `notify run` is the caller of the third, and none of the three knows either, so whatever spawns a program, ends on a signal or waits for a file next uses them and does not copy them.

**The child.** `child::run(command, &Policy, &Stop)` is what "A call" above describes, plus two things the caller chooses. `Policy::input` is written to the child's stdin by a thread of its own, `tagents-in`, which closes stdin after the last byte (`write_input`, `crates/tagents-core/src/child.rs:190`, started at `:270`); `None` gives the child `/dev/null` and never the parent's stdin. The write error is dropped on purpose: a program that exits without reading its input makes the write fail with EPIPE, and its exit code says the rest. A program that never reads its input keeps that thread in the write until the call stops the program, and the thread is detached, so a process outside the group that keeps the read end of the pipe open keeps it there until that process ends. `Policy::kill_grace: None` is SIGKILL at the deadline and at a stop, with no SIGTERM first (`stopping`, `child.rs:373`). A call that was stopped, with a grace or without, gives the pipes the drain and no more (`child.rs:349`). The drain plus the grace, or plus `READER_WAIT`, two seconds, when there is no grace, is for a program that exits by itself with bytes or an end still in a pipe whose reader has not taken them yet (`child.rs:347`); `with_no_grace_a_program_that_exits_with_its_output_still_in_the_pipe_loses_none_of_it` pins it. `Finished` says which stream was cut (`stdout_cut`, `stderr_cut`) as well as ending it with the marker.

**The ending.** `ending::Stop` is the token a call carries and `ending::on_signals` turns the first SIGTERM, SIGINT or SIGHUP into one call of a function on a thread of its own, which gets the name of the signal as node spells it (`"SIGTERM"`) so that a daemon can log which one stopped it; `the_function_is_given_the_name_of_the_signal_that_came` pins the three names (`crates/tagents-core/tests/ending_signals.rs`; the code is `crates/tagents-core/src/ending.rs:14` and `:52`). A `Stop` that several calls share keeps one watcher per call until it trips, so a call that outlives many others takes a stop of its own. `sync::locked` is how the crate takes a lock: a poisoned lock hands back its data, because what sits under these locks is valid between any two of its steps (`crates/tagents-core/src/sync.rs:5`).

**The watch.** `Watch::start(sink)` starts a thread, `tagents-watch`, that sends `T::from(Heard::Fired(key))` to the sink for every key whose watch fired, and `T::from(Heard::Ended(error))` once when a wait fails, or a re-arm of a key's file watch fails for any reason but a missing file, and the thread has to end; `dir(path, key)` and `file(path, key)` arm a directory watch and a file watch for a key, one of each per key, a second call for the same key and kind replacing the first (`crates/tagents-core/src/watch/mod.rs:105`, `:120`, `:125`). On Linux the thread blocks in `poll` over the inotify descriptor and a wake pipe, on macOS in `kevent` through the `kqueue` crate with the wake pipe registered as one more event, and in both with no timeout: nothing in the module sleeps, polls or wakes on a timer (`watch/linux.rs:112`, `watch/macos.rs:124`). Arming a watch sends a command to the thread over a channel, writes a byte to the wake pipe and waits for the thread's reply, so `dir` and `file` return only when the watch is armed and never wait for an event (`arm`, `watch/mod.rs:129`). Dropping a `Watch` drops the channel, writes the byte and joins the thread, so it ends while it waits (`Drop for Watch`, `watch/mod.rs:153`).

A caller that must not lose a write does three things. It arms the watch and only then reads the file to the end, because an edge-triggered watch says nothing about a write that landed before it was armed. It reads to the end again on every key it hears, because one wake can stand for several writes. And it resolves the directory it wants watched to its real path before it passes it, because the watch takes the path as written. `no_byte_is_missed_when_writes_land_as_the_watch_is_armed` in `crates/tagents-core/src/watch/tests.rs` writes to a new file while its watch is armed, 200 rounds, and fails when the read after the arming is removed; `arming_another_watch_loses_no_wake_of_one_already_armed` writes to one file while 300 others are armed after it and pins that none of its wakes is lost.

**What a watch hears.** A directory watch fires when an entry is added, removed or renamed. On Linux it also fires when a file in the directory is written, because inotify reports that; kqueue does not, so nothing may depend on it. A file watch sits on the inode and fires when the file is written, grown, truncated, removed, renamed or revoked; `a_file_truncated_in_place_is_heard` and `a_file_truncated_by_creating_it_again_is_heard` pin truncation. The masks are what libuv asks inotify for (`watch/linux.rs:17`) and the vnode notes that cover the same events on kqueue (`watch/macos.rs:16` and `:24`). Several keys may watch one directory, and an event reaches every one of them: inotify gives one descriptor to an inode however many times it is watched, so the Linux backend keeps the slots apart and removes a descriptor only when the last slot on it leaves (`watch/linux.rs:50` and `:61`), where macOS opens a descriptor for every slot; `two_keys_on_one_directory_both_hear_an_entry_written` and `a_key_that_leaves_a_directory_does_not_take_the_watch_of_another_key_with_it` pin both halves on both systems.

**Where a file watch goes stale, and what the thread does about it.** A file saved by writing a temporary file and renaming it over the path leaves the file watch on an inode that is no longer at the path. The thread therefore opens the path again, before it reports the key, whenever the key's directory reports anything and whenever the file's own watch reports that the inode was deleted, renamed or revoked (`run`, `watch/mod.rs:163-211`; `a_file_saved_by_rename_and_then_edited_in_place_is_heard_again` and `a_file_watch_alone_follows_the_path_across_a_rename` pin it). The path is remembered per key from the first `file` call, whether or not that call found a file, so a file created later is watched from the next directory event on (`a_file_that_did_not_exist_is_watched_from_the_next_directory_event`). Linux reports a file written in a watched directory through the directory, so without the re-arm only the second of the two tests fails there; on macOS both fail. On Linux a rename over a file that a reader still holds open sends `IN_ATTRIB` for the old inode's link count and no `IN_DELETE_SELF`, which comes only when the last descriptor of that inode closes, so `ATTRIB` re-arms a file watch too (`FILE_GONE`, `watch/linux.rs:27`); `a_file_replaced_while_a_reader_still_holds_the_old_one_is_followed_to_the_new_one` pins it.

**A symlink is never followed by a file watch.** `file` on a path that names a symlink returns `Ok(())` and arms nothing, so the target of a link being edited is not heard and the link being replaced is heard through the directory. On macOS the path is opened with `O_NOFOLLOW`, and `ELOOP` is how the kernel says that the path is a link (`watch/macos.rs:114`); the open is also `O_NONBLOCK`, so that a FIFO at the path does not hold the watch thread, and `Drop` behind it, until a writer opens the other end (`a_fifo_does_not_hold_the_watch_thread_for_a_writer`). inotify takes a path and not a descriptor, so on Linux the path is looked at with `symlink_metadata` first and armed with `IN_DONT_FOLLOW`, which rustix spells `WatchFlags::DONT_FOLLOW` (`watch/linux.rs:104`); a link swapped in between the two is armed on the link itself, so its target is still not followed. A directory that is a symlink is followed, because the caller names the directory it wants and a directory is not a file the caller reads. `a_symlink_has_no_file_watch_so_its_target_edited_is_not_heard_and_the_link_replaced_is` and `a_directory_that_is_a_symlink_is_followed_and_a_file_is_not_a_directory` pin both halves.

**Descriptors.** Every descriptor of a watch is close-on-exec, and dropping a watch closes every one it opened (`crates/tagents-core/tests/watch_fds.rs`: `dropping_a_watch_closes_every_descriptor_it_opened` counts the process's descriptors through `/proc/self/fd` or `/dev/fd` over five rounds, and `a_child_spawned_beside_a_live_watch_inherits_none_of_its_descriptors` lists what `/bin/sh` sees). Two limits remain. macOS has no `pipe2`, so a child forked by another thread between the `pipe` and the `fcntl` of the wake pipe inherits its two ends until it execs (`wake_pipe`, `watch/mod.rs:225`). The kqueue descriptor is made by the `kqueue` crate, which gives it back only as a raw descriptor that safe code cannot flag; kqueue(2) says a queue is not inherited by a child, and the second test above passes on macOS with a live watch. On Linux `inotify_init1` takes `CLOEXEC` and the wake pipe is `pipe2` (`wake_pipe`, `watch/mod.rs:220`).

**Known limits.**

- A wait that fails (a closed descriptor, a kernel error), or a re-arm of a key's file watch that fails for any reason but a missing file (a descriptor or watch limit), ends the thread after one last `Heard::Ended(error)` to the sink, which is what lets a daemon whose sink is a shared channel learn that the watch is dead; the keys that fired in the same wake are not delivered after a failed re-arm, because the thread returns before it sends them (`watch/mod.rs:194-204`); `a_re_arm_that_fails_for_want_of_a_descriptor_ends_the_watch_with_the_error` and `a_wait_that_fails_is_the_last_thing_the_sink_hears_and_then_the_thread_ends` pin the two endings; `dir` and `file` then fail with "the watch thread has ended". The module does not restart it. On macOS an event the `kqueue` crate cannot decode (`InvalidData`, a vnode event with no flag it knows) is skipped, as `NotFound` is, and is not a failed wait.
- A re-arm that fails because the file is gone leaves the key without a file watch until the next directory event or the next `file` call, and the key is reported all the same (`a_re_arm_that_finds_the_file_gone_is_no_ending`).
- On macOS a file watch the kernel refuses (kqueue refuses a vnode watch on a pipe, for one) is removed from the queue again, because the `kqueue` crate keeps the refused entry and re-submits it with every later `watch`, which would fail the arming of every other key (`watch/macos.rs:72-79`; `a_watch_the_kernel_refuses_does_not_stop_the_arming_of_the_next`).
- A directory watch on macOS does not report a write inside the directory, so a caller that follows a file by its directory alone hears a replacement but not an edit in place; it arms the file as well.
- inotify has a limit on queued events and on watches per user (`fs.inotify.max_queued_events`, `fs.inotify.max_user_watches`). A queue that overflowed lost events, and the thread reports every key and re-arms every file watch (`watch/linux.rs:71`). A system out of watches makes `dir` and `file` fail with the operating system's error.
- kqueue holds a descriptor for every watched file and directory for as long as it is watched, so a process near its descriptor limit fails to arm.
- The thread ends when the sink has no receiver, with no value, because there is nobody to send it to; a `Watch` whose thread ended is not told, and the next `dir` or `file` is the first thing that fails.

## The notify daemon

`tagents-core notify run` is the notification service of `packages/notify` (`service.ts`, `engine.ts`, the options, the lock) in Rust: the process that follows `events.tsv`, posts a notice through the macOS helper or the `log` backend, and holds a prompt-cache deadline per idle session. It serves nothing but `run`: `install`, `status`, `setup` and the other verbs stay the node CLI's ("Which program a command goes to"). The requirements are `openspec/specs/rust-notify/spec.md`, which this section cites by name rather than restating, and the behaviour it copies is node's, so where a line below says "as node does" the node code is the specification. The modules are under `crates/tagents-core/src/notify/`: `service.rs` (the process), `engine.rs` (events in, notices out), `feed.rs`, `events.rs` and `state.rs` (the agent feed), `options.rs`, `lock.rs`, `hand_over.rs`, `deadlines.rs`, `screen.rs`, `compose.rs`, `phrases.rs`, `kinds.rs`, `helper.rs` and `platform.rs`.

**Three threads and one channel.** The main thread is the engine; the watch thread (`watch::Watch`) and the signal thread (`ending::on_signals`) only put a `Message` (`Wake(Key)`, `Ended(error)` or `Stop`) on one `mpsc` channel (`service.rs:43`, and `:50` for the conversion of the watch's answer). The loop waits on it with a timeout of the engine's next deadline, runs what a message means to the end and only then reads the next (a wait that runs out with no message is the engine's `tick`, `service.rs:346`), so a post that takes five seconds holds the loop for five seconds while the other two threads keep queueing (`serve`, `service.rs:335`). There is no runtime, no timer thread and no poll: the one timed wait is the channel's, which is what "Nothing polls" requires. Everything the loop asks of the clock goes through `Clock::now_ms` (`notify/clock.rs`), and a deadline is a wall-clock time asked again on every wake, capped at five minutes (`deadlines::MAX_SLEEP_MS`), because a cache's time-to-live runs in wall time and a Mac that slept through a deadline would otherwise be hours late.

**The engine** is a plain struct that the loop drives with six calls, `start`, `wake`, `tick`, `next_due`, `reload` and `stop` (`engine.rs:267`, `:278`, `:283`, `:306`, `:325`, `:330`); it has no thread, channel or timer of its own, so the tests drive it with a scripted feed, a fake clock and a recording log. `start` follows the feed and arms what the state rows say is waiting, and runs no job: node's `start` returns before the timer of an overdue deadline and the microtask of a line its first read found have run, and the service logs `started` right after it, so both wait for the first call of the loop, which `next_due` makes immediate by returning zero while a job is queued (`start_runs_no_job_an_overdue_deadline_waits_for_the_first_call_of_the_loop`, `what_the_first_read_found_waits_for_the_first_call_of_the_loop_too`). `wake` is what a watch event calls and reads the events file; `tick` is what the loop calls when `next_due` has elapsed and nothing was heard, and is node's timers: it ends the grace of a rotated file by reading the old file to its end and closing it, without reading the file followed, so the next watch event is what reads the new file (`a_tick_reads_no_line_where_a_wake_reads_the_file`, `the_end_of_the_grace_reads_the_old_file_only_and_a_full_file_is_rotated_by_the_next_wake`). Both follow a dead follower again when its time has come, then sweep and run. One FIFO queue of jobs holds what a wake brought: each line of the follower is a job, followed at once by a sweep that queues the deadlines that have come due, and a wake that brought no line sweeps once, which is node's deadline timer (`ingest` and `sweep`, `engine.rs:381` and `:396`). A prompt that cancels a key is therefore seen before that key's cache notice runs. A call runs every job it made before it returns; the stop of a signal is looked at between two jobs and never inside one, so a post in flight lands and the jobs behind it are dropped (`engine.rs:361`). A job that panics is logged as `error <why>` and the next job runs, as node's `enqueue` does (`caught`, `engine.rs:356`; `a_job_that_panics_is_logged_as_an_error_with_its_text_and_the_next_job_runs`), which needs the release profile to unwind: `panic = "abort"` would turn one bad job into the end of the daemon. A follower that dies is followed again after one second, doubling to five minutes while it keeps dying, and the wait starts over only for a follower that heard an event or lived longer than the wait before it (`engine.rs:37`, `:445`; `a_follower_that_dies_at_once_three_times_is_followed_after_1_2_and_4_seconds`); what was written while it was dead is gone, so the state rows arm again what those events would have (`engine.rs:461`).

**What the watch watches, and a reload.** One `Watch` serves two keys. `Key::Events` is `events.tsv` and its directory, armed by the follower; `Key::Options` is the `plugins` directory of the config directory and the file `notify.toml` in it. The config directory is usually a symlink into a dotfiles repository, which a watch does not follow, so the options watch arms the real path (`OptionsWatch`, `service.rs:203`; `a_symlinked_config_dir_is_armed_by_its_real_path_and_a_change_wakes_the_loop`). It arms the directory, then the file, then reads the options once more, because a write between the first read and the arming raised no wake (`a_file_that_changes_between_the_first_read_and_the_arming_is_read_once_more`). When `plugins` does not exist yet its parent is watched in its place and the daemon moves to `plugins` when it appears, with one look after the arming of the parent, because a directory made between the first look and the arming raises nothing (`a_directory_that_appears_later_is_adopted_and_watched_in_its_parents_place`). With no config directory at all it logs `options reload is off: <dir> does not exist` and runs on (`with_no_config_dir_reload_is_off`). A directory watch cannot filter by name, so every wake of `Key::Options` reads the file and `Settings::apply` ignores a read that says what is in force already: an unrelated file, the same bytes in other words, or a file that is back to the defaults after a bad one log nothing (`service.rs:160`; `the_same_value_in_other_words_and_an_unrelated_file_are_no_reload`). A changed value logs `options reloaded` and the engine reads it at its next job; a changed backend logs `backend changes take effect after a restart (tagents notify install)` and is not applied (`a_reload_to_the_value_in_force_is_ignored_and_a_changed_backend_waits_for_a_restart`). A bad file never stops the daemon: the defaults are in force and each problem is logged once, however often the file is read. Both daemons read `notify.toml` at every event in the options directory, whatever its name, and ignore a read that changed nothing, so an edit of a symlink's target, which raises no event there, takes effect at the next event of any name and a replaced link is a reload at once. Both read through the same rule for the open: an EINVAL, which macOS returns while a rename replaces a symlink on the path, is tried again, three tries in all (`OPEN_TRIES`, `crates/tagents-core/src/notify/options.rs:168`; `READ_TRIES`, `packages/core/src/config-file.ts`), and any other error is reported at once. The tests of the open are `an_open_that_fails_with_einval_twice_is_tried_a_third_time`, `an_open_that_always_fails_with_einval_is_tried_three_times_and_reports_it` and `an_open_that_fails_with_enoent_or_eacces_is_tried_once` (`crates/tagents-core/src/notify/options.rs`).

**Which parser reads what.** The tree has two parsers besides the hand-written ones, and each exists because a byte of the daemon's output depends on it. `toml` reads the options file (`notify/options.rs:208`, `DeTable::parse`): the crate gives the parse tree and the code checks it by hand against node's schema, because the lines the daemon logs are zod's, in zod's order, and serde's texts would be other words in another order; an integer beyond 2^53 is read by the crate and refused by the code, which is what node's parser does. `json.rs` follows `JSON.parse` and reads what is not ours to shape: a transcript, for the body of a `turn_done` notice (`transcripts::last_assistant_text`, called from `compose.rs:76`), and the line the helper prints (`helper.rs:106`); `json::quote` is the one `JSON.stringify` of a string, for log lines and the helper's input. `serde_json` only builds the helper's input, in node's key order (`notice_json`, `helper.rs:68`). The events file and the state rows are tab separated text, split by hand (`events::parse_event_line`, `events.rs:109`; `state.rs`). Every copy of a node rule that changes a byte is pinned by `crates/tagents-core/tests/fixtures/notify-vectors.json`, which was written from the real node functions before they were deleted, is frozen, and is read by `crates/tagents-core/tests/notify_vectors/`.

**The lock shared with node.** `<state dir>/notify.lock` (`LOCK_FILE`, `lock.rs:23`) holds `<pid> <start time>\n`, the start time as `/bin/ps -o lstart=` prints it under `LC_ALL=C TZ=UTC`, or the bare `<pid>\n` of the first format, which is still read; it records no host name, as node's does not. A node daemon and a Rust daemon on one state directory exclude each other because `take_lock` is node's `takeLock` byte for byte (`lock.rs:229`; "One service per machine, whichever program runs it"). The file is made whole or not at all: the text goes into `notify.lock.<pid>.<8 hex>.tmp` and `link` puts it at the lock path, which fails when something is there, so a reader never sees it empty (`create_lock`, `lock.rs:150`; `the_lock_is_never_visible_empty_and_no_temp_file_is_left`), and taking the lock first sweeps the temp files of a dead pid or older than a minute, of that exact shape and no other (`lock.rs:176`). A holder is told from a stranger by the start time, because pids are reused: the pid is alive (signal 0, `EPERM` counts as alive) and `ps` gives the start time the file recorded (`holds`, `lock.rs:128`). A lock with no start time, or a `ps` that cannot answer in two seconds, falls back on the lock's age against the boot time read once at start, `kern.boottime` on macOS and `/proc/uptime` on Linux (`boot_ms`, `lock.rs:288`), and a lock whose pid is the daemon's own is never held. A takeover removes the stale file only while it still says what was judged, and two takeovers over one stale lock end with exactly one holder (`two_takeovers_racing_over_one_stale_lock_end_with_exactly_one_holder`); between the read and the removal another process can still put its own lock there, the window node's protocol has between two node processes, since node takes no mutex that a second implementation could honour. Release unlinks the file only while it names this process, so a lock somebody else took over survives (`lock.rs:255`).

**The start.** `run` (`service.rs:482`) does these steps in this order: register SIGTERM, SIGINT and SIGHUP; create the state directory; take the lock, where a live holder is `another notify service holds <file> (pid <n>); exiting` and exit 0 with the lock untouched; read the options; pick the backend, where `none` and a system with no backend are `<why>; exiting`, a release of the lock and exit 0, which is a choice and not a failure (`leave`); start the watch thread; build the engine and `start` it, which follows `events.tsv` and arms the sessions the state rows say are idle; arm the options watch; and write `started`, last, so that whoever waits for that line finds the lock, the stream, the engine and the watchers all up. A failure of any step before `started` that is not a deliberate exit is logged and ends the process with exit 1, the code launchd retries (the requirement "A start that fails is logged and exits 1"): unless a stop was requested, the daemon writes `could not start: <why>`, closes the follower and the watch (the kqueue descriptor is closed by `WatchSlot`, which joins the watch thread; `a_closed_watch_slot_arms_nothing_and_closes_twice_without_harm`), releases the lock and exits 1 (`a_failed_start_says_why_closes_releases_the_lock_and_exits_1`). A stop that was requested wins and writes no line: the lock is released and the exit is 0 (`a_stop_that_was_requested_wins_over_a_failed_start`, and `a_stop_that_lands_during_the_close_of_a_failed_start_exits_0` for one that lands while the follower closes). A daemon whose stderr has closed fails that last line quietly and the exit stays 1 (`a_failed_start_with_stderr_a_closed_pipe_exits_1_and_is_not_killed_by_sigpipe`). The registration of the three signals, the first step of `run`, is a step that can fail, which node has no counterpart of: its handlers are `process.on` calls that cannot fail to register. A failure after `started` ends nothing: a watch of the options directory or file that cannot be armed is a line, `options watch failed <path> <why>`, and the daemon runs without that reload (`a_failed_options_watch_is_not_a_failed_start`).

**The stop.** A signal ends the daemon as node's `stop` ends it, in this order (the requirement "A signal ends the service as it ends the node service"): the line `stopping (<signal name>)`, then the stop token is tripped so that the post in flight lands and the jobs behind it are dropped, then the watch is closed, the engine stops (the follower closes and `events.on` is removed with the last follower), and the lock is released last, so a restart cannot overlap what is still being drained (`end`, `service.rs:359`; `stopping_precedes_the_notice_of_a_post_in_flight`, `the_watch_closes_first_and_the_lock_goes_last`). The line is written once by whichever thread gets there first: the signal thread, or the main thread when the watch ended (`Said`, `service.rs:95`; `the_stopping_line_is_written_once_by_the_signal_or_by_the_watch_that_ended`). A signal that arrives during start is only remembered by the `StartGate` (the first one wins): the main thread writes the line after `started` when no line was written yet, so a second signal after start gives one line (`Signalling::settle`, `service.rs:125`; `a_signal_during_start_and_a_second_one_after_it_give_one_stopping_line`), and a start that fails writes no `stopping` line at all, releases the lock and exits 0 (`service.rs:59`; `a_signal_during_a_start_that_succeeds_logs_started_and_then_stopping`, `a_signal_during_a_start_that_fails_logs_no_stopping`, `a_stop_during_a_failing_start_ends_the_process_as_a_stop_ends_it`). The loop looks at the stop before each message, so wakes queued behind a signal are dropped (`a_wake_queued_behind_a_tripped_stop_is_dropped`). A follower that will not close is `drain failed <why>` and the lock is still released.

**When the watch ends.** The watch thread sends `Heard::Ended` once and stops when a wait fails or a re-arm fails for a reason other than a missing file ("Known limits" above). Nothing is polled, so a daemon whose watch is dead would never hear another write; node keeps running in that case because it has other mechanisms (a retry timer for the follower, an options watcher that closes and leaves the rest going). The Rust daemon therefore stops: the loop serves the post in flight and the wakes queued ahead of the end first, in channel order, then writes `stopping (watch failed: <why>)`, runs the stop above and exits 1 (`Ending::WatchFailed`, `service.rs:324` and `:374`; `a_watch_that_ends_behind_a_post_in_flight_is_served_after_the_queued_wake_and_stops_with_its_reason`, `a_watch_that_ends_with_nothing_in_flight_stops_with_its_reason_and_exits_1`). Exit 1 is what the LaunchAgent restarts: its `KeepAlive` is `SuccessfulExit` false with a `ThrottleInterval` of 300 seconds (`packages/notify/src/platform/macos/launchd.ts:61-67`), so launchd starts the daemon again after any non-zero exit, at most once in 300 seconds, and the start takes the start path above. A daemon started by hand, or by the wrapper `install.sh` writes, has no `KeepAlive` and stays stopped. A failed watch is never handed over to node.

## The plugin verbs

Node stays the host of plugins, which are JavaScript: `plugin list`, the verbs of the plugins themselves and the services they offer are node's, apart from the notify daemon (`notify run`), which the binary serves. The front door forwards them, and no protocol runs between the binary and a plugin, so a machine that runs a plugin needs node. `openspec/changes/archive/2026-10-31-rust-core/design.md` weighs this against JSON lines over stdio with a node shim, which would pay off only when a service has to live in Rust, and against an engine embedded in the binary, which it rejects.

`plugin add` and `plugin remove` are ports of `add` and `remove` in `packages/core/src/cli/plugin.ts` over the config writer of `packages/core/src/plugin-config.ts` (`crates/tagents-core/src/plugin.rs`, `plugin/config.rs`, `plugin/resolve.rs`), and `plugin new` is the port of `new` in the same file over the scaffold of `packages/core/src/cli/scaffold.ts` (`plugin.rs`, `plugin/scaffold.rs`). One rule decides what it prints: **the Rust verb answers every call of its verbs, and never hands one to node** (`plugin::serve` returns `None` only for `plugin list` and a word it does not know). Where node's text is a line of the messages table or a fixed template, as `util.parseArgs` errors are, the binary prints the same bytes. Where node's text carries a third party's words (the TOML parser's message), the binary prints node's frame and exit code with the words of its own parser inside. Where node's text is the operating system's, it is worded as node words it for the error numbers of `node::ERRNOS` and `node::SYSTEM_ERRNOS`.

The calls it answers:

| call | stream and exit code | text (catalogue key) |
|------|----------------------|----------------------|
| `add` with no package | stderr, 2 | `missingOption` with `<package-or-path>` |
| `add`, a name that is not `NAME` (`^[A-Za-z0-9][A-Za-z0-9._-]*$`) | stderr, 2 | `pluginBadName` |
| `add`, nothing at the path | stderr, 1 | `pluginUnresolved` |
| `add`, a package that is not a plugin, or whose entry is missing | stderr, 3 | `pluginBadManifest`, `pluginNoEntry` |
| `add`, the key is listed | stderr, 3 | `pluginExists` |
| `add` | stdout, 0 | `pluginAdded` |
| `remove` with no name | stderr, 2 | `missingOption` with `<name>` |
| `remove`, the key is not listed | stderr, 3 | `pluginNotListed` |
| `remove` | stdout, 0 | `pluginRemoved` |
| `new` with no name | stderr, 2 | `missingOption` with `<name>` |
| `new`, a name that is not `NAME` | stderr, 2 | `pluginBadName` |
| `new`, a target directory that holds anything | stderr, 3 | `pluginTargetExists` |
| `new` | stdout, 0 | `pluginScaffolded` |

The order is node's: the missing package, then the resolution, then the name, then the config. A bad name for a package that is not there is the package's error. `new` checks the name first and the target second, and the target is `--dir` or the name, made absolute against the working directory.

The arguments are read by `parse_args` (`crates/tagents-core/src/parse_args.rs`), node's `util.parseArgs` in strict mode with its wording, the reader the `okb` verbs use too: an unknown option, a missing value, a flag given a value or a positional where none is allowed gives node's line and exit 2, and an argument is decoded with U+FFFD for each bad byte. A positional is an argument that does not start with `-`, or a lone `-`; `--` ends the options; `add` takes `--name V` when `V` does not start with `-` and `--name=V` for any `V`, and the last one wins; `new` takes `--dir` on the same terms and `--name` is not its option; `remove` takes no option. A second positional is ignored, as node ignores it.

What the binary words itself, where node's own text is not a line it can print:

- a verb the group does not serve (`list`, a bare `plugin`, a word nobody knows) is the one call node still answers, and the front door execs it before anything is read;
- a config that is not UTF-8 is read with U+FFFD for each bad byte and written back so, as node does. A document the TOML parser refuses, an integer beyond ±(2^53−1) and an edit that does not parse back to what was meant are `<file>: <reason>` and `<file>: the edit would not parse: <reason>` with exit 1, the reason in the words of the Rust parser (rule 2). A `plugins` that is not a table, and a key `__proto__`, are node's. Any I/O error (a link that leads nowhere or in a loop, a directory where the file is, a file nobody may read, a directory nobody may write in) is the system's line as node words it, exit 1; only a missing file (`ENOENT`) reads as an empty config, in both programs (`read_text`), because every other failure to read it would otherwise have the edit replace what could not be read;
- a package.json that is not UTF-8 is read with U+FFFD, a working directory that is not UTF-8 is lossy, and one that is gone is `ENOENT: no such file or directory, uv_cwd` with exit 1 (`GONE_CWD`);
- for `new`, a target that cannot be looked at or listed is the system's line, a binary whose place does not tell where `packages/core` is (`node::root`) is `tagents-core: <why>`, and a write that fails undoes what the binary wrote and prints the system's line.

**`plugin new` writes what `spec/cli/scaffold/plugin.txt` holds.** The file is the five files of the scaffold, each a section that starts with a line `@@ <path>`, with the placeholders <code v-pre>{{name}}</code>, <code v-pre>{{dir}}</code> and <code v-pre>{{core|json}}</code>. Node reads it at run time and the binary embeds it (`include_str!` in `plugin/scaffold.rs`), so the bytes have one source and `plugin::scaffold::tests` and the vectors (14 cases of `tests/rust-plugin-vectors/scaffold.mts`) pin how each program fills it. The placeholders are replaced in one pass, so a name or a directory that holds <code v-pre>{{name}}</code> is written as typed, and any other <code v-pre>{{…}}</code> stays. <code v-pre>{{core|json}}</code> is the specifier that links `packages/core` as a JSON string escape without the quotes, and only `package.json` holds it. The specifier is `relativeSpecifier` of `scaffold.ts` with its quirk, which `relative_specifier` keeps: a relative path that starts with `.` gets no `./` in front, so a hidden directory is linked as `.hidden/x`. The directory is written as node writes it, `mkdir -p` of the parent and then the file; when a write fails the binary removes what it wrote, the files and the directories it made for them, deepest first (`undo`), and prints the system's line with exit 1, where node's `create` leaves what it wrote. `dir` and the directories above it stay, as node makes those first as well.

**`doctor` prints four lines and exits 0** (`crates/tagents-core/src/doctor.rs`): the node version and path (`doctorNode`), the state directory with its record count (`doctorStateDir`), the config file and whether it exists (`doctorConfig`), and the `claude` found on `PATH` (`doctorClaude`). It reads no argument, so its group takes a call whatever the bytes of its arguments are, and it says what is wrong instead of failing on it. The count is that of `read_agent_state`, the reader the notify daemon uses, so a record that does not parse is not counted; the config exists as `fs.existsSync` says it does, so a link that leads nowhere is missing. The version and the path are `process.version` and `process.execPath` of the node that runs the CLI, and the operating system may report another path for that node than the one that started it, so the binary asks it once with `node -p` (`identity`; `$TAGENTS_NODE`, else `node` on `PATH`, within 10 seconds) and uses the answer only when it is an array of two strings. When node cannot be asked, line one is `doctorNodeMissing`, `node: missing` (`node: нет`), and the other three lines are printed: node cannot run without node, so this line has no twin and the unit tests of `doctor.rs` are what pin it. A signal (SIGTERM, SIGINT or SIGHUP) while node is being asked stops that question, which runs in a process group of its own that the terminal's Ctrl-C does not reach, and ends the call with nothing printed and the status a shell reports for a program that signal killed (143, 130, 129), where node's `doctor` is killed by the signal itself.

**The config is edited as text, and the parser only answers questions** (`plugin/config.rs`, the twin of `addPluginEntry` and `removePluginEntry`). The file is the owner's, with comments and spacing of their own. `add` appends `[plugins.KEY]` and `from = "…"` behind one blank line, re-parses the result and checks that `plugins.KEY.from` is what was meant; `remove` cuts the section and its subsections out by their header lines (a section runs from its header to the next header, less the comment lines just above that header, which belong to it; the blank lines that trail the section go with it, and at the end of the file so does the blank line `add` put before it), re-parses, and checks that everything else is deeply equal to what it was, numbers compared as JavaScript compares them (`NaN` is unequal to itself, an integer beyond 2^53 is a TOML error in node and in the binary). The write goes to `<target>.<pid>.tmp` and is renamed over the target after `mkdir -p`; a failed write or rename removes the temporary file and prints the system's line (`save`, `plugin/config.rs:314`). The target is `file` itself, or the file a symbolic link at that path ends in, so a config kept in a dotfiles repository stays a link (`write_target`, `plugin/config.rs:295`). The new file has the mode `0666` less the umask, not the mode of the file it replaces, and nothing locks the file: two edits at once end with the last rename, as in node.

**The package is found by the part of node's resolution that can be proved** (`plugin/resolve.rs`, the twin of `resolvePluginPackage`). A spec that starts with `.`, `~` or `/` is a directory and is resolved here in full: `~` is `os.homedir()`, the path is made absolute as `path.resolve` does, and the manifest is read, qualified (`name` a non-empty string if present, `tagents.apiVersion` the number 1, `tagents.entry` a non-empty string) and its entry checked to exist. Anything else is `require.resolve('<spec>/package.json')` from the working directory and then from the global folder `pnpm root -g` names: the walk of the `node_modules` directories up from the working directory, `NODE_PATH` and the two folders in the home directory, the `exports` of the package it meets (the `./package.json` key, a pattern key with one `*`, a `null` target) and the self-reference of the nearest package above the working directory to its own name. A name found nowhere is node's line and exit 1. The real path comes from `node::realpath` (`node.rs:109`), which follows JavaScript's `fs.realpathSync` and keeps the case the caller typed, where `fs::canonicalize` writes the case the disk has: on a case-insensitive volume `plugin add Plain` and the two would otherwise differ. It gives up on a path that holds more than 32 links, the smaller of the limits of macOS (32) and Linux (40), where node leaves the limit to the kernel. It runs no `--require` hook and does not know the `lib/node` folder of the node installation ("Where the two are known to differ"). Nothing reads more of the package than its package.json, and nothing imports it.

**The texts have one source.** `spec/cli/messages.json` is generated from the catalogue (`packages/core/src/i18n/export.ts`, `pnpm messages:check` in `.github/workflows/ci.yml`), refuses a text with `$t(` or a placeholder that is not <code v-pre>{{word}}</code>, and holds `en` and `ru`; the 15 `summary*` keys that `ru` lacks fall back to `en`, as in node. The binary embeds it (`tagents_spec::Messages`, `crates/tagents-spec/src/lib.rs:190`) and `Texts::t` (`crates/tagents-core/src/messages.rs`) fills the placeholders the way i18next 26 does, including the quirk that matters: after each placeholder it replaces the first occurrence of that placeholder's text in the whole string, so a value that holds a later placeholder (<code v-pre>--name={{file}}</code>) takes that placeholder's value instead of keeping its own text. The locale is `TAGENTS_LOCALE`, read as `Locale::of` reads it for the notify daemon: `ru` only when it is exactly that.

**What pins it.** `tests/rust-plugin-vectors.mts` writes `crates/tagents-core/tests/fixtures/plugin-vectors.json` from the node code (61 config documents, 532 config cases, 74 resolution cases over a package tree, 418 catalogue cases) and `crates/tagents-core/tests/plugin_vectors/` checks the Rust code against every case; the workflow regenerates the file and runs `git diff --exit-code` on it, so a node change that moves an output fails there until the copy follows. `tests/rust-plugin-parity.sh` ("The parity suite") runs the two programs over the same tree. The tripwires are the files the vectors and the suite share, `tests/rust-plugin-vectors/corpus.mts` (the documents) and `tree.mts` (the packages).

## The session verbs

`session open`, `session list` and `session last` are ports of the three verbs of `session()` in `packages/core/src/cli/main.ts` that start no process (`crates/tagents-core/src/session/read.rs`, `session/reference.rs`), `session prompt` is the port of the verb that starts `claude` and of `ClaudeHeadlessDriver.prompt`, which it calls (`session/prompt.rs`), and `session abort` is the port of the verb that ends a headless session (`session/abort.rs`). They follow the rule of the plugin verbs: **the Rust verb answers every call of its verbs** (`session::run` returns an `Output`). A bare `session`, a word nobody knows and `session --help` print `unknownCommand` for `session <verb>` and the usage line and exit 2.

**One option grammar.** `parse_args.rs` is node's `util.parseArgs` in strict mode with its wording, and the session and plugin verbs read their arguments through it as the `okb` verbs do, so there is one reader and no pin between two. An unknown option, a missing value, a flag given a value or a positional where none is allowed gives node's line and exit 2. `every_grammar_is_the_options_of_its_command_in_the_data_file` holds each table to the `options` of its command in `spec/cli/tagents-core.json`.

**What `open` decides.** The checks run in node's order (a missing or empty `--cwd` is `missing required option --cwd`, exit 2; `--config-dir` with `--no-config-dir` is `unknown option --config-dir + --no-config-dir`, exit 2), `cwd` is made absolute as `path.resolve` does, the id is a version 4 UUID from 16 bytes of `/dev/urandom` (a failure to read them is `tagents-core: cannot read random bytes: <why>` and exit 1), and the reference is printed in the order of `main.ts`. With `--resume` the transcript is the first state row of that session that names one.

**The reference.** `session/reference.rs` reads a reference given as JSON through `json::parse_exact` and the schema of `packages/core/src/session-ref.ts`: a text that fails the schema is no match (`no session matches <ref>`, exit 1, as node says), and a text node accepts but whose strings Rust cannot hold or act on is `badRef` too (the line `no session matches <ref>` and exit 1, rule 3 of the design): a lone surrogate in a key or in a string the schema keeps, a NUL in one, a `spec.env` entry that `spawn` refuses (an empty name, a name with `=`), an empty `bin`. No `session open` writes such a reference; it is reached only by one written by hand. The key `__proto__` of `env` is dropped whatever it holds and a key written twice counts once, as zod and `JSON.parse` do. A reference that is not JSON is resolved against the state rows: the key or session id first, then the first row whose session id starts with the text (`resolveRef`).

**Exact strings.** A transcript can hold a lone surrogate escape (`"\ud83d"`), which `JSON.stringify` writes back and which Rust's `String` cannot hold. `json::parse_exact` keeps such a string as `Value::Units`, `js.rs` has the UTF-16 operations on units, and `json::stringify` prints a value as `JSON.stringify` does (JavaScript's key order, `js::number_text`, the two-space layout). `session last` reads the transcript through the same loop as `sessions show` (`transcripts::last_assistant_reply`) with the exact parser, where `sessions show` keeps the lossy one. `at` is the file's `mtimeMs` as the exact double (`node::mtime_ms_exact`). The stream of a turn goes through `json::parse_whole`, which keeps a key with a lone half as `Value::Keyed` as well, because `--events` prints a tool's input and a result payload back and node writes that key as the escape.

**The state rows.** `notify::state::AgentStateRow` carries the `pid` (column 8: a whole number above zero; a number a `u32` cannot hold is no pid). `list` is the rows that are not `subdone`, in the order the reader returns them, filtered by `--label` (exact, against `history.tsv`) and `--state` (one or more of `new`, `working`, `blocked`, `done`, `gone`; another word is `unknown option --state <words>`, exit 2); `last` prints `null` for no transcript, no file or no text, and the reader's message with exit 1 for a transcript that exists and cannot be read.

**What `prompt` decides first.** Once `claude` runs the call cannot go back, so what node would refuse is decided with nothing written or started: the reference above, and a value `spawn` refuses, such as a NUL in an argument (`Invocation::of`, `session/command.rs`), which is `badRef`. An environment entry that is not UTF-8 is decoded with U+FFFD, name and value, as node decodes it (`command::parent_environment`), and a machine with no node starts the child all the same, with the real path of `$TAGENTS_NODE` or `node` for the directory at the front of its `PATH` when there is one (`command::node_directory`). A SIGCHLD that is ignored at the start does not stop the verb: the handler it installs covers it. A start that fails with `ENOENT` and `EACCES` is the outcome `spawn-failed` with the detail `spawn <bin> <CODE>`, `ENOTDIR` is `spawn ENOTDIR` alone on stderr, and any other errno is `spawn <the system's line>` on stderr with exit 1, the shapes of node's `error` event and of its throw.

**How the child starts.** `session/command.rs` builds the argument vector and the environment as `buildArgs` and `childEnv` do, and `session/spawn.rs` starts the child once, with the null device as standard input, in the working directory of the spec. On Linux `Command` ends in the `execvp` that libuv's child ends in. On macOS libuv walks the child's `PATH` with one `posix_spawn` per entry, so `spawn.rs` walks it the same way and gives `Command` each file by its absolute path, and a relative path is resolved against the working directory of the child first. A file the kernel may answer with `ENOEXEC` (`kernel_may_refuse`) is reported as `spawn ENOEXEC` before the start, because the libc's `posix_spawnp` behind `Command` runs such a file through `/bin/sh` where node prints `spawn ENOEXEC`. `session/awake.rs` holds `caffeinate -i -w <pid>` through the turn on macOS unless `TA_KEEP_AWAKE=0`, as `holdAwake` does, and a failure there is silent, as in node.

**The supervisor.** `session/turn.rs` is the machine of `ClaudeHeadlessDriver.prompt`: a time limit that kills the child with SIGKILL, the first well-formed `result`, which cancels the limit and starts a grace of 60 seconds that ends in a kill and leaves the turn a success, and the exit of the child, which starts a drain of 5 seconds for its pipes. It reads no clock and starts nothing, because the process, the pipes and the time come through the trait `World`, so each timing rule runs in virtual time in a unit test. `session/turn/supervisor.rs` is the real `World`: one thread per pipe and one that waits for the child feed one channel, and the loop sleeps in `recv_timeout` until the next timer. At the end of the drain the machine takes what the channel already holds before it decides, so a line the child wrote before it left is not lost to the order of a timer and a read. The only signal handler is a flag for SIGCHLD, which ends nothing, so a signal that ends the CLI leaves the child running, and `session list` finds it.

**The writes and the lingering.** Stdout has a thread of its own with an unbounded queue (`Stdout`, `session/prompt.rs`), because node's writes to a pipe are asynchronous: a reader that stopped reading holds up neither the turn nor the time limit, and everything reaches it when it comes back. The error line waits at most one second for stdout, so two streams on one pipe keep node's order and a stdout nobody reads cannot hold the line back. After the outcome the process stays until both pipes of the child have closed (`turn::linger`), because node never lets go of them: a grandchild that holds one keeps the call running, and leaving earlier would change what it sees on its next write. With `--events` a whole line that arrives in that time is still an event on stdout, as node's `data` listeners go on printing it, and a last line with no newline never is.

**The pins.** `tests/rust-session-vectors.mts` runs node's own functions on corpora and writes `crates/tagents-core/tests/fixtures/session-vectors.json`, which `crates/tagents-core/tests/session_vectors.rs` requires Rust to match (the printing of numbers, strings and keys, the decoding of invalid UTF-8, the reference schema with its `badRef` classes); a step of `.github/workflows/rust.yml` regenerates the file and runs `git diff --exit-code`. The sections `stream`, `args`, `env` and `outcome` hold the reader of a turn, its argument vector, its environment and what it ends as, and `no_section_is_left_unread` fails when the file holds a section no test reads.

## Where the binary is looked for

| who | looks at, in this order |
|-----|-------------------------|
| `tagents` (for a verb it does not know) | `tagents-core` on `PATH`, then `target/release/tagents-core` beside the script when it is executable, then the built `packages/core/dist/cli/main.js` |
| the `tagents-core` wrapper from `install.sh` | `$TAGENTS_HOME/target/release/tagents-core` while it is executable, then the node CLI |

`install.sh` names the Rust binary in the wrapper only if the binary is executable when the installer runs. With none, the wrapper runs the node CLI, which answers a retired verb with the needs-binary line and exit 69. A binary that is there and cannot run is an error that is reported, not a reason to fall back silently. A directory at the binary's path is not a binary either.

A binary built by hand goes stale. `target/` is ignored by git and nothing rebuilds it, so after `tagents update` or a `git pull` an older `cargo build --release` keeps answering `sessions` until the next `cargo build --release`. The wrappers name any executable binary, of any version: a stale binary is better than none, and `tagents update` replaces it. `tagents-mcp` ends in node's `mcp`, which gives the needs-binary line and exit 69. Rebuild after every update. The prebuilt binary cannot go stale that way: on every run the installer compares its marker with the version of the checkout ("How the installer fetches it").

## How a release is made

**The version is the identity of the binary.** `version` in `[workspace.package]` of `Cargo.toml` is the only place it is written, `tagents-core --version` prints it, and a release is the tag `v<version>`. A binary of version V must come from the source of version V, so the version has to move whenever the source does.

**A pull request cannot forget to move it.** The `release-path` job of `.github/workflows/rust.yml` runs `.github/scripts/core-release.sh gate origin/<base>` on every pull request: when the diff against the merge base changes an input of the binary and the workspace version is not higher than the one at the merge base (the same, or lower: the three numbers are compared one by one, as numbers), the job fails, names the files and says whether the version stayed or went down. The inputs are `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `crates/*/Cargo.toml`, `crates/*/build.rs`, `crates/*/src/*` and `spec/cli/*` (the CLI spec is compiled into the binary by `include_str!`, and the schema beside it counts too, because the rule is a prefix). Tests under `crates/*/tests/`, docs, workflows and the node side are not inputs. A rename out of an input path counts as a change to it.

**A tag makes the release.** Pushing `v<version>` on a commit of `main` starts `.github/workflows/release.yml`:

1. `verify` (read-only token, whole history): the tag is `v` plus the workspace version of that commit, the commit is an ancestor of `origin/main`, and no release of that tag exists yet. A release is never overwritten; a wrong one is superseded by a new version.
2. `build`, on three targets: `aarch64-apple-darwin` and `x86_64-apple-darwin` (cross-built on the arm64 macOS runner) and `x86_64-unknown-linux-musl`. Each runs `cargo build --locked --release --target <triple> --package tagents-core --package okb`, packages both with `core-release.sh package`, and on the two targets the runner can run unpacks the archive elsewhere and checks `--version` and `--spec`.
3. `publish` (the only job with `contents: write`, and it checks out nothing): `gh release create` with exactly twelve files, the six of `tagents-core` and the six of `okb` (the same two files per target).

| file | content |
|------|---------|
| `tagents-core-<version>-<triple>.tar.gz` | exactly two members: `tagents-core` (mode 755) and `LICENSE` |
| `tagents-core-<version>-<triple>.tar.gz.sha256` | one line, `<64 lowercase hex>  <archive name>`, readable by `sha256sum -c` and `shasum -a 256 -c` |
| `okb-<version>-<triple>.tar.gz` | exactly two members: `okb` (mode 755) and `LICENSE` |
| `okb-<version>-<triple>.tar.gz.sha256` | the same one line for the okb archive |

A pull request that changes the workflow, the scripts or an input of the binary (the paths above, which `tests/release.sh` pins to the `pull_request.paths` of `release.yml`) runs the three builds as a dry run and publishes nothing, so a musl link failure or a failed cross-build shows on the pull request and not when the tag is pushed. The `build` job checks out the commit the `verify` job checked, not the tag by name, so a tag moved between the two jobs is not built unverified. A run that failed halfway is redone from the Actions tab with the tag as input (`workflow_dispatch`).

```sh
git switch main && git pull --ff-only          # the commit that holds the bump
sh .github/scripts/core-release.sh version     # 0.8.0
git tag v0.8.0 && git push origin v0.8.0       # starts the release workflow
```

**When `main` is ahead of the last release,** a managed copy that follows `main` holds a version with no release yet. Its installer finds nothing to download, says so, keeps the binary it already has, and the wrappers keep naming it until the tag of that version is pushed. With no binary at all it warns what will not work. Nothing releases on a push to `main`: the person who merges the bump pushes the tag.

## How the installer fetches it

`install.sh` runs `fetch_native` after the build and before it writes the wrappers, never with `--check`. The rules, in the order the function applies them:

| rule | behaviour |
|------|-----------|
| nothing to do | no `$TAGENTS_HOME/Cargo.toml`, or `TAGENTS_NO_NATIVE=1` (which also removes a binary that has a marker), ends the function silently |
| what is wanted | the workspace version of `$TAGENTS_HOME/Cargo.toml`, read by `core_version` in `install.sh`, a second copy of `core-release.sh version` that `tests/release.sh` runs against it over the same `Cargo.toml` shapes |
| whose binary it is | `target/release/tagents-core.release` holds `<version> <target> <sha256 of the binary>` on one line. A binary with no marker was built by hand: it is not replaced, deleted or shadowed by a download |
| nothing changed | the binary is executable and the marker names the wanted version, this target and the hash of the binary: the function ends, and no request is made |
| any other state | a marked binary of another version, target or hash, or a marker without a binary, is replaced when the fetch succeeds and kept when it does not; only `TAGENTS_NO_NATIVE=1` deletes it. A directory or a link at the binary's path, or a marker without a file, is cleared before anything is fetched |
| this machine | `x86_64-unknown-linux-musl`, `x86_64-apple-darwin` or `aarch64-apple-darwin` from `uname`, where an x86_64 process under Rosetta counts as arm64 (`sysctl -n sysctl.proc_translated` is 1). `TAGENTS_CORE_TARGET` replaces the guess |
| where | `https://github.com/SkuratovichA/tagents/releases/download/v<version>/`; `TAGENTS_CORE_BASE_URL` replaces it (a directory URL that starts with `https://` or `file://`; when a fetch is due and `curl` is there, any other scheme is refused with a warning, no request is made and the run ends with status 1) and is announced in one line. `curl` only, with a bounded wait; an `https://` URL is HTTPS only, TLS 1.2 or newer, two retries, and a `file://` URL is held to files. No `gh`, no login |
| downloaded to | a directory made under `target/` of the copy and removed when the run ends, not under `TMPDIR`: the downloaded binary is run once there for its `--version`, and `TMPDIR` may be mounted `noexec` |
| no release, no network, no `curl`, no `sha256sum` or `shasum`, an unsupported machine | one line that says the installed binary stays (or, with none, what will not work), and the run still exits 0 |
| a download that fails a check | `warn`, nothing installed, the wrappers are written, and the run ends with status 1. The checks, in order: the first field of the `.sha256` file is 64 lowercase hex and equals the archive's SHA-256; the archive lists exactly `tagents-core` and `LICENSE`; the extracted `tagents-core` is a regular file and `--version` prints exactly `tagents-core <version>` |
| installing | the marker first, then the binary, each written to a temporary name and renamed, so an interrupted run leaves a marker that does not match, which the next run removes |

The checksum is published beside the archive, so it proves the transfer and that the archive is the one that was packaged, and it does not prove who published it: whoever can write the release can write both files, and the binary is not signed. Trust rests on HTTPS to GitHub and on who may create releases of the repository.

## The knowledge server and its daemon

This part of the binary is the `okb` crate since 0.8.0: `crates/okb`, a binary of its own with the module that was `knowledge` in `tagents-core`, and the words after `knowledge` are now the words of `okb` (`okb mcp`, `okb serve`, `okb join`, and the verbs `index`, `search`, `show`, `list`, `lint`, `toc` and `usage`). The node package `@tagents/knowledge` is gone; the tag v0.7.0 is the node program the parity suite compares with. Where a line below says `tagents-core knowledge X`, read `okb X`.

`okb mcp` is the MCP server of the former `packages/knowledge` (tag v0.7.0) over stdio: the four tools (`knowledge_search`, `knowledge_get`, `knowledge_list`, `knowledge_usage`) with the descriptions, the schemas and the error texts of the node server, on the same index and the same usage store. The tool list and the two sentences the program prints itself are not written by hand: `tools.json` and `texts.json` in `crates/okb/src/knowledge` are kept by hand now that the node catalogue is gone, and `packages/contract/src/sources.ts` reads `tools.json` for `contract.json`. The two session tools (`sessions_recent`, `sessions_search`) were tools of that server too; they belong to the tagents server now (`mcp::sessions_tools`, listed by `sessions_tools.json` beside it, with the same names, schemas and answers), because okb keeps no sessions. The stdio loop is the one of the plugin's MCP server (`mcp::server`), which ends with exit 0 when the input ends.

`knowledge serve` prints the socket of the shared server of this environment and starts that server when nothing answers; `--foreground` is that server. There is one daemon per environment, not per session: the socket is named after a hash of the variables the server reads and of the code that serves, so two sessions that would answer alike share a process and two that would not never do. The hash of a Rust daemon starts with `rust:`; the node daemon it was told apart from no longer exists. The socket directory is `<tmpdir>/tagents-<uid>` with mode 0700. The daemon is one accept loop on `poll` over the listener and a wake pipe, with a thread for each connection. Only the loop adds connections, and the thread of a connection only removes its own, so the count cannot rise behind the loop. The loop is also what decides to leave, and the decision follows a drain of the backlog: it accepts what is waiting and then reads the count, so a session that reached the socket before the drain is counted and served however long it waited there, and one that comes after the drain is closed without a reply when the listener closes, which is what the retry of `join` handles. It leaves after `--idle` seconds (default 600) with nobody connected, counted from the last disconnect or from the start, never while a client is connected, and removes its socket and its pid file when it goes, a failure of the loop included. The socket file goes before the listener closes: while the listener is open a probe finds it live, so nobody else can have replaced the file, and a leaving daemon never unlinks the socket of the next one. It is started detached: its own process group, working directory `/`, and the descriptors 0 to 2 on `/dev/null`.

A connection reads its input in ticks of 500 ms. A reader that waits for the end of a stream does not wake on macOS (Darwin 25.5) for the `shutdown(Write)` of its peer in about one round in fifteen hundred, while the end of the stream is there at the next read; the daemon would then keep a connection of a session that is long gone and never idle out. The tick makes every wait finite, and a read that times out is read again. A peer that has already shut down its writing side refuses a read timeout on macOS with `EINVAL`, so the daemon sets the timeout and ignores that error. The tests that script a server on a socket read with the same tick (`tests/common/shared.rs`).

`knowledge join` is what a session runs in place of `knowledge mcp`: a byte relay between its standard streams and the daemon, which it starts when none answers. When its input ends it shuts the writing half of the connection and copies replies until the daemon closes it, then exits 0. When the connection ends before the first reply byte it connects once more and sends again what it had sent (kept up to `REPLAY_CAP` bytes and dropped at the first reply byte), which covers a daemon that left as the session arrived. The replay happens once and only before the first reply byte, and the daemon may have executed a request it did not answer, so a tool call can run twice and its usage events can count twice. When the second connection ends with no reply byte too, an input that has ended exits 0, the same as a normal end, with the request unanswered and nothing on stderr (`relay` in `crates/tagents-core/src/knowledge/join.rs`), and an input still open exits 1 as below. When the connection ends after a reply byte with the input still open, the daemon died in the middle of the session: it exits 1 with `tagents-knowledge: the shared server went away` on stderr, so that the client sees its server die and reconnects. A daemon that cannot be had at all is no error: the session is served by the process itself, as `mcp` serves it.

**SQLite.** The index and the usage store are SQLite files with an FTS5 table, and the node program writes the same files, so the two programs have to read each other's. `rusqlite` with the `bundled` feature compiles one SQLite (3.54.1, FTS5 and the `unicode61 remove_diacritics 2` tokenizer in it) into the binary, on the three release targets, with no system library. The cost is a C compiler in the build, `musl-tools` on the musl runner and about 1.76 MB more in a release binary (measured on 01.11.2026, with the three rows of the dependency table). A sweep of every code point of the Basic Multilingual Plane, of U+10000 to U+3FFFF and of U+E0000 to U+E01FF compares what the tokenizer gives on both sides, one digest per 256 code points, and names the block that differs.

**The parser.** The front matter of a document is YAML 1.2, which node reads with the `yaml` package. `saphyr` reads it in Rust, and a converter turns its tree into the values the `yaml` package gives `doc.ts`, which then applies its own rules unchanged. A differential of 41 front matters on 01.11.2026 found the real differences, and the converter closes three: an explicit core tag (`!!int '7'`) is applied, a custom tag (`!custom`) is dropped and its value used untagged, and an integer above 2^53 is cast through `f64` and printed by `js::number_text`, as node prints a double. Complex mapping keys stay different: node renders such a key as text and the Rust key is the raw form. The six malformed documents agree on refusal and differ only in the wording of the error, which the server never prints; a document that stops parsing is dropped from the index.

The dependencies are listed with the others in "Rules for the Rust code".

## Where the two are known to differ

These are the differences the port does not hide, and the suite does not cover them:

- The usage text names `notify run` as served by the binary alone; the oracle build (tag `v0.6.7`) still adds that the binary hands over to node when it cannot start, a hand-over that was removed. The parity suites put the new words into the oracle's transcript (`oracle_usage_words` in `tests/lib/parity.sh`) and compare the rest.
- `tagents-core --spec` prints the spec as JSON on the Rust binary and is a usage error on the node CLI, so which program the wrapper picks changes what that call does.
- `tagents-core --version`, as the only argument, prints `tagents-core <workspace version>` and exits 0 on the Rust binary; the node CLI has no such flag and reports a usage error. It is the one identity check the installer makes of a downloaded binary, so it is not in `spec/cli/tagents-core.json`, which would move the plugin contract. With more words after it the flag is the node CLI's.
- A search word that holds U+FFFD can match a lone surrogate escape (`"\ud800"`) in a transcript, because Rust reads the escape as U+FFFD where a JavaScript string keeps the lone half.
- An object key that holds a lone surrogate escape is read as U+FFFD by the exact reader (`Exact::lone_key`), so a reference with such a key is `badRef`; nothing in a transcript or a reference is keyed by one that the verbs print. The stream of a turn is read by `json::parse_whole`, which keeps such a key.
- Lower casing uses the Unicode data of the Rust standard library, where node uses ICU's. Both gave the same result for every scalar value on node 22, and a newer node that knows a newer Unicode version can differ first.
- An I/O error is worded as node words it for the ten error numbers of `node::ERRNOS` (`ENOENT`, `EIO`, `E2BIG`, `ENOEXEC`, `ENOMEM`, `EACCES`, `ENOTDIR`, `EISDIR`, `EMFILE`, `ETXTBSY`, pinned by `the_errno_table_is_nodes`); any other error number prints Rust's description.
- A directory entry whose name is not UTF-8 is not listed. Node lists it with U+FFFD in the name, and the next `stat` on that name fails there.
- A modification time that `Date` cannot represent, and a `HOME` that is unset (the suite always sets it, empty at times), are not covered.

The plugin verbs differ from `packages/core` in these ways, and the suite leaves them out:

- A `--require` hook in `NODE_OPTIONS` is not run by the binary, so a hook that changes what `require.resolve` finds changes the answer of node's `plugin add` and not the binary's. The binary does not know the `lib/node` folder of the node installation either, and it resolves `exports` by the keys a package lists and the one pattern form with a `*`, not by the whole algorithm of conditions.
- The binary reads the `./package.json` subpath of `exports` by its key and does not follow its target, its conditions or the precedence of an exact key over a pattern, so it accepts some shapes that node refuses, and for `{"./*":"./dist/*"}` it gives `<pkg>` where node gives `<pkg>/dist`.
- `NODE_PRESERVE_SYMLINKS` and `NODE_OPTIONS` have no effect on how the binary finds a package, where they change what node's `require.resolve` finds.
- A temporary file is `<target>.<pid>.tmp` in both programs, so a crash between the write and the rename leaves a file named with the pid of the program that crashed.
- `plugin new` that fails to write undoes what it wrote, where node leaves the files it wrote; a crash of the binary between two writes leaves the files written so far, and a second `plugin new` then refuses the target as one that holds something.
- `doctor` starts one process, `node -p`, where node's `doctor` starts none. A `NODE_OPTIONS` hook that writes to stdout puts its text before the answer, which is then not an array, so line one reads `node: missing` where node prints the version. A node that cannot be asked prints `node: missing`, a line node cannot print. A signal ends the call by the exit status 143, 130 or 129, not by the signal, so `wait` reports an exit where node's `doctor` reports a kill.

The calls the binary words itself differ from node's text, and each scenario of the suites that sets `OWN_ERR` or `OWN_CODE` is on this list (`tests/rust-session-parity.sh`, `tests/rust-plugin-parity.sh`). The design rule that decides each one is named:

- A TOML document the parsers word differently (rule 2): `add: a config that is not TOML` and the corpus documents `bigint`, `ctrl-del`, `dup-key`, `dup-table`, `lone-cr`, `nul` and `nul-comment` for `add` and `remove`. Node prints `<file>: <smol-toml's reason>` and the binary prints `<file>: <the Rust parser's reason>`; the exit code is node's (1). The suite requires `<file>: ` in the binary's stderr.

A turn of `session prompt` differs from `packages/core` in these ways, and the suite leaves them out:

- An awake stall of more than 20 seconds. Node adds up awake time in ticks of 10 seconds, at most two ticks for one gap (`AWAKE_TICK_MS`, `packages/core/src/claude-driver.ts`), so it discounts a longer stall of its event loop, where the binary's limit is an `Instant` that counts it. Neither counts a machine that sleeps.
- A line in the pipe at the end of the drain. The binary takes what is already queued before it decides, and node's event loop can run its timer first and lose the line.
- A signal the caller left ignored. Node sets the dispositions back to their defaults when it starts, so a node CLI under `nohup` dies by SIGHUP and its child starts with the defaults. The binary installs no handler for it, so it keeps what it inherited: it survives that signal, and so does its child, SIGPIPE excepted, which `Command` resets. `claude` is a node program and sets its own dispositions. SIGCHLD is not in this class: on Linux a caller that ignores it has the kernel reap the child, so `session prompt` gives it a handler that only sets a flag, and `prompt-sigchld-ignored` runs that case; macOS keeps the disposition through exec but still lets a parent wait for its child.
- A descriptor the caller left open. On macOS node's child has every descriptor above 2 closed (`POSIX_SPAWN_CLOEXEC_DEFAULT` in libuv), and the binary's child inherits one that is not close-on-exec, because closing it takes `pre_exec`, which is `unsafe`.
- The order of the child's environment. `Command` sorts the names, and node keeps the order of `childEnv`.
- A line nested deeper than `JSON.stringify` can recurse, which depends on node's stack. Node's listener catches the `RangeError` and the event is dropped, and the binary prints it: under node 22 an input nested 5,000 levels prints on both, and one nested 20,000 levels on the binary alone.
- A terminal as stdout. Node writes to a terminal synchronously and to a pipe asynchronously, and the binary writes to both through its stdout thread, so a terminal that stops reading holds up the writes alone.
- A kill that fails with `EPERM`, from a child that changed its user. Node's `error` event makes the turn `spawn-failed` with that message, and the binary goes on waiting.
- A limit in the range of the time the child takes to start. The binary's deadline is the clock read before the spawn plus the limit. Node's is the same for a limit over `AWAKE_TICK_MS` (10 seconds); for one of 10 seconds or less its only timer is armed after the spawn, for at least 1 ms, so it kills later by the time the start took. Under `--timeout 0.5` on Linux node's child has run its first line by then and the binary's usually has not; on macOS neither has. `prompt-limit-under-a-millisecond` compares what the two print, not what the stub left.
- A reader thread that has read a chunk and is descheduled before it sends it, while a process outside the turn keeps the emptied pipe open past the drain. `queued` (`session/turn/supervisor.rs`) sees an empty open pipe and stops asking, so the turn decides its outcome without that chunk, and with `--events` its lines come after the outcome; node's one thread cannot be descheduled between reading and storing. Without such a holder the pipe polls as hung up and the turn waits for the reader.
- A file on macOS that `kernel_may_refuse` reads as one the kernel accepts and that the kernel then refuses: one replaced between the read and the start, or a fat file whose slice is damaged. It reaches the `/bin/sh` route of `posix_spawnp`, where node prints `spawn ENOEXEC`.

The MCP server differs from `packages/mcp` in these ways. The suite leaves them out, or pins the Rust side alone:

- A second signal during the ending: node dies by a repeat of the same signal (`process.once` in `packages/mcp/src/main.ts:18-33`), so a program that ignores SIGTERM outlives the call with no SIGKILL; the Rust server ignores the second signal and finishes the ending.

Where a server writes a request string back (the name in `unknown tool <name>`, the `id` of a request), Rust writes U+FFFD and node writes the escape. - A `notifications/cancelled` that arrives in the same read as its request: node never starts the program, the Rust server may start it and stop it at once.
- A pipe that a process outside the group holds open costs one blocked reader thread until it lets go; node destroys the stream.
- A process outside the group that keeps writing to a pipe holds a Rust call for up to the drain plus the grace after the program exited (2.25 s by default), because a pipe with bytes in it is read on past the drain; node destroys the streams at the end of the drain. A holder that writes nothing is given up on at the drain in both (`a_holder_outside_the_group_that_keeps_writing_does_not_hold_the_call_and_gets_epipe_after_it` in `crates/tagents-core/tests/mcp_run.rs` pins that the call ends and the holder gets EPIPE, not the bound); a call that was stopped is given up on at the drain even then (`a_call_that_was_stopped_is_given_up_on_at_the_drain_even_when_a_holder_keeps_writing`).
- A call that was stopped (timeout, cancellation, the server ending) is given up on at the drain after its program exited, whether or not a helper holds the pipes, so a reader thread that is descheduled for longer than the drain on a loaded machine can cost it output that node would have read; node's one thread reads the pipes in its poll phase whatever stopped the call, and ours gives a stopped call only the drain so that a second grace cannot overrun the server's ending, which waits `KILL_GRACE` plus `SHUTDOWN_MARGIN` (`server.rs`).
- A reader thread that has read a chunk and is descheduled before it stores it, while a holder outside the group keeps the emptied pipe open past the drain, loses that chunk, because the call sees an empty open pipe and gives up; node's one thread cannot be descheduled between reading and storing. Without such a holder the pipe polls as hung up and the call waits for the reader.
- A server started with SIGCHLD ignored gets ECHILD from `waitid` (`child.rs:195-206`) and reports a program that exited 0 as having no exit code; Claude Code starts its servers through libuv, which resets every signal disposition to the default in the child before exec.
- The usage line and the start-up failures say `tagents-core mcp` and not `tagents-mcp`, and a missing or invalid contract file is worded in Rust's words; the suite compares their exit codes only.
- The node CLI does not know `mcp`, and its list of reserved words (`reserved: session · sessions · plugin · config · doctor · help`, pinned by `packages/core/test/plugin-commands.test.ts`) is unchanged, so it still lets a plugin name a verb `mcp`; behind the front door that word is always the server's.
- `parseCliContract` has no Rust counterpart. The node server never calls it (only the generator in `packages/contract` does), so the one test of `contract-file.test.ts` that reads a spec with a program name of its own through it is not ported.

- A CRLF document: `splitFrontmatter` (`packages/knowledge/src/doc.ts`) cuts the `\r` of the last front-matter line together with its `\n`, so the last value reads as `Crlf` and the Rust reader reads the same text (`packages/knowledge/test/doc.test.ts`).
- A name for the index file that starts with `file:`. The bundled SQLite is built with `SQLITE_USE_URI` and `node:sqlite` opens every database with the URI flag, so at the library both read `file:rel.db` as the file `rel.db`, both make a folder named `file:sub` for `file:sub/rel.db` and then fail with `unable to open database file`, and both honour `?mode=memory` and `?mode=ro` (`tests/knowledge_file_uri.rs`). The verbs never hand either one such a name, because `resolveDb` (`packages/knowledge/src/paths.ts`) is `path.resolve(expandHome(value))`: `TAGENTS_KNOWLEDGE_DB=file:rel.db` creates a file named `file:rel.db` in the working directory, so the Rust verbs must resolve the path the same way before they open it.

The knowledge server and its daemon (`knowledge::{mcp, serve, daemon, socket, join}`) differ from the node `packages/knowledge/src/mcp` of v0.7.0 in these ways, and the suite leaves them out or asserts them on the Rust side alone:

- The socket of a Rust daemon is not the socket of a node daemon of the same environment, because the key starts with `rust:`; the two never serve each other's sessions, and a session that switches program starts a daemon of the other kind.
- The Rust daemon reads each connection in ticks of 500 ms (see "The knowledge server and its daemon"); node waits for the end of a stream without a tick.
- `join` retries once before the first reply byte and serves in process when no daemon can be had; the session of the node arrangement is `nc -U`, which does not retry, and when `serve` fails the launcher falls back to `mcp`.
- A session that reaches the socket while the daemon is stopped past its idle time waits in the backlog. When the daemon runs again the Rust one counts the connection before it decides to leave and serves the session; the node one closes the session with no reply, measured with `SIGSTOP` on Darwin (`d_backlog_past_idle` in `tests/rust-knowledge-parity.sh`).
- A node server writes the schema version into `meta` on every open of the index, which takes the write lock; the Rust one writes it only when it differs, so a reader that changes nothing writes nothing (`r_reader_writes_nothing` in `tests/rust-knowledge-parity.sh`).
- An `--idle` longer than 2147483 seconds is waited for in full by the Rust daemon; the node one clamps it to the longest timer a `setTimeout` counts (2^31 - 1 ms, about 24.8 days).

## What is not decided yet

Whether `session prompt` should end at the drain instead of lingering while a grandchild holds a pipe of the child, which changes what that grandchild sees on its next write, is open, and so is what replaces the node directory at the head of the child's `PATH` on a machine that has no node, which has to go to the fallback today and gets the front door's error.

All five `session` verbs have a Rust implementation and node's stay as the fallback for a machine with no Rust binary. Retiring the node verbs comes only after a release has shipped the binary for a while, and when is open. The change that introduced the front door, `openspec/changes/archive/2026-10-31-rust-core/`, lays out the slices. Signing or notarising the archives is not done (see the last paragraph of "How the installer fetches it"), and a Windows build does not exist.
