# The Rust front door of tagents-core

`tagents-core` is moving from node to Rust one verb group at a time. This page explains the seam that makes that safe: a Rust program that answers the verbs it has and runs the node CLI for everything else, the file that lists which program serves which verb, and the suite that proves the two print the same bytes. A machine with no Rust binary runs the node CLI it always did, and a managed install fetches the prebuilt binary only when a GitHub release exists for the version it holds ("How a release is made" and "How the installer fetches it" below).

## What is served in Rust today

`tagents-core sessions` (`recent [N]`, `search <words…>`, `show <id-prefix>`, and the bare `sessions` that means `recent`) is a port of `packages/core/src/transcripts.ts`, `tagents-core mcp --contract <file>` is the plugin's MCP server, a port of `packages/mcp` ("The MCP server"), and `tagents-core notify run` is the notification daemon, a port of `packages/notify`'s service ("The notify daemon"). Every other word is the node CLI's: `session`, `plugin`, `doctor`, a plugin's own verbs, help and a word nobody knows. The node CLI itself does not know `mcp` (`unknown command: mcp`), so on a machine with no Rust binary the plugin's server is `packages/mcp/dist/main.js`, as before.

The decision is made by the first word, so a group of verbs belongs wholly to one program: `sessions rescent` is answered by Rust with the node CLI's usage line and exit code. `notify` is the one word that is not decided alone: the arm matches exactly the two words `["notify", "run"]` (`crates/tagents-core/src/front_door.rs:46` and `:138`), and every other argument list that starts with `notify` (`notify status`, `notify install`, `notify run extra`) goes to the node CLI, which hands it to the plugin host, so a verb of the plugin keeps the word.

The LaunchAgent and the `tagents-notify` wrapper start the node service: the LaunchAgent's program is the node that ran `tagents notify install` with `packages/notify/dist/main.js run` (`packages/notify/src/plugin.ts:130`), and the wrapper `install.sh` writes execs `node $TAGENTS_HOME/packages/notify/dist/main.js` and never names the binary (`install.sh:16`, `:282`; only `tagents-core` and `tagents-mcp` do). `tagents-core notify run` runs when a person or a caller names it, and nothing on a machine starts it by itself.

## The front door

The binary is `target/release/tagents-core`. A contributor builds it with `cargo build --release`; a managed install gets the prebuilt, checksummed one of its own version from the GitHub release `v<version>` (`pnpm build` builds nothing of it, and `install.sh` never compiles it).

```sh
target/release/tagents-core sessions recent 3   # answered in Rust
target/release/tagents-core plugin list         # exec node packages/core/dist/cli/main.js plugin list
target/release/tagents-core --spec              # the verbs this binary serves, as JSON
target/release/tagents-core --version           # tagents-core 0.5.0: the workspace version it was built from
```

For a word it does not serve, the binary replaces itself with `node packages/core/dist/cli/main.js` of the checkout it sits in, with the same arguments, environment, working directory and stdio. There is no wrapper process left: the exit code, and a signal the call ends with, are the node CLI's own. The node is `$TAGENTS_NODE` when that is set (the wrappers `install.sh` writes set it to the node they pinned), and `node` on `PATH` otherwise.

When it cannot find the node CLI it prints `tagents-core: cannot find <relative>: <why>; this binary has to stay in <root>/target/<profile>/ of a root where it is built`, with the node CLI's path below the root and the reason it failed, and exits 2. A binary copied anywhere else does not find the node CLI. When the node cannot be started it exits 127 if there is no such file and 126 if there is one that cannot run.

## Which program a command goes to

The verbs live in `spec/cli/tagents-core.json`, described by `spec/cli/cli-spec.schema.json`. Each command says `"impl": "rust"` or `"impl": "node"`, and may carry an `effect` (`read`, `write`, `spawn`, `destructive` or `serve`) and `"tool": false`, which the plugin contract generator reads. The node CLI reads the file (`packages/core/src/cli/spec.ts`), the contract generator reads it through the node CLI, and the Rust crate `tagents-spec` embeds it, so moving a verb between languages is a one-word edit that leaves the generated plugin contract untouched. `pnpm plugin:gen` then shows no diff, and a test in `crates/tagents-core/tests/front_door.rs` checks that `tagents-core --spec` prints exactly the `rust` entries of the file.

Both loaders refuse the structural mistakes the schema forbids: a key the schema does not name, an empty `program` or `summary`, an empty `path`, an empty word in `path`, `positionals` or `required`, and a `null` where the schema says string or boolean. Both add the one rule a schema cannot state, that two commands never share a `path` (dispatch is by path, so the second would never run). The Rust loader is the stricter one: no input is known that it loads and the node loader refuses. It refuses three inputs the node loader accepts: an `exit` value written `1.0` (the number 1 to JavaScript, a non-integer to the `u8` the model holds), a key written twice in one object (`JSON.parse` keeps the last), and a lone surrogate escape in a string (`JSON.parse` accepts it); a unit test in `crates/tagents-spec/src/lib.rs` pins each. The path to the data file in `packages/core/src/cli/spec.ts` (`SPEC_FILE`) leads out of `packages/core`, so the package works from a checkout and from `$TAGENTS_HOME`, which is one, and would not work from a packed tarball (`files` is `dist`, which does not hold the data file). Nothing publishes or packs the package, and the repository installs from a clone; the package is not marked `private` because the plugin contract lists the public API of every package that is not.

The one-line summary of a command stays in the language catalogue (`packages/core/src/i18n/`), keyed by the `summary` field, so there is one source of the text.

## The MCP server

`tagents-core mcp --contract <file>` is the plugin's MCP server: JSON-RPC, one message per line, on stdin and stdout, with one tool for every command of the `cli` section of the contract. It is a port of `packages/mcp`, which stays in the tree as the oracle of the parity suite and as the server a machine without the Rust binary runs. The contract is read once, at start (`crates/tagents-core/src/mcp/contract.rs`), so a plugin update brings a new file and the next session sees the new tools. `plugin.json` is unchanged: it registers the wrapper `tagents-mcp`, which `install.sh` writes to start `tagents-core mcp --contract <contract.json>` when the Rust binary exists at install time and `packages/mcp/dist/main.js` otherwise.

```sh
target/release/tagents-core mcp --contract contract.json                    # serves until stdin ends or SIGTERM, SIGINT or SIGHUP arrives
target/release/tagents-core mcp --contract contract.json < requests.jsonl   # a request a line, an answer a line
```

The code is in `crates/tagents-core/src/mcp/`: `contract.rs` reads the file, `tools.rs` makes the tool of each command (name, description, annotations, input schema) and the command line a call stands for, `run.rs` turns one call into a program and an answer, `server.rs` is the loop and `rpc.rs` is the wire. The program is run by `child::run` and the ending is `ending::Stop` and `ending::on_signals`, which are modules of the crate and not of `mcp`, because whatever else spawns a program or ends on a signal uses them too (`crates/tagents-core/src/child.rs`, `crates/tagents-core/src/ending.rs`). Stdout carries JSON-RPC lines and nothing else: the module denies `print_stdout`, and `rpc::Out` is the only writer.

**What it answers.** `initialize` answers the protocol version the client asks for when the SDK of `packages/mcp` lists it (`2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`, `2024-10-07`; the suite reads the list from the SDK) and the newest otherwise, and tells `serverInfo.version` as the workspace version, where the node server's constant is `0.1.0`. Then `ping`, `tools/list`, `tools/call` and the notification `notifications/cancelled`. Any other method is -32601 `Method not found`, and a call of a tool nobody listed is -32602. A command is a tool unless its spec entry says `"tool": false` or its effect is `serve`, so `mcp` is not one. `contract.json` records the list the generator made from the specs, and a test (`crates/tagents-core/tests/mcp_server.rs`) pins the list `tools.rs` makes from the same file to it.

**Threads.** The main thread reads stdin and answers `initialize`, `ping` and `tools/list` itself. Each `tools/call` runs on a thread of its own, so a slow call does not hold up the next request, and the answers are written in the order the calls finish, not the order they came in. One writer behind a lock writes each message with a single `write_all`, so two answers never interleave. A thread of its own takes SIGTERM, SIGINT and SIGHUP from `signal-hook`'s iterator and starts the same ending as the end of stdin, so no signal handler runs arbitrary code.

**A call.** The program of the verb runs as a child with no stdin, the server's environment and a process group of its own. Each stream keeps its first 256 KiB: the rest is read and thrown away so that the program never blocks on a full pipe, and the cut falls before a character it would split, followed by `\n[output cut at 262144 bytes]`, with `"truncated": true` in the result. A call that has not ended in five minutes, a `notifications/cancelled` for its request, and the end of the server each stop the whole group: SIGTERM, then SIGKILL two seconds later. When the program exits by itself, whatever it left in its group is killed at once and the pipes get 250 ms to drain, because a process that left the group can hold them open for good. At the end of the drain a pipe that still holds bytes, or has lost its last writer, is read on in steps of 10 ms, for at most the drain plus the grace after the exit (`readable` and the timeout arm of `supervise`, `crates/tagents-core/src/child.rs:290-299` and `:344-356`): its reader thread has not run yet, which the machine's load can cause, and a reader thread that has not run is not a holder. A holder that keeps an empty pipe open is given up on at the drain, and so is a call that was stopped, since its answer is `cancelled` or its output is partial already. `a_program_that_exits_with_its_output_still_in_the_pipe_loses_none_of_it` in `crates/tagents-core/tests/mcp_run.rs` pins that nothing the program wrote before it exited is lost when no helper outside the group holds the pipes. Nothing a call starts in that group outlives the call. A process that called `setsid` has left the group, is not the call's to stop and keeps running, as it does under the node server; `a_holder_of_the_pipes_that_left_the_group_cannot_be_killed_and_still_does_not_hold_the_call_longer_than_the_drain` in `crates/tagents-core/tests/mcp_run.rs` pins that such a holder of the pipes still does not hold the call longer than the drain. The constants are pinned to the TypeScript sources by `crates/tagents-core/tests/mcp_pins.rs`, which reads `packages/mcp/src/run.ts` and `main.ts`.

**The result** is `{"content": [{"type": "text", "text": <body>}], "isError": <exit is not 0>}`. The body is the two-space pretty form of `exit`, `outcome` (the first name of the program's `exit` table that carries the code, else `exit <code>`), `stdout`, `stderr` and, when a stream was cut, `truncated`. A refusal has the same shape, with an empty stdout and the reason on stderr. When stdout, after leading JavaScript white space, starts with `{` or `[` and parses as JSON, the body holds the parsed value and not the escaped text; only JSON white space (space, tab, line feed, carriage return) may stand before the document, as in node, so a document behind a no-break space stays text. Node reads that document and writes it again, so the Rust server keeps the order of the keys (`preserve_order`) and tells every number as `JSON.stringify` tells the double it reads as: `1.0` is `1`, `1E2` is `100`, `-0` is `0`, `1e400` is `null` (`js::number_text`, `mcp/run.rs`).

**The ending.** The end of stdin, one of the three signals, or a write error on stdout (the client is gone) ends the server: every call in flight is stopped and answers with the outcome `cancelled`, the server waits until they have answered, for the two seconds of the grace plus two more at the most, and exits 0. A second signal during the ending is caught and ignored (`ending::on_signals`), so a program that ignores SIGTERM still gets its SIGKILL after the grace. A call stopped by `notifications/cancelled` gets no answer, as with the SDK, even if it had finished by then. The answer is written before the call leaves the registry the ending waits on (`Registry::settle` and `finish` in `server.rs`): a registry that empties first lets the process exit with the answer unwritten, which a test pins (`the_ending_returns_only_after_the_answers_of_the_calls_it_stopped_are_written`). A request line longer than 10 MiB, the SDK's `STDIO_DEFAULT_MAX_BUFFER_SIZE`, is treated as the end of the stream.

## The shared child, the ending and the file watch

Three modules of the crate belong to no verb: `child.rs` runs a program with a deadline, `ending.rs` ends a process on a signal, and `watch/` tells a thread that a file or a directory changed. `mcp` and `notify run` are the callers of the first two and `notify run` is the caller of the third, and none of the three knows either, so whatever spawns a program, ends on a signal or waits for a file next uses them and does not copy them.

**The child.** `child::run(command, &Policy, &Stop)` is what "A call" above describes, plus two things the caller chooses. `Policy::input` is written to the child's stdin by a thread of its own, `tagents-in`, which closes stdin after the last byte (`write_input`, `crates/tagents-core/src/child.rs:190`, started at `:270`); `None` gives the child `/dev/null` and never the parent's stdin. The write error is dropped on purpose: a program that exits without reading its input makes the write fail with EPIPE, and its exit code says the rest. A program that never reads its input keeps that thread in the write until the call stops the program, and the thread is detached, so a process outside the group that keeps the read end of the pipe open keeps it there until that process ends. `Policy::kill_grace: None` is SIGKILL at the deadline and at a stop, with no SIGTERM first (`stopping`, `child.rs:373`). A call that was stopped, with a grace or without, gives the pipes the drain and no more (`child.rs:349`). The drain plus the grace, or plus `READER_WAIT`, two seconds, when there is no grace, is for a program that exits by itself with bytes or an end still in a pipe whose reader has not taken them yet (`child.rs:347`); `with_no_grace_a_program_that_exits_with_its_output_still_in_the_pipe_loses_none_of_it` pins it. `Finished` says which stream was cut (`stdout_cut`, `stderr_cut`) as well as ending it with the marker.

**The ending.** `ending::Stop` is the token a call carries and `ending::on_signals` turns the first SIGTERM, SIGINT or SIGHUP into one call of a function on a thread of its own, which gets the name of the signal as node spells it (`"SIGTERM"`) so that a daemon can log which one stopped it; `the_function_is_given_the_name_of_the_signal_that_came` pins the three names (`crates/tagents-core/tests/ending_signals.rs`; the code is `crates/tagents-core/src/ending.rs:14` and `:52`). A `Stop` that several calls share keeps one watcher per call until it trips, so a call that outlives many others takes a stop of its own. `sync::locked` is how the crate takes a lock: a poisoned lock hands back its data, because what sits under these locks is valid between any two of its steps (`crates/tagents-core/src/sync.rs:5`).

**The watch.** `Watch::start(sink)` starts a thread, `tagents-watch`, that sends `T::from(Heard::Fired(key))` to the sink for every key whose watch fired, and `T::from(Heard::Ended(error))` once when a wait fails, or a re-arm of a key's file watch fails for any reason but a missing file, and the thread has to end; `dir(path, key)` and `file(path, key)` arm a directory watch and a file watch for a key, one of each per key, a second call for the same key and kind replacing the first (`crates/tagents-core/src/watch/mod.rs:105`, `:120`, `:125`). On Linux the thread blocks in `poll` over the inotify descriptor and a wake pipe, on macOS in `kevent` through the `kqueue` crate with the wake pipe registered as one more event, and in both with no timeout: nothing in the module sleeps, polls or wakes on a timer (`watch/linux.rs:112`, `watch/macos.rs:124`). Arming a watch sends a command to the thread over a channel, writes a byte to the wake pipe and waits for the thread's reply, so `dir` and `file` return only when the watch is armed and never wait for an event (`mod.rs:129`). Dropping a `Watch` drops the channel, writes the byte and joins the thread, so it ends while it waits (`mod.rs:153`).

A caller that must not lose a write does three things. It arms the watch and only then reads the file to the end, because an edge-triggered watch says nothing about a write that landed before it was armed. It reads to the end again on every key it hears, because one wake can stand for several writes. And it resolves the directory it wants watched to its real path before it passes it, because the watch takes the path as written. `no_byte_is_missed_when_writes_land_as_the_watch_is_armed` in `crates/tagents-core/src/watch/tests.rs` writes to a new file while its watch is armed, 200 rounds, and fails when the read after the arming is removed; `arming_another_watch_loses_no_wake_of_one_already_armed` writes to one file while 300 others are armed after it and pins that none of its wakes is lost.

**What a watch hears.** A directory watch fires when an entry is added, removed or renamed. On Linux it also fires when a file in the directory is written, because inotify reports that; kqueue does not, so nothing may depend on it. A file watch sits on the inode and fires when the file is written, grown, truncated, removed, renamed or revoked; `a_file_truncated_in_place_is_heard` and `a_file_truncated_by_creating_it_again_is_heard` pin truncation. The masks are what libuv asks inotify for (`watch/linux.rs:17`) and the vnode notes that cover the same events on kqueue (`watch/macos.rs:16` and `:24`). Several keys may watch one directory, and an event reaches every one of them: inotify gives one descriptor to an inode however many times it is watched, so the Linux backend keeps the slots apart and removes a descriptor only when the last slot on it leaves (`watch/linux.rs:50` and `:61`), where macOS opens a descriptor for every slot; `two_keys_on_one_directory_both_hear_an_entry_written` and `a_key_that_leaves_a_directory_does_not_take_the_watch_of_another_key_with_it` pin both halves on both systems.

**Where a file watch goes stale, and what the thread does about it.** A file saved by writing a temporary file and renaming it over the path leaves the file watch on an inode that is no longer at the path. The thread therefore opens the path again, before it reports the key, whenever the key's directory reports anything and whenever the file's own watch reports that the inode was deleted, renamed or revoked (`mod.rs:163-211`; `a_file_saved_by_rename_and_then_edited_in_place_is_heard_again` and `a_file_watch_alone_follows_the_path_across_a_rename` pin it). The path is remembered per key from the first `file` call, whether or not that call found a file, so a file created later is watched from the next directory event on (`a_file_that_did_not_exist_is_watched_from_the_next_directory_event`). Linux reports a file written in a watched directory through the directory, so without the re-arm only the second of the two tests fails there; on macOS both fail. On Linux a rename over a file that a reader still holds open sends `IN_ATTRIB` for the old inode's link count and no `IN_DELETE_SELF`, which comes only when the last descriptor of that inode closes, so `ATTRIB` re-arms a file watch too (`FILE_GONE`, `watch/linux.rs:27`); `a_file_replaced_while_a_reader_still_holds_the_old_one_is_followed_to_the_new_one` pins it.

**A symlink is never followed by a file watch.** `file` on a path that names a symlink returns `Ok(())` and arms nothing, so the target of a link being edited is not heard and the link being replaced is heard through the directory. On macOS the path is opened with `O_NOFOLLOW`, and `ELOOP` is how the kernel says that the path is a link (`watch/macos.rs:114`); the open is also `O_NONBLOCK`, so that a FIFO at the path does not hold the watch thread, and `Drop` behind it, until a writer opens the other end (`a_fifo_does_not_hold_the_watch_thread_for_a_writer`). inotify takes a path and not a descriptor, so on Linux the path is looked at with `symlink_metadata` first and armed with `IN_DONT_FOLLOW` (`watch/linux.rs:104`); a link swapped in between the two is armed on the link itself, so its target is still not followed. A directory that is a symlink is followed, because the caller names the directory it wants and a directory is not a file the caller reads. `a_symlink_has_no_file_watch_so_its_target_edited_is_not_heard_and_the_link_replaced_is` and `a_directory_that_is_a_symlink_is_followed_and_a_file_is_not_a_directory` pin both halves.

**Descriptors.** Every descriptor of a watch is close-on-exec, and dropping a watch closes every one it opened (`crates/tagents-core/tests/watch_fds.rs`: `dropping_a_watch_closes_every_descriptor_it_opened` counts the process's descriptors through `/proc/self/fd` or `/dev/fd` over five rounds, and `a_child_spawned_beside_a_live_watch_inherits_none_of_its_descriptors` lists what `/bin/sh` sees). Two limits remain. macOS has no `pipe2`, so a child forked by another thread between the `pipe` and the `fcntl` of the wake pipe inherits its two ends until it execs (`mod.rs:225`). The kqueue descriptor is made by the `kqueue` crate, which gives it back only as a raw descriptor that safe code cannot flag; kqueue(2) says a queue is not inherited by a child, and the second test above passes on macOS with a live watch. On Linux `inotify_init1` takes `CLOEXEC` and the wake pipe is `pipe2` (`mod.rs:220`).

**Known limits.**

- A wait that fails (a closed descriptor, a kernel error), or a re-arm of a key's file watch that fails for any reason but a missing file (a descriptor or watch limit), ends the thread after one last `Heard::Ended(error)` to the sink, which is what lets a daemon whose sink is a shared channel learn that the watch is dead; the keys that fired in the same wake are not delivered after a failed re-arm, because the thread returns before it sends them (`mod.rs:194-204`); `a_re_arm_that_fails_for_want_of_a_descriptor_ends_the_watch_with_the_error` and `a_wait_that_fails_is_the_last_thing_the_sink_hears_and_then_the_thread_ends` pin the two endings; `dir` and `file` then fail with "the watch thread has ended". The module does not restart it. On macOS an event the `kqueue` crate cannot decode (`InvalidData`, a vnode event with no flag it knows) is skipped, as `NotFound` is, and is not a failed wait.
- A re-arm that fails because the file is gone leaves the key without a file watch until the next directory event or the next `file` call, and the key is reported all the same (`a_re_arm_that_finds_the_file_gone_is_no_ending`).
- On macOS a file watch the kernel refuses (kqueue refuses a vnode watch on a pipe, for one) is removed from the queue again, because the `kqueue` crate keeps the refused entry and re-submits it with every later `watch`, which would fail the arming of every other key (`watch/macos.rs:72-79`; `a_watch_the_kernel_refuses_does_not_stop_the_arming_of_the_next`).
- A directory watch on macOS does not report a write inside the directory, so a caller that follows a file by its directory alone hears a replacement but not an edit in place; it arms the file as well.
- inotify has a limit on queued events and on watches per user (`fs.inotify.max_queued_events`, `fs.inotify.max_user_watches`). A queue that overflowed lost events, and the thread reports every key and re-arms every file watch (`watch/linux.rs:71`). A system out of watches makes `dir` and `file` fail with the operating system's error.
- kqueue holds a descriptor for every watched file and directory for as long as it is watched, so a process near its descriptor limit fails to arm.
- The thread ends when the sink has no receiver, with no value, because there is nobody to send it to; a `Watch` whose thread ended is not told, and the next `dir` or `file` is the first thing that fails.

## The notify daemon

`tagents-core notify run` is the notification service of `packages/notify` (`service.ts`, `engine.ts`, the options, the lock) in Rust: the process that follows `events.tsv`, posts a notice through the macOS helper or the `log` backend, and holds a prompt-cache deadline per idle session. It serves nothing but `run`: `install`, `status`, `setup` and the other verbs stay the node CLI's ("Which program a command goes to"). The requirements are `openspec/changes/rust-notify/specs/rust-notify/spec.md`, which this section cites by name rather than restating, and the behaviour it copies is node's, so where a line below says "as node does" the node code is the specification. The modules are under `crates/tagents-core/src/notify/`: `service.rs` (the process), `engine.rs` (events in, notices out), `feed.rs`, `events.rs` and `state.rs` (the agent feed), `options.rs`, `lock.rs`, `hand_over.rs`, `deadlines.rs`, `screen.rs`, `compose.rs`, `phrases.rs`, `kinds.rs`, `helper.rs` and `platform.rs`.

**Three threads and one channel.** The main thread is the engine; the watch thread (`watch::Watch`) and the signal thread (`ending::on_signals`) only put a `Message` (`Wake(Key)`, `Ended(error)` or `Stop`) on one `mpsc` channel (`service.rs:43`, `:3`). The loop waits on it with a timeout of the engine's next deadline, runs what a message means to the end and only then reads the next, so a post that takes five seconds holds the loop for five seconds while the other two threads keep queueing (`serve`, `service.rs:326`). There is no runtime, no timer thread and no poll: the one timed wait is the channel's, which is what "Nothing polls" requires. Everything the loop asks of the clock goes through `Clock::now_ms` (`notify/clock.rs`), and a deadline is a wall-clock time asked again on every wake, capped at five minutes (`deadlines::MAX_SLEEP_MS`), because a cache's time-to-live runs in wall time and a Mac that slept through a deadline would otherwise be hours late.

**The engine** is a plain struct that the loop drives with five calls, `start`, `wake`, `next_due`, `reload` and `stop` (`engine.rs:267`, `:280`, `:297`, `:313`, `:318`); it has no thread, channel or timer of its own, so the tests drive it with a scripted feed, a fake clock and a recording log. One FIFO queue of jobs holds what a wake brought: each line of the follower is a job, followed at once by a sweep that queues the deadlines that have come due, and a wake that brought no line sweeps once, which is node's deadline timer (`ingest` and `sweep`, `engine.rs:369` and `:384`). A prompt that cancels a key is therefore seen before that key's cache notice runs. A call runs every job it made before it returns; the stop of a signal is looked at between two jobs and never inside one, so a post in flight lands and the jobs behind it are dropped (`engine.rs:349`). A job that panics is logged as `error <why>` and the next job runs, as node's `enqueue` does (`caught`, `engine.rs:344`; `a_job_that_panics_is_logged_as_an_error_with_its_text_and_the_next_job_runs`), which needs the release profile to unwind: `panic = "abort"` would turn one bad job into the end of the daemon. A follower that dies is followed again after one second, doubling to five minutes while it keeps dying, and the wait starts over only for a follower that heard an event or lived longer than the wait before it (`engine.rs:37`, `:433`; `a_follower_that_dies_at_once_three_times_is_followed_after_1_2_and_4_seconds`); what was written while it was dead is gone, so the state rows arm again what those events would have (`engine.rs:449`).

**What the watch watches, and a reload.** One `Watch` serves two keys. `Key::Events` is `events.tsv` and its directory, armed by the follower; `Key::Options` is the `plugins` directory of the config directory and the file `notify.toml` in it. The config directory is usually a symlink into a dotfiles repository, which a watch does not follow, so the options watch arms the real path (`OptionsWatch`, `service.rs:194`; `a_symlinked_config_dir_is_armed_by_its_real_path_and_a_change_wakes_the_loop`). It arms the directory, then the file, then reads the options once more, because a write between the first read and the arming raised no wake (`a_file_that_changes_between_the_first_read_and_the_arming_is_read_once_more`). When `plugins` does not exist yet its parent is watched in its place and the daemon moves to `plugins` when it appears, with one look after the arming of the parent, because a directory made between the first look and the arming raises nothing (`a_directory_that_appears_later_is_adopted_and_watched_in_its_parents_place`). With no config directory at all it logs `options reload is off: <dir> does not exist` and runs on (`with_no_config_dir_reload_is_off`). A directory watch cannot filter by name, so every wake of `Key::Options` reads the file and `Settings::apply` ignores a read that says what is in force already: an unrelated file, the same bytes in other words, or a file that is back to the defaults after a bad one log nothing (`service.rs:151`; `the_same_value_in_other_words_and_an_unrelated_file_are_no_reload`). A changed value logs `options reloaded` and the engine reads it at its next job; a changed backend logs `backend changes take effect after a restart (tagents notify install)` and is not applied (`a_reload_to_the_value_in_force_is_ignored_and_a_changed_backend_waits_for_a_restart`). A bad file never stops the daemon: the defaults are in force and each problem is logged once, however often the file is read.

**Which parser reads what.** The tree has two parsers besides the hand-written ones, and each exists because a byte of the daemon's output depends on it. `toml` reads the options file (`options.rs:210`, `DeTable::parse`): the crate gives the parse tree and the code checks it by hand against node's schema, because the lines the daemon logs are zod's, in zod's order, and serde's texts would be other words in another order; an integer beyond 2^53 is read by the crate and refused by the code, which is what node's parser does. `json.rs` follows `JSON.parse` and reads what is not ours to shape: a transcript, for the body of a `turn_done` notice (`transcripts::last_assistant_text`, called from `compose.rs:76`), and the line the helper prints (`helper.rs:106`); `json::quote` is the one `JSON.stringify` of a string, for log lines and the helper's input. `serde_json` only builds the helper's input, in node's key order (`helper.rs:9`). The events file and the state rows are tab separated text, split by hand (`events::parse_event_line`, `events.rs:109`; `state.rs`). Every copy of a node rule that changes a byte is pinned by `crates/tagents-core/tests/fixtures/notify-vectors.json`, which `tests/rust-notify-vectors.mts` writes from the real node functions, `crates/tagents-core/tests/notify_vectors/` reads, and CI regenerates and compares (the step "The notify vectors node writes are the ones committed" of `.github/workflows/rust.yml`).

**The lock shared with node.** `<state dir>/notify.lock` (`LOCK_FILE`, `lock.rs:23`) holds `<pid> <start time>\n`, the start time as `/bin/ps -o lstart=` prints it under `LC_ALL=C TZ=UTC`, or the bare `<pid>\n` of the first format, which is still read; it records no host name, as node's does not. A node daemon and a Rust daemon on one state directory exclude each other because `take_lock` is node's `takeLock` byte for byte (`lock.rs:228`; "One service per machine, whichever program runs it"). The file is made whole or not at all: the text goes into `notify.lock.<pid>.<8 hex>.tmp` and `link` puts it at the lock path, which fails when something is there, so a reader never sees it empty (`create_lock`, `lock.rs:149`; `the_lock_is_never_visible_empty_and_no_temp_file_is_left`), and taking the lock first sweeps the temp files of a dead pid or older than a minute, of that exact shape and no other (`lock.rs:175`). A holder is told from a stranger by the start time, because pids are reused: the pid is alive (signal 0, `EPERM` counts as alive) and `ps` gives the start time the file recorded (`holds`, `lock.rs:127`). A lock with no start time, or a `ps` that cannot answer in two seconds, falls back on the lock's age against the boot time read once at start, `kern.boottime` on macOS and `/proc/uptime` on Linux (`boot_ms`, `lock.rs:287`), and a lock whose pid is the daemon's own is never held, which is how the node service that a failed start is handed to takes over the lock its predecessor made under the same pid. A takeover removes the stale file only while it still says what was judged, and two takeovers over one stale lock end with exactly one holder (`two_takeovers_racing_over_one_stale_lock_end_with_exactly_one_holder`); between the read and the removal another process can still put its own lock there, the window node's protocol has between two node processes, since node takes no mutex that a second implementation could honour. Release unlinks the file only while it names this process, so a lock somebody else took over survives (`lock.rs:254`).

**The start, and the hand-over of a failed start.** `run` (`service.rs:471`) does these steps in this order: register SIGTERM, SIGINT and SIGHUP (`:489`); create the state directory (`:492`); take the lock (`:504`), where a live holder is `another notify service holds <file> (pid <n>); exiting` and exit 0 with the lock untouched; read the options (`:518`); pick the backend (`:524`), where `none` and a system with no backend are `<why>; exiting`, a release of the lock and exit 0, which is a choice and not a failure (`leave`, `service.rs:454`); start the watch thread (`:529`); build the engine and `start` it, which follows `events.tsv` and arms the sessions the state rows say are idle (`:556`); arm the options watch (`:562`); and write `started`, last, so that whoever waits for that line finds the lock, the stream, the engine and the watchers all up (`:566`). A failure of any step before `started` that is not a deliberate exit is handed to the node service (`hand_over`, `hand_over.rs:44`; the requirement "A start that fails is handed to the node service"): unless a stop was requested, the daemon writes `handing over to the node service: <why>`, closes the follower and the watch, and replaces its process with `node packages/notify/dist/main.js run` in the same environment, which runs or fails by its own lines. The exec keeps the pid and the lock is not released, so the lock still names the process, the node service reads it as its own and no manual `run` can slip in between (`a_hand_over_says_why_closes_and_keeps_the_lock_across_the_exec`, `the_lock_still_names_the_pid_after_the_exec`). The watch is closed first because the kqueue descriptor is not close-on-exec and safe code cannot set the flag (see "Descriptors" above): an exec would carry it into node, so `WatchSlot` drops the real `Watch`, which joins its thread and closes every descriptor, before the exec (`service.rs:382`; `a_closed_watch_slot_arms_nothing_and_closes_twice_without_harm`). When the exec fails the lock is released, `could not hand over to the node service: <why>` is written (the same line when `packages/notify/dist/main.js` is not there, with no `tagents-core: cannot find` line) and the exit is 1, the code launchd retries (`an_exec_that_fails_writes_the_line_and_exits_1_with_the_lock_released`, `a_missing_main_js_writes_the_same_line_exits_1_releases_the_lock_and_prints_no_cannot_find_line`). A failed `Command::exec` leaves SIGPIPE at its default in the caller, so a daemon whose stderr has closed can die of it on that last line. The registration of the three signals, the first step of `run`, is a step that hands over (`service.rs:489`), which node has no counterpart of: its handlers are `process.on` calls that cannot fail to register. A failure after `started` is never handed over, because an exec there would lose the events queued in the engine and its record of the cache notices already sent; a watch of the options directory or file that cannot be armed is a line, `options watch failed <path> <why>`, and the daemon runs without that reload (`a_failed_options_watch_does_not_hand_over`).

**The stop.** A signal ends the daemon as node's `stop` ends it, in this order (the requirement "A signal ends the service as it ends the node service"): the line `stopping (<signal name>)`, then the stop token is tripped so that the post in flight lands and the jobs behind it are dropped, then the watch is closed, the engine stops (the follower closes and `events.on` is removed with the last follower), and the lock is released last, so a restart cannot overlap what is still being drained (`end`, `service.rs:351`; `stopping_precedes_the_notice_of_a_post_in_flight`, `the_watch_closes_first_and_the_lock_goes_last`). The line is written once by whichever thread gets there first: the signal thread, or the main thread when the watch ended (`Said`, `service.rs:95`; `the_stopping_line_is_written_once_by_the_signal_or_by_the_watch_that_ended`). A signal that arrives during start is only remembered by the `StartGate` (the first one wins): the main thread writes the line after `started`, and a start that fails writes no `stopping` line at all, releases the lock, exits 0 and does not exec (`service.rs:59`; `a_signal_during_a_start_that_succeeds_logs_started_and_then_stopping`, `a_signal_during_a_start_that_fails_logs_no_stopping`, `a_stop_during_a_failing_start_ends_the_process_and_does_not_exec`). The loop looks at the stop before each message, so wakes queued behind a signal are dropped (`a_wake_queued_behind_a_tripped_stop_is_dropped`). A follower that will not close is `drain failed <why>` and the lock is still released.

**When the watch ends.** The watch thread sends `Heard::Ended` once and stops when a wait fails or a re-arm fails for a reason other than a missing file ("Known limits" above). Nothing is polled, so a daemon whose watch is dead would never hear another write; node keeps running in that case because it has other mechanisms (a retry timer for the follower, an options watcher that closes and leaves the rest going). The Rust daemon therefore stops: the loop serves the post in flight and the wakes queued ahead of the end first, in channel order, then writes `stopping (watch failed: <why>)`, runs the stop above and exits 1 (`Ending::WatchFailed`, `service.rs:315` and `:363`; `a_watch_that_ends_behind_a_post_in_flight_is_served_after_the_queued_wake_and_stops_with_its_reason`, `a_watch_that_ends_with_nothing_in_flight_stops_with_its_reason_and_exits_1`). Exit 1 is what the LaunchAgent restarts: its `KeepAlive` is `SuccessfulExit` false with a `ThrottleInterval` of 300 seconds (`packages/notify/src/platform/macos/launchd.ts:61-67`), so launchd starts the daemon again after any non-zero exit, at most once in 300 seconds, and the start takes the start path above. A daemon started by hand, or by the wrapper `install.sh` writes, has no `KeepAlive` and stays stopped. A failed watch is never handed over to node.

## Where the binary is looked for

| who | looks at, in this order |
|-----|-------------------------|
| `tagents` (for a verb it does not know) | `tagents-core` on `PATH`, then `target/release/tagents-core` beside the script when it is executable, then the built `packages/core/dist/cli/main.js` |
| the `tagents-core` wrapper from `install.sh` | `$TAGENTS_HOME/target/release/tagents-core` while it is executable, then the node CLI |

`install.sh` names the Rust binary in the wrapper only if the binary is executable when the installer runs. With none, the wrapper is byte for byte what the installer wrote before a Rust binary existed. A binary that is there and cannot run is an error that is reported, not a reason to fall back silently; a binary that has been removed is not an error, and the wrapper runs the node CLI. A directory at the binary's path is not a binary either.

A binary built by hand goes stale. `target/` is ignored by git and nothing rebuilds it, so after `tagents update` or a `git pull` an older `cargo build --release` keeps answering `sessions` until the next `cargo build --release`. For `tagents-mcp` the installer asks a hand-built binary `--version` once per install (`install.sh:295`) and names it only when it answers `tagents-core <version of the checkout>`; otherwise `tagents-mcp` runs the node server, while `tagents-core` still names the binary, because every verb it lacks goes to the node CLI. A checkout with no `Cargo.toml` keeps naming the binary; a `Cargo.toml` whose version cannot be read (a pre-release such as `0.2.0-rc.1`, an unreadable file) names none. Rebuild after every update. The prebuilt binary cannot go stale that way: on every run the installer compares its marker with the version of the checkout ("How the installer fetches it").

## How a release is made

**The version is the identity of the binary.** `version` in `[workspace.package]` of `Cargo.toml` is the only place it is written, `tagents-core --version` prints it, and a release is the tag `v<version>`. A binary of version V must come from the source of version V, so the version has to move whenever the source does.

**A pull request cannot forget to move it.** The `release-path` job of `.github/workflows/rust.yml` runs `.github/scripts/core-release.sh gate origin/<base>` on every pull request: when the diff against the merge base changes an input of the binary and the workspace version is not higher than the one at the merge base (the same, or lower: the three numbers are compared one by one, as numbers), the job fails, names the files and says whether the version stayed or went down. The inputs are `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `crates/*/Cargo.toml`, `crates/*/build.rs`, `crates/*/src/*` and `spec/cli/*` (the CLI spec is compiled into the binary by `include_str!`, and the schema beside it counts too, because the rule is a prefix). Tests under `crates/*/tests/`, docs, workflows and the node side are not inputs. A rename out of an input path counts as a change to it.

**A tag makes the release.** Pushing `v<version>` on a commit of `main` starts `.github/workflows/release.yml`:

1. `verify` (read-only token, whole history): the tag is `v` plus the workspace version of that commit, the commit is an ancestor of `origin/main`, and no release of that tag exists yet. A release is never overwritten; a wrong one is superseded by a new version.
2. `build`, on three targets: `aarch64-apple-darwin` and `x86_64-apple-darwin` (cross-built on the arm64 macOS runner) and `x86_64-unknown-linux-musl`. Each runs `cargo build --locked --release --target <triple> --package tagents-core`, packages with `core-release.sh package`, and on the two targets the runner can run unpacks the archive elsewhere and checks `--version` and `--spec`.
3. `publish` (the only job with `contents: write`, and it checks out nothing): `gh release create` with exactly six files.

| file | content |
|------|---------|
| `tagents-core-<version>-<triple>.tar.gz` | exactly two members: `tagents-core` (mode 755) and `LICENSE` |
| `tagents-core-<version>-<triple>.tar.gz.sha256` | one line, `<64 lowercase hex>  <archive name>`, readable by `sha256sum -c` and `shasum -a 256 -c` |

A pull request that changes the workflow, the scripts or an input of the binary (the paths above, which `tests/release.sh` pins to the `pull_request.paths` of `release.yml`) runs the three builds as a dry run and publishes nothing, so a musl link failure or a failed cross-build shows on the pull request and not when the tag is pushed. The `build` job checks out the commit the `verify` job checked, not the tag by name, so a tag moved between the two jobs is not built unverified. A run that failed halfway is redone from the Actions tab with the tag as input (`workflow_dispatch`).

```sh
git switch main && git pull --ff-only          # the commit that holds the bump
sh .github/scripts/core-release.sh version     # 0.5.0
git tag v0.5.0 && git push origin v0.5.0       # starts the release workflow
```

**When `main` is ahead of the last release,** a managed copy that follows `main` holds a version with no release yet. Its installer finds nothing to download, says so, and the node CLI runs until the tag of that version is pushed; it never keeps the binary of an older version in the meantime. Nothing releases on a push to `main`: the person who merges the bump pushes the tag.

## How the installer fetches it

`install.sh` runs `fetch_native` after the build and before it writes the wrappers, never with `--check`. The rules, in the order the function applies them:

| rule | behaviour |
|------|-----------|
| nothing to do | no `$TAGENTS_HOME/Cargo.toml`, or `TAGENTS_NO_NATIVE=1` (which also removes a binary that has a marker), ends the function silently |
| what is wanted | the workspace version of `$TAGENTS_HOME/Cargo.toml`, read by `core_version` in `install.sh`, a second copy of `core-release.sh version` that `tests/release.sh` runs against it over the same `Cargo.toml` shapes |
| whose binary it is | `target/release/tagents-core.release` holds `<version> <target> <sha256 of the binary>` on one line. A binary with no marker was built by hand: it is not replaced, deleted or shadowed by a download |
| nothing changed | the binary is executable and the marker names the wanted version, this target and the hash of the binary: the function ends, and no request is made |
| any other state | a marked binary of another version, target or hash, or a marker without a binary, is deleted before anything is fetched, so a failed fetch leaves the node CLI in use and never a binary of another version |
| this machine | `x86_64-unknown-linux-musl`, `x86_64-apple-darwin` or `aarch64-apple-darwin` from `uname`, where an x86_64 process under Rosetta counts as arm64 (`sysctl -n sysctl.proc_translated` is 1). `TAGENTS_CORE_TARGET` replaces the guess |
| where | `https://github.com/SkuratovichA/tagents/releases/download/v<version>/`; `TAGENTS_CORE_BASE_URL` replaces it (a directory URL that starts with `https://` or `file://`; when a fetch is due and `curl` is there, any other scheme is refused with a warning, no request is made and the run ends with status 1) and is announced in one line. `curl` only, with a bounded wait; an `https://` URL is HTTPS only, TLS 1.2 or newer, two retries, and a `file://` URL is held to files. No `gh`, no login |
| downloaded to | a directory made under `target/` of the copy and removed when the run ends, not under `TMPDIR`: the downloaded binary is run once there for its `--version`, and `TMPDIR` may be mounted `noexec` |
| no release, no network, no `curl`, no `sha256sum` or `shasum`, an unsupported machine | one line on the way to the node CLI, and the run still exits 0 |
| a download that fails a check | `warn`, nothing installed, the wrappers are written, and the run ends with status 1. The checks, in order: the first field of the `.sha256` file is 64 lowercase hex and equals the archive's SHA-256; the archive lists exactly `tagents-core` and `LICENSE`; the extracted `tagents-core` is a regular file and `--version` prints exactly `tagents-core <version>` |
| installing | the marker first, then the binary, each written to a temporary name and renamed, so an interrupted run leaves a marker that does not match, which the next run removes |

The checksum is published beside the archive, so it proves the transfer and that the archive is the one that was packaged, and it does not prove who published it: whoever can write the release can write both files, and the binary is not signed. Trust rests on HTTPS to GitHub and on who may create releases of the repository.

## The parity suite

`tests/rust-parity.sh` builds a seeded home (`tests/rust-parity-seed.mts`: the two sessions of `packages/core/test/fixtures/sessions/` and several hundred more made so that JavaScript and a naive port disagree), runs `node packages/core/dist/cli/main.js` and the Rust binary on it under the same environment, and passes a case only when stdout, stderr and the exit code are identical. Besides these node-against-Rust cases the suite packages the debug binary with `core-release.sh package`, serves it as a `file://` release in a sandbox and checks that the installer accepts its `--version` line.

```sh
pnpm install && pnpm build
env -u TMUX -u TMUX_PANE TMUX_TMPDIR="$(mktemp -d)" bash tests/rust-parity.sh
```

It needs `python3` (the seed sets exact modification times, including ones before 1970) and builds the debug binary when it is missing and `TAGENTS_CORE_BIN` does not name one; after a Rust edit or a version bump run `cargo build` first, because the suite does not rebuild a binary that exists, and a binary whose version is not the workspace version fails the installer case with a warning that says `for --version`. `cargo test` holds a second, node-free check: the five fixture files, `packages/core/test/fixtures/sessions/*.txt`, which the Rust output must reproduce byte for byte.

Where node's behaviour is an accident of its runtime, the port repeats it, because agents read this text out of a shell: lengths are counted in UTF-16 units, white space is ECMAScript's, a modification time rounds with `Math.round`, names come in the order libuv lists them, and a transcript line is parsed by `json.rs`, a parser that follows `JSON.parse`. What the repository pins is the awkward lines of the seed (`tests/rust-parity-seed.mts`) and the unit tests of `json.rs`; a differential fuzz against `JSON.parse` was run during development and is not kept.

`tests/rust-mcp-parity.sh` does the same for the server. It feeds one script of requests to `node packages/mcp/dist/main.js --contract F` and to `target/debug/tagents-core mcp --contract F` (or `$TAGENTS_CORE_BIN`) under `env -i`, with stub programs on `PATH` and a scratch home, so no real tagents program runs, and passes a scenario only when the two transcripts are the same bytes once `serverInfo.version` is dropped. A transcript is every answer keyed by request id, the order the answers came in, how the server ended and which processes of the call were still alive after it; the typed client that writes it is `tests/rust-mcp-parity-driver.mts`. The scenarios are `initialize` with every protocol version the SDK lists and one it does not, `tools/list` on a fixture that has every feature of a spec, on an empty contract and on the bundled `contract.json`, the command line of every path of `argvFor` and about twenty refusals, every exit code, JSON and text output (white space before the document, numbers, key order, deep nesting), output cut at the cap, across a character and on both streams, a missing program, `requires: tmux`, cancellation, two calls in flight, the end of stdin and each signal with a call running, and a program that leaves a child holding its pipes. Tripwires assert on the node transcript alone, so a scenario that stops provoking what it exists for fails and does not pass for nothing. Timeouts and the grace are not in the suite, because both come from constants; `crates/tagents-core/tests/mcp_run.rs` takes them as arguments.

```sh
pnpm install && pnpm build
env -u TMUX -u TMUX_PANE TMUX_TMPDIR="$(mktemp -d)" bash tests/rust-mcp-parity.sh
PARITY_ONLY="JSON numbers" PARITY_SHOW=300 bash tests/rust-mcp-parity.sh    # the scenarios whose label holds the text, with both transcripts cut at 300 characters a line
```

It needs a built node server and node 22.18 or newer (the driver is TypeScript run as it is), builds the debug binary when it is missing, and uses no real home, no tmux server and no network. `tests/rust-parity.sh` never runs `mcp`. `cargo test` carries the node server's own tests, ported: every case of `packages/mcp/test/*.test.ts` has a Rust test in `mcp/*.rs` or `crates/tagents-core/tests/mcp_{run,server,pins}.rs`, except the one named in the last item of the list below.

## Where the two are known to differ

These are the differences the port does not hide, and the suite does not cover them:

- `tagents-core --spec` prints the spec as JSON on the Rust binary and is a usage error on the node CLI, so which program the wrapper picks changes what that call does.
- `tagents-core --version`, as the only argument, prints `tagents-core <workspace version>` and exits 0 on the Rust binary; the node CLI has no such flag and reports a usage error. It is the one identity check the installer makes of a downloaded binary, so it is not in `spec/cli/tagents-core.json`, which would move the plugin contract. With more words after it the flag is the node CLI's.
- A search word that holds U+FFFD can match a lone surrogate escape (`"\ud800"`) in a transcript, because Rust reads the escape as U+FFFD where a JavaScript string keeps the lone half.
- Lower casing uses the Unicode data of the Rust standard library, where node uses ICU's. Both gave the same result for every scalar value on node 22, and a newer node that knows a newer Unicode version can differ first.
- An I/O error is worded as node words it for `ENOENT`, `EIO`, `EACCES`, `ENOTDIR`, `EISDIR` and `EMFILE`; any other error number prints Rust's description.
- A directory entry whose name is not UTF-8 is not listed. Node lists it with U+FFFD in the name, and the next `stat` on that name fails there.
- A modification time that `Date` cannot represent, and a `HOME` that is unset (the suite always sets it, empty at times), are not covered.

The MCP server differs from `packages/mcp` in these ways. The suite leaves them out, or pins the Rust side alone:

- A second signal during the ending: node dies by a repeat of the same signal (`process.once` in `packages/mcp/src/main.ts:18-33`), so a program that ignores SIGTERM outlives the call with no SIGKILL; the Rust server ignores the second signal and finishes the ending.
- A request whose `params` do not have the shape the method needs is -32602 `Invalid params: <reason>` on the Rust server; node answers -32603 with the text of its schema library. `initialize` checks fewer fields than the SDK's schema (only that `capabilities` is an object and `clientInfo` has string `name` and `version`), so a body such as `"capabilities":{"roots":5}` is answered where node refuses it.
- The calls an ending stopped (stdin closed, a signal) are always answered `cancelled` by the Rust server. Node races `process.exit` against writing those answers, so which of them arrive changes from run to run; the suite drops them from the comparison and pins the Rust ones (`rust_answers`).
- A lone surrogate escape in a *request* is read as U+FFFD, which is what node's spawn passes to the program, so the calls match (the parity scenario "a request with lone surrogate escapes" proves it). Where a server writes a request string back (the name in `unknown tool <name>`, the `id` of a request), Rust writes U+FFFD and node writes the escape. A request nested deeper than 128 levels is ignored by Rust (`serde_json`'s limit) where node answers it.
- Program JSON that `serde_json` does not read stays text where node parses it: a lone surrogate escape (`"\ud800"`) in a program's output and a document nested deeper than 128 levels. The keys of an object that are integers are not moved to the front, as JavaScript moves them.
- A call argument named like a member of `Object.prototype` (`constructor`, `toString`) is refused as unknown, where node lets it through and ignores it.
- A program that cannot be started for a reason other than a missing file reports the operating system's text as Rust words it, not as Node does, and the child leads a process group of its own, not a session, and stays that way: `Command::setsid` is unstable in rustc 1.99.1 (rust-lang/rust#105376, error E0658) and `pre_exec` needs `unsafe`, which the crate forbids. When the server has a controlling terminal, the call keeps it: a program that opens `/dev/tty` and reads is stopped by SIGTTIN (a write by SIGTTOU when the terminal has `tostop`), where node's child, a session leader without a terminal, fails at once with ENXIO. The call still ends, because cancellation and the 5-minute limit send SIGTERM to the group and SIGKILL after the 2 s grace, and no verb of the contract opens the terminal (`plugin add` records configuration and spawns no git).
- A `notifications/cancelled` that arrives in the same read as its request: node never starts the program, the Rust server may start it and stop it at once.
- A pipe that a process outside the group holds open costs one blocked reader thread until it lets go; node destroys the stream.
- A process outside the group that keeps writing to a pipe holds a Rust call for up to the drain plus the grace after the program exited (2.25 s by default), because a pipe with bytes in it is read on past the drain; node destroys the streams at the end of the drain. A holder that writes nothing is given up on at the drain in both (`a_holder_outside_the_group_that_keeps_writing_does_not_hold_the_call_and_gets_epipe_after_it` in `crates/tagents-core/tests/mcp_run.rs` pins that the call ends and the holder gets EPIPE, not the bound); a call that was stopped is given up on at the drain even then (`a_call_that_was_stopped_is_given_up_on_at_the_drain_even_when_a_holder_keeps_writing`).
- A call that was stopped (timeout, cancellation, the server ending) is given up on at the drain after its program exited, whether or not a helper holds the pipes, so a reader thread that is descheduled for longer than the drain on a loaded machine can cost it output that node would have read; node's one thread reads the pipes in its poll phase whatever stopped the call, and ours gives a stopped call only the drain so that a second grace cannot overrun the server's ending, which waits `KILL_GRACE` plus `SHUTDOWN_MARGIN` (`server.rs`).
- A reader thread that has read a chunk and is descheduled before it stores it, while a holder outside the group keeps the emptied pipe open past the drain, loses that chunk, because the call sees an empty open pipe and gives up; node's one thread cannot be descheduled between reading and storing. Without such a holder the pipe polls as hung up and the call waits for the reader.
- A server started with SIGCHLD ignored gets ECHILD from `waitid` (`child.rs:195-206`) and reports a program that exited 0 as having no exit code; Claude Code starts its servers through libuv, which resets every signal disposition to the default in the child before exec.
- The usage line and the start-up failures say `tagents-core mcp` and not `tagents-mcp`, and a missing or invalid contract file is worded in Rust's words; the suite compares their exit codes only.
- The node CLI does not know `mcp`, and its list of reserved words (`reserved: session · sessions · plugin · config · doctor · help`, pinned by `packages/core/test/plugin-commands.test.ts`) is unchanged, so it still lets a plugin name a verb `mcp`; behind the front door that word is always the server's.
- `parseCliContract` has no Rust counterpart. The node server never calls it (only the generator in `packages/contract` does), so the one test of `contract-file.test.ts` that reads a spec with a program name of its own through it is not ported.

## Rules for the Rust code

- `unsafe` is forbidden, and `unwrap` and `expect` are denied outside tests, for the whole workspace (`Cargo.toml`, `crates/clippy.toml`).
- No async runtime, and no parser in the tree but `serde_json` and `toml`: the notify daemon's options file is TOML and the daemon has to read it. Every dependency is a row of the table below with its reason and its cost, and a new one is a new row.

| dependency | used by | reason | cost |
|------------|---------|--------|------|
| `serde` (derive) | `tagents-spec` | reads the data file into a typed model that refuses unknown fields | `serde_derive`, `syn`, `quote`, `proc-macro2`, `unicode-ident`, `serde_core` at build time |
| `serde_json` | `tagents-spec`, `tagents-core` | parses the data file, prints `--spec`, speaks JSON-RPC and reads the contract | `itoa`, `memchr`, `zmij`; its parser is not used for transcripts (`json.rs`) |
| `serde_json` features `preserve_order`, `arbitrary_precision` | `mcp` | a program's JSON keeps the order of its keys and the digits of its numbers, and the contract's maps keep the file's order | `indexmap`, `equivalent`, `foldhash`, `hashbrown`; the features are additive, so they apply to every crate of the workspace |
| `rustix` (features `process`, `event`) | `child` | signal a process group, wait for a child without reaping it and ask a pipe whether it is readable, in safe code (`unsafe_code = "forbid"` stays) | `bitflags`, `errno`, `libc` |
| `rustix` features `fs`, `pipe` | `watch` | inotify on Linux, opening a path with `O_NOFOLLOW` and the descriptor flags on macOS, and the wake pipe of the watch thread, in safe code | none: the crate is in the tree |
| `rustix` feature `system` | `notify::service` | `uname`, whose node name is the host name a notice carries (`os.hostname()` in node), read afresh for each notice because macOS renames the host with the network (`crates/tagents-core/src/notify/service.rs:431`) | none: the crate is in the tree |
| `kqueue` 1.2.1 (target `cfg(target_os = "macos")` only) | `watch::macos` | a safe binding of kqueue, because `rustix` declares `kevent` unsafe and the workspace forbids `unsafe` | `kqueue-sys` |
| `signal-hook` | `ending` | end on SIGTERM, SIGINT or SIGHUP from a thread, in safe code | `signal-hook-registry` |
| `toml` 1.1.8 (`default-features = false`, features `std`, `parse`, `preserve_order`) | `notify::options` | the options file `<configDir>/plugins/notify.toml` is TOML and the daemon has to read it. The reader uses the parse tree `toml::de::DeTable`, which keeps each integer and float as the text the file wrote, so the code decides what node's parser would have made of it (an integer beyond 2^53 is refused as node's is); the lines that report a bad file are checked by hand against node's schema, because serde's texts would be other words in another order | `toml_parser`, `toml_datetime`, `serde_spanned`, `winnow`; `indexmap` is in the tree already for `serde_json`. `Cargo.lock` also lists `toml_writer`, which these features do not build (`cargo tree --workspace --target all -e all -i toml_writer` prints nothing) |

The three rows of the server add 10 crates (23 names in the build of `tagents-core` instead of 13, 21 of them external instead of 11), raise the release binary (`lto`, one codegen unit, `strip`) from 518,992 to 819,312 bytes, 300,320 of them, and a clean `cargo build --release -p tagents-core` from 8.8 s to 12.5 s on an Apple silicon laptop. The bytes include the server's own code, and the dependencies cannot be measured apart from it, because the server does not build without them. `rustix` has what `mcp::run` calls, `waitid` with `NOWAIT`, `kill_process_group` and `poll`, on the three targets of the release, `aarch64-apple-darwin`, `x86_64-apple-darwin` and `x86_64-unknown-linux-musl` (`rustix` 1.1.6, the `cfg` of `src/process/wait.rs`, `src/process/kill.rs` and `src/event/mod.rs`); the dry run of `release.yml` on a pull request builds all three, and if one of them ever fails, `nix` is the substitute. Against it the server saves memory and start-up time: an idle `tagents-core mcp` has a footprint (`footprint <pid>`) of 1.6 MB and the node server 38 MB, and the time from spawn to the answer of `initialize` is 3.2 ms against 99.7 ms (median of ten runs each).

The watch adds `kqueue` and `kqueue-sys` to the macOS build and nothing to the Linux build, where it is `rustix` features only (`cargo tree -p tagents-core --prefix none -e normal` lists 28 packages before and 30 after on the macOS host, and 28 before and after with `--target x86_64-unknown-linux-musl`). `libc` and `bitflags`, which `kqueue-sys` needs, were in the tree already. The release binary is 819,312 bytes before and after, and a clean `cargo build --release --locked -p tagents-core` takes 10.2 s before and 10.8 s after on an Apple silicon laptop under a load of about 2.6. The binary does not grow because the linker drops a module that nothing calls, so these figures are the cost of the dependencies and the build, and the bytes of the watch itself show only once code calls it. `kqueue` and `kqueue-sys` are MIT licensed. The release of the three targets builds `kqueue` only for the two macOS ones.
- `cargo fmt --all --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings` and `cargo test --workspace --locked` run in CI (`.github/workflows/rust.yml`) after `pnpm install`, because the smoke test of the MCP server calls the node CLI from its sources (it skips that half where `node_modules` is missing), together with the parity suite, the version gate, and the shell suites `tests/release.sh` and `tests/install.sh`.

## What is not decided yet

How plugins (JavaScript) are hosted once more of the CLI is Rust, and which verbs move next, are open. The change that introduced the front door, `openspec/changes/archive/2026-10-31-rust-core/`, lays out the slices and the three options for the plugin host. Signing or notarising the archives is not done (see the last paragraph of "How the installer fetches it"), and a Windows build does not exist.
