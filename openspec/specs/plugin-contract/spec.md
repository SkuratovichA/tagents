# plugin-contract Specification

## Purpose
The Claude Code plugin ships a contract of tagents (its CLI verbs and flags, MCP tool schemas, public TypeScript API and script help) that is generated from the code, never written by hand. This capability covers the generator, its stale check, the version the plugin carries and the pre-commit hook that keeps the contract in step with every commit.

## Requirements

### Requirement: The contract is generated from the code
`pnpm plugin:gen` (`node packages/contract/src/main.ts`) SHALL rewrite the generated files from the code in the working tree: `contract.json` at the repository root and, under `skills/tagents/references/`, `cli.md`, `mcp.md`, `scripts.md` and one `<package>.api.md` per public package. A hand edit is overwritten. `cli.md`, `mcp.md` and `scripts.md` SHALL say they are generated by `pnpm plugin:gen`; each `<package>.api.md` carries API Extractor's note that it is a generated report.

#### Scenario: Regenerating
- **WHEN** `pnpm plugin:gen` runs after a verb, a flag, an MCP tool or an exported signature changed
- **THEN** the files that differ are rewritten, one `wrote <path>` line is printed for each, and the exit code is 0

#### Scenario: Nothing changed
- **WHEN** the generated files already match the code
- **THEN** the output is `the plugin contract is up to date; nothing written` and no file is touched

### Requirement: What generation covers
The generator SHALL read four things from the code: the verbs, flags, exit codes, effects and requirements of the CLI specs (`tagents-core`, `tagents-knowledge`, `tagents-notify`, `tagents.cli.json`); the tools of the knowledge MCP server as a client lists them and the tools of the `tagents` server derived from the CLI specs; the public TypeScript API of every public package (not private, with `exports`); and the `--help` text of the `tagents`, `tusage` and `tnotes` scripts.

#### Scenario: Where the CLI and MCP parts come from
- **WHEN** the CLI contracts and MCP tools are collected
- **THEN** the `tagents-core` CLI is read from `spec/cli/tagents-core.json`, the other CLIs from the command specs they parse with (and, for the script, from `tagents.cli.json`), the knowledge tools from the server's tool list without opening a database, and the `tagents` tools from the CLI contracts

#### Scenario: Reading the sources, not a build
- **WHEN** a package's built output is older than its sources
- **THEN** the generated contract still follows the sources

#### Scenario: Script help is machine independent
- **WHEN** the scripts' help is collected
- **THEN** each script runs with `--help` under a throwaway home and only the caller's `PATH`, so the text does not depend on the machine

#### Scenario: The API of every public package
- **WHEN** the API reports are produced
- **THEN** there is one per public package, named `<package>.api.md` after the package name without its scope, in the order of the package names

### Requirement: The output is deterministic and English
The generated files SHALL be identical whatever the working directory, the locale (`TAGENTS_LOCALE`) or the number of parallel runs, with LF newlines, a fixed order and one newline at the end of each markdown file. Headings and labels in the references SHALL always be English; text taken from the code is reproduced as it is, and a script's help verbatim, even when it contains a code fence.

#### Scenario: Another locale
- **WHEN** the generator runs with a non-English `TAGENTS_LOCALE`
- **THEN** the files written to the repository are the same English text

#### Scenario: Two runs at once
- **WHEN** two generator runs overlap
- **THEN** each produces what a single run produces

### Requirement: Stray references are removed
Any file under `skills/tagents/references/` that the generator did not produce SHALL be deleted by `pnpm plugin:gen` (each reported as `deleted <path>`) and named stale by the check. Files elsewhere under `skills/`, such as `SKILL.md`, SHALL never be deleted. A file the operating system drops into a folder (`.DS_Store`) is not part of the tree.

#### Scenario: A stray reference
- **WHEN** `skills/tagents/references/old.md` exists
- **THEN** generation deletes it and the check names it stale

#### Scenario: Other skill files
- **WHEN** `skills/tagents/SKILL.md` is edited
- **THEN** it is kept, and the edit counts as a change of what the plugin ships

### Requirement: plugin:check fails when the tree is stale
`pnpm plugin:check` (`node packages/contract/src/main.ts --check`) SHALL write nothing. When every generated file, every stray file and the plugin version and digest are as generation would leave them, it SHALL print `the plugin contract is up to date` and exit 0. Otherwise it SHALL print one `stale: <path>` line for each path generation would write or delete, then `run pnpm plugin:gen to bring them up to date`, and exit 1.

#### Scenario: Fresh
- **WHEN** the committed files are what the code generates
- **THEN** the check exits 0

#### Scenario: Stale
- **WHEN** a flag was added to a verb and nothing was regenerated
- **THEN** the check exits 1 and names `contract.json`, `skills/tagents/references/cli.md` and `.claude-plugin/plugin.json` among the stale paths

### Requirement: The test suite fails on a stale contract
`pnpm test` SHALL fail when the generated files on disk, or the plugin's version and digest, are not what the code generates, so a change to a verb, flag, tool, signature, script help or the skill that forgets `pnpm plugin:gen` cannot pass.

#### Scenario: Forgotten regeneration
- **WHEN** a command spec changes and the contract is not regenerated
- **THEN** the contract package's freshness test fails

### Requirement: Generator usage and failures
The generator SHALL accept `--check` and nothing else: any other option prints `usage: node packages/contract/src/main.ts [--check]` on stderr and exits 2. Any failure while collecting sources or writing SHALL print its message on stderr and exit 1.

#### Scenario: A stray option
- **WHEN** the generator is run with `--nope`
- **THEN** the usage line is printed on stderr and the exit code is 2

#### Scenario: A script whose help cannot be read
- **WHEN** one of the scripts fails to print its help
- **THEN** the message names that script and the exit code is 1

### Requirement: The plugin version follows what the plugin ships
`.claude-plugin/plugin.json` SHALL carry a `version` and a `metadata.digest`, both maintained by the generator. The digest SHALL be a `sha256:` hash over the paths and contents of the payload: the generated files, every file under `skills/` outside `references/`, `.claude-plugin/marketplace.json` when present, and `plugin.json` without its `version` and `digest`. The version SHALL move only when the digest moved.

#### Scenario: The first run
- **WHEN** `plugin.json` has no stored digest
- **THEN** the digest is stored, the version stays as it was and the output says the first digest was stored

#### Scenario: Nothing changed
- **WHEN** the stored digest equals the new one
- **THEN** `plugin.json` is not rewritten, even if its formatting differs

#### Scenario: Only the version and digest differ
- **WHEN** nothing but `version` and `metadata.digest` of `plugin.json` changed
- **THEN** the digest does not move

### Requirement: Minor and patch moves
When the digest moved, the version SHALL go up by a minor step (`X.Y.Z` to `X.(Y+1).0`) if the structure of the contract changed, and by a patch step (`X.Y.(Z+1)`) otherwise. The structure is the new `contract.json` with every `summary` and `description` string removed at any depth, compared with the one on disk; a missing or unparseable file on disk is structural. The output says `plugin version <from> to <to>` and whether the move was minor or patch.

#### Scenario: What is structural
- **WHEN** a verb, flag, tool, input schema or API report hash is added, removed or changed
- **THEN** the move is minor

#### Scenario: What is not
- **WHEN** only wording, skill text, a manifest, a script's help or the order of an object's keys changes
- **THEN** the move is a patch or none

#### Scenario: A flag is added
- **WHEN** a verb gains a flag
- **THEN** the version goes from `0.1.4` to `0.2.0`

#### Scenario: A description is reworded
- **WHEN** only a tool description or a verb summary changes
- **THEN** the version goes from `0.1.4` to `0.1.5`

#### Scenario: A property that is called description
- **WHEN** a tool has an input property named `description`
- **THEN** it is part of the structure, and adding or removing it is a minor move

#### Scenario: The exported API changes
- **WHEN** an API report's hash changes
- **THEN** the version takes a minor step

### Requirement: plugin.json is edited, not rewritten
Generation SHALL change only the `version` and `metadata.digest` of `.claude-plugin/plugin.json`: every other key keeps its order and value, and `metadata` is appended at the end when absent. The file is two-space JSON with a trailing newline. A missing `plugin.json`, one that is not a JSON object, or one whose `version` is not a string SHALL stop generation with an error naming the problem and exit 1.

#### Scenario: Other keys stay
- **WHEN** the digest changes
- **THEN** `name`, `description`, `mcpServers` and the other keys are where they were

#### Scenario: Other keys of metadata
- **WHEN** `metadata` already holds other keys
- **THEN** they stay in place and only `digest` changes

#### Scenario: A version that cannot be bumped
- **WHEN** `plugin.json` has the version `1.0` and the digest moved
- **THEN** generation fails saying the version is not major.minor.patch

### Requirement: The pre-commit hook regenerates the contract
`.githooks/pre-commit` SHALL, when a commit stages a change (including a deletion) to a source of the contract, run the generator and add `contract.json`, `.claude-plugin/plugin.json` and `skills/tagents/references/*.md` to that same commit. Any other commit passes untouched.

#### Scenario: A source changed
- **WHEN** a commit stages a change under `packages/core/src/`
- **THEN** the regenerated contract files are in the same commit

#### Scenario: The script's spec changed
- **WHEN** a commit stages a change to `tagents.cli.json`
- **THEN** the regenerated contract files are in the same commit

#### Scenario: A skill file changed
- **WHEN** a commit stages a change under `skills/`
- **THEN** the regenerated contract files are in the same commit

#### Scenario: A partially staged file
- **WHEN** a source file is only partly staged
- **THEN** the generator still reads all of it from the working tree

#### Scenario: Unrelated commit
- **WHEN** a commit stages only a README
- **THEN** the hook does nothing

### Requirement: The hook refuses a commit it cannot regenerate for
When the generator fails, the hook SHALL say the contract could not be regenerated and nothing was committed, hint at `pnpm -r build` for a missing export of a workspace package, and exit 1. When `packages/contract` has no `node_modules`, the hook SHALL say the contract was not regenerated, tell the committer to run `pnpm install` and then the generator, and let the commit proceed (exit 0); the stale check in `pnpm test` then catches it.

#### Scenario: Generation fails
- **WHEN** the generator exits non-zero during a commit
- **THEN** the commit is refused

#### Scenario: Dependencies are not installed
- **WHEN** `packages/contract/node_modules` does not exist
- **THEN** the commit goes through with a message that the contract was not regenerated

### Requirement: The hook is switched on by install
The root `prepare` script, run by `pnpm install`, SHALL set `core.hooksPath` to `.githooks` in a git clone that has no `core.hooksPath` of its own, and SHALL change nothing in a clone that already has one or is not a git repository.

#### Scenario: A fresh clone
- **WHEN** `pnpm install` runs in a clone with no hooks path configured
- **THEN** `core.hooksPath` becomes `.githooks`

#### Scenario: A clone with its own hooks path
- **WHEN** `core.hooksPath` is already set
- **THEN** it is left as it is

### Requirement: A verb declares what it does
A command in a structured CLI spec MAY declare an `effect`: `read` (changes nothing), `write` (changes files, settings or the screen), `spawn` (starts a program or window that goes on by itself), `destructive` (removes or stops something that cannot be got back) or `serve` (runs until stopped, so answers no request); and MAY declare `requires: tmux`. The generator SHALL record both on the verb in `contract.json`, and the annotations the effect stands for on its tool.

#### Scenario: Recorded
- **WHEN** a verb declares `effect: destructive`
- **THEN** `contract.json` holds `"effect": "destructive"` on the verb and `destructiveHint: true` on its tool

#### Scenario: A verb that serves
- **WHEN** a verb declares `effect: serve`
- **THEN** it is in `contract.json` and in the references, and has no tool

### Requirement: A verb may be left out of the tools
A command in a structured CLI spec MAY declare `tool: false`, meaning that it is not offered as a tool. The generator SHALL record it on the verb in the `cli` section of `contract.json`, list no tool for the verb, and keep the verb in the contract and in the references, so the CLI is still documented.

#### Scenario: A verb opts out
- **WHEN** a verb declares `tool: false`
- **THEN** `contract.json` holds `"tool": false` on the verb in its `cli` section, `mcp.tagents.tools` has no tool for it, and `references/cli.md` still describes it

### Requirement: A verb may default an option for its tool
A command MAY declare `toolDefaults`, a map from the name of one of its boolean options to the value a tool call uses when the caller leaves the option out. The generator SHALL record it on the verb and give the tool's property that default, and SHALL stop, naming the tool and the option, when the map names an option the verb does not have or one that is not boolean.

#### Scenario: A default for a tool
- **WHEN** `tagents --window` declares `toolDefaults: { detach: true }`
- **THEN** `contract.json` holds the default on the verb and the tool `tagents_window` has a `detach` property whose default is true

#### Scenario: A default for an option that is not there
- **WHEN** a verb declares `toolDefaults: { attach: true }` and has no `--attach` option
- **THEN** generation stops with an error naming the tool and `--attach`

#### Scenario: A default for an option that is not a flag
- **WHEN** a verb declares a default for an option that takes a string
- **THEN** generation stops with an error saying the option takes a string

### Requirement: The tools of the tagents server come from the CLI specs
`contract.json` SHALL list under `mcp.tagents.tools` one tool for each verb of each structured CLI spec that is not `serve` and not `tool: false`, ordered by tool name. A tool SHALL be derived from its verb alone, so the generator holds no list of tools.

#### Scenario: A verb is added to a spec
- **WHEN** a command is added to a spec and `pnpm plugin:gen` runs
- **THEN** `contract.json` lists a new tool for it, the digest is different, the plugin version takes a minor step, and no file that is not generated and not the spec was edited

#### Scenario: A summary is reworded
- **WHEN** only the summary of a verb changes
- **THEN** the tool's description changes and the plugin version takes a patch step

#### Scenario: An effect changes
- **WHEN** a verb's effect changes from `read` to `write`
- **THEN** the plugin version takes a minor step

### Requirement: The structured CLI specs
The structured CLI specs are those of `tagents-core`, `tagents-knowledge` and `tagents-notify`, which the packages parse their arguments with, and `tagents.cli.json` at the repository root, which describes the non-interactive flags of the `tagents` script. A spec file that cannot be read or parsed SHALL stop generation, saying which file and why, and exit 1.

#### Scenario: A spec file that is not JSON
- **WHEN** `tagents.cli.json` is not valid JSON
- **THEN** the generator prints `cannot read the CLI spec tagents.cli.json` and the reason on stderr and exits 1

### Requirement: The script's spec is pinned to its help
Every flag that `tagents.cli.json` describes SHALL appear in the script's `--help` with the same positionals, and every flag of the help SHALL be either in `tagents.cli.json` or in the test's list of flags that are not tools, each with its reason; otherwise the contract package's tests fail. The flags that start something SHALL declare `requires: tmux`.

#### Scenario: A flag is renamed in the help
- **WHEN** the help names `--window` as `--open` and the spec is unchanged
- **THEN** the pin test fails naming `--window`

#### Scenario: A positional changes
- **WHEN** `--new` takes a third positional in the help and the spec is unchanged
- **THEN** the pin test fails naming `--new`

### Requirement: Verbs without an effect are reported, not refused
`pnpm plugin:gen` and `pnpm plugin:check` SHALL print one `notice:` line naming every verb (as `<program> <verb>`) that declares no effect, saying that each is offered as a tool that is not read-only. The notice SHALL NOT change the exit code and SHALL NOT mark the tree stale.

#### Scenario: A verb added by another change
- **WHEN** a command without an `effect` is added to a spec and `pnpm plugin:check` runs on a regenerated tree
- **THEN** the output holds a `notice:` line naming it, the exit code is 0, and its tool is not read-only

#### Scenario: Everything declared
- **WHEN** every verb declares an effect
- **THEN** no notice is printed

### Requirement: The contract file holds what generation read
`contract.json` SHALL hold the CLI contracts, the MCP tools of both servers, with their input (and output) schemas, and a hash of each API report.

#### Scenario: Both servers are in the file
- **WHEN** the contract is generated
- **THEN** `contract.json` lists the tools of the knowledge server and of the `tagents` server, and one API report hash per public package

### Requirement: What counts as a source of the contract
A file SHALL be a source of the contract when it is under `packages/<package>/src/`, a package's `package.json` or `tsconfig*.json`, `pnpm-lock.yaml`, `tagents`, `tagents.cli.json`, `tusage`, `tnotes`, anything under `spec/cli/`, `skills/` or `.claude-plugin/`, or `contract.json`.

#### Scenario: A file the contract is generated from
- **WHEN** a file is `tagents.cli.json`, the spec of the `tagents` script that its contract is generated from
- **THEN** it is a source of the contract

#### Scenario: The data file of tagents-core
- **WHEN** a file is `spec/cli/tagents-core.json` or its schema
- **THEN** it is a source of the contract

### Requirement: The tagents-core verbs come from the CLI spec file
The verbs of `tagents-core` SHALL be read from `spec/cli/tagents-core.json`, whichever implementation serves them, so that moving a verb to Rust changes no byte of the contract.

#### Scenario: A verb changes implementation
- **WHEN** the `impl` of a command in `spec/cli/tagents-core.json` changes from `node` to `rust` and `pnpm plugin:gen` runs
- **THEN** no generated file differs
