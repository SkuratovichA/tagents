## Context

The notification service is one node process per machine, `node packages/notify/dist/main.js run`, started by a LaunchAgent and alive for days. It follows the events file the hooks append to (`<state dir>/events.tsv`), decides which events deserve a notice, keeps one prompt-cache deadline per idle session, runs a helper app once per notice, and re-reads its options when the file changes. On 30.10.2026 it held 31 MB by `footprint` (peak 40 MB) after two days and four hours. The code that does this is about 2,000 lines of TypeScript, split between `packages/notify/src` (`engine.ts`, `service.ts`, `deadlines.ts`, `compose.ts`, `kinds.ts`, `screen.ts`, `options.ts`, `phrases.ts`, `exec.ts`, the helper and log notifiers) and `packages/core/src` (`agent-events.ts`, `agent-state.ts`, `plugin-options.ts`, `zod-issues.ts`), with about 4,300 lines of tests.

After `rust-mcp` the crate has what a long-lived server needs first: a front door that forwards every word it does not serve to the node CLI, a call that runs a program in a process group with a deadline and a cap on its output (`mcp/run.rs`), a cancellation token and an ending on SIGTERM, SIGINT and SIGHUP through `signal-hook` (`mcp/server.rs`, `mcp/mod.rs`), `rustix` for signals and `poll`, and the helpers that repeat node's behaviour (`transcripts.rs` `last_assistant_text`, `node.rs`, `date.rs`, `js.rs`). It has no TOML reader, no file watch, no code for the state rows, event lines, labels and history the daemon reads, and no engine.

This change makes the daemon a verb of the binary that already ships, keeps the node daemon as the fallback and as the oracle the new one is tested against, and leaves a watch and a child-with-input module for the next port (the knowledge server). It follows `rust-mcp` in form and in how a machine switches: through the installer's wrapper, only when a binary of the checkout's version is installed.

## Goals / Non-Goals

**Goals:**

- On a machine with the prebuilt binary, the LaunchAgent starts `tagents-core notify run`, and nothing the person sees changes: the same notices for the same events, the same log lines, the same exit codes, the same lock, the same files left behind, the same reaction to a bad options file.
- On a machine without the binary, or with one of another version, nothing changes.
- Nothing polls, and a node daemon and a Rust daemon on one state directory exclude each other.
- The two daemons cannot drift unnoticed: one suite starts both on the same state, feeds them the same events and compares what they post, log and leave behind, and the helpers that exist twice are pinned by vectors that node generates.
- The watch, the child with input and a deadline, and the signal ending are modules the next port reuses, not code of this daemon.

**Non-Goals:**

- Retiring `packages/notify`, changing what a notice says or when one is posted, or changing the options.
- The verbs `install`, `uninstall`, `status`, `test` and `send`, the Swift helper, `launchctl`, and a notification backend for Linux.
- A YAML reader, a Windows build, an async runtime, the `notify` crate.
- Cutting a release: the tag needs Sasha's word, and until it exists the installer keeps node for the version this ships in.
- Restarting the running service when a binary is installed: `launchctl` is not in `install.sh`.

## Decisions

### One binary, one more verb: `tagents-core notify run`

Decision: the daemon is the verb `["notify", "run"]` of `spec/cli/tagents-core.json` with `impl: rust` and `effect: serve`, so it is not a tool (`isTool`) and the generated contract and references gain one entry. Its summary goes in `packages/core/src/i18n/{en,ru}.ts`. `front_door.rs` serves exactly the arguments `notify run`: any other argument list that starts with `notify` (`notify install`, `notify status`, `notify run extra`) is forwarded to the node CLI, which hands it to the plugin host, as every unserved word is today. `served_spec` lists the verb because `STREAMING` holds it.

Reason: the binary is built, checksummed, released and installed already, and `mcp` is the precedent for a verb that owns stdin, stdout and the process until it ends. The data file's rule that a first word is served by one program holds, because the word `notify` has no `impl: node` entry in it: the plugin's other verbs are the host's, not the data file's (`packages/core/test/cli-spec.test.ts`, "a verb word is served by one program").

What `tagents notify run` does through the node plugin host: it runs the node daemon, as today, because the `tagents` command is the node CLI and no wrapper routes it to the binary. Two implementations stay reachable, and one of them is the reference: `packages/notify` is to `tagents-core notify run` what `packages/mcp` is to `tagents-core mcp`, the oracle that `tests/rust-notify-parity.sh` runs the port against, and the fallback a machine without the binary runs. That is not a second implementation in the repository's sense because a suite that fails on any difference stands between the two, and the wrapper, not a person, chooses.

Rejected: a second binary `tagents-notify` in Rust (a new archive member, `release.yml`, the installer's member check and `tests/release.sh` for one more executable of the same kind); the verb as the top-level word `notify-run` (a first word of its own for what is one verb of the plugin's group).

```rust
// front_door.rs: run()
match args.iter().map(|a| a.to_str()).collect::<Vec<_>>().as_slice() {
    [Some("mcp"), ..] => mcp::run(&args[1..]),
    [Some("notify"), Some("run")] => notify::run(),     // blocks until a signal or a deliberate exit
    _ => /* the group lookup, else forward() */,
}
```

### The wrapper chooses, and launchd names the wrapper

Decision: launchd runs `~/.local/bin/tagents-notify run` when that wrapper is there, and the wrapper decides between the binary and node. Three edits make it so. `install.sh`: `write_wrapper` takes a sixth parameter, the one argument list the native binary is for, and the `tagents-notify` entry of `install_commands` names the binary of `tagents-core` with the word `notify` for the argument list `run` and nothing else, under the same `--version` check that `tagents-mcp` has, so a binary that predates the verb is never named. `runSpecFor` in `packages/notify/src/plugin.ts` writes `[<wrapper>, 'run']` into the plist when `findOnPath('tagents-notify', env.PATH)` names a file whose text holds this checkout's `dist/main.js` (`MAIN_JS` in `paths.ts`), and today's `[process.execPath, <dist/main.js>, 'run']` otherwise. The contract entry above is the third.

```sh
# the tagents-notify wrapper with a binary installed: the line of the tagents-mcp wrapper with one more test, so only the argument list `run` goes to the binary
r="$TAGENTS_HOME/target/release/tagents-core"
[ ! -f "$r" ] || [ ! -x "$r" ] || [ "$#" -ne 1 ] || [ "$1" != run ] || { TAGENTS_NODE="$n"; export TAGENTS_NODE; exec "$r" notify "$@"; }
exec "$n" "$TAGENTS_HOME/packages/notify/dist/main.js" "$@"
```

```ts
// runSpecFor: the program the plist names
const wrapper = findOnPath('tagents-notify', env['PATH']);
const viaWrapper = wrapper !== null && fs.readFileSync(wrapper, 'utf8').includes(`"${mainJs}"`);   // the wrapper writes the path of the program in double quotes (write_wrapper in install.sh), so another checkout's path that merely contains this one is not taken for it
return viaWrapper ? { program: wrapper, args: ['run'] } : { program: process.execPath, args: [mainJs, 'run'] };
```

Reason: the daily update removes the binary of a version that has no release, and the wrapper is rewritten on every update, so a plist that named the binary would be left pointing at nothing and `KeepAlive` would restart it every 300 seconds for good, while a plist that names the wrapper falls through to node at the next start. The wrapper `exec`s, so the process launchd supervises is the daemon and keeps its pid: `status` reads the lock file, `events.on`, `launchctl print` and `ps` by pid and never the program's name, so it works for either. A wrapper of another checkout is not used because its `dist/main.js` is not this checkout's. Every other verb of `tagents-notify` reaches node, so `install`, `uninstall`, `status`, `test` and `send` are untouched.

Rejected: the plist naming `tagents-core notify run` (the crash loop above); a node `run` that execs the binary (the node process the change exists to remove would stay, and the execed one would not be the program of the plist); a second LaunchAgent label (two services, two locks and a migration of the person's allow-listing in System Settings).

Nothing restarts the running service when a binary is installed. A running node daemon stays node until `tagents notify install` (which boots the agent out and in) or the next login; the migration plan says so.

### The options file: the `toml` crate, and a validator that writes zod's lines

Decision: `notify.toml` is read by the `toml` crate (`default-features = false`, features `std`, `parse`, `preserve_order`; the dependency PR keeps the smallest set that builds), and a hand-written validator in `notify/options.rs` checks the table against the one schema of `packages/notify/src/options.ts` and writes the problem lines the node daemon writes, byte for byte. `preserve_order` is needed because the lines depend on the order of the keys in the file. The workspace's rule "no other parser is in the tree" (the comment above `[workspace.dependencies]` in `Cargo.toml` and `docs/architecture/rust-core.md`, the line "The only dependencies are `serde` and `serde_json`") is widened to name `toml`, with its reason: the options file is TOML and the daemon has to read it.

The problem lines come from `issueLines` (`packages/core/src/zod-issues.ts`): `<path>: <message>` for each issue in zod 4.6.2's order, or the bare message when the path is empty. Every message the schema can produce, with what produces it (checked by running zod 4.6.2 and `smol-toml` 1.9.1 on the cases below, 30.10.2026):

| When | The line |
|---|---|
| an unknown key at the top | `Unrecognized key: "<key>"`, with two or more `Unrecognized keys: "<a>", "<b>"` |
| an unknown key in `events`, `events.<kind>` | the same, after `events: ` or `events.<kind>: ` |
| `backend` or `click` not in its list, whatever its type | `backend: Invalid option: expected one of "auto"\|"macos"\|"log"\|"none"`, `click: Invalid option: expected one of "dock"\|"goto"\|"focus"` |
| `icon` is the empty string | `icon: Too small: expected string to have >=1 characters` |
| a value of the wrong type for a string, a boolean or a table | `<path>: Invalid input: expected <string, boolean or object>, received <type>` |
| a duration that the grammar refuses | `<path>: not a duration: <the value as JSON.stringify writes it> (use 90, 45s, 50m, 2h or 1h30m)` |
| a duration that is neither a string nor a number | `<path>: Invalid input` |
| `after` is not below `ttl` and both are well formed | `events.cache_expiring.after: after must be below ttl: a notice about a cache that already expired helps nobody` |
| a file that is not TOML | `<file>: Invalid TOML document: <reason>` (see the known differences) |

`<type>` is `string`, `number`, `boolean`, `array`, `object`, `TomlDate` (any TOML date or time), `NaN`, `Infinity` or `-Infinity`. A duration is a string or a number, so a boolean, an array, a table, a date and a non-finite float fall to the bare `Invalid input` of the union. The unknown keys are written raw (a quote inside a key is not escaped) in JavaScript's property order: keys that are canonical array indexes, in ascending order, then the rest in file order. The issues of an object come in the order of its shape (`backend`, `click`, `icon`, `events` with `question`, `permission`, `turn_done`, `cache_expiring` with `enabled`, `skip_visible`, `after`, `ttl`, `session_end`), each key's issues being its value's, then the object's unknown-keys issue, then its refine: a type problem anywhere inside `cache_expiring` stops the `after`/`ttl` check, and an unknown key does not. A date or time where a table is expected is read as an empty table, as zod does. A duration is read by `parseDuration`: a number or a string of ASCII digits is seconds, a safe non-negative integer; otherwise `^(?:(\d+)h)?(?:(\d+)m)?(?:(\d+)s)?$` with ASCII digits only, the empty string refused, the sum a safe integer; a float that is whole (`1.0e1`) is a number like any other, and the value in the message is written by `js::number_text`, so `5e-1` reads `0.5`.

The path is `<configDir>/plugins/notify.toml` and nothing else, as `pluginOptionsFile` has it (`packages/core/src/plugin-options.ts:14`): no file of another name is looked at, so the defaults hold when only such a file is there. The file is read as `loadPluginOptions` reads it (`packages/core/src/plugin-options.ts:23-43`, which reads with `fs.readFileSync` through `parseConfigFile`, `packages/core/src/config-file.ts:38-39`): a read that fails with `ENOENT` (no file, a dangling symlink) is the missing file, the defaults, `not found` in the `started` line; any other failure is one problem line `<file>: <the text node prints>` and the defaults, `invalid`: `EISDIR: illegal operation on a directory, read` for a directory named `notify.toml`, `EACCES: permission denied, open '<file>'` for a file that cannot be read, `ENOTDIR: not a directory, open '<file>'` when `plugins` is a file. The Rust text is written by `node::io_message` (`crates/tagents-core/src/node.rs:69`), and an error number it does not name prints what Rust says (a known difference below). Whether the file is read at start or at a reload, and from a symlink or not, is the same read.

```rust
// notify/options.rs
pub fn load(config_dir: &Path) -> Loaded;   // Loaded::{Found(Options), Missing(Options), Invalid(Vec<String>)}
fn check(root: &toml::Table, issues: &mut Vec<String>) -> Options;
```

Reason: `serde` with `deny_unknown_fields` writes serde's texts in serde's order, and a schema crate for one fixed schema is a dependency for forty lines. The vectors fixture (`tests/rust-notify-vectors.mts`) holds about a hundred documents, every row of the table, pairs of problems and the cases above, each with the lines node writes, and the differential suite feeds the same files to both daemons.

Rejected: a derive on the options struct (the texts, the order and the date rule are all different); copying only the custom messages (the unknown-key, type and enum lines are what a person sees first).

### A failed start hands over to node, at start

Decision: the Rust daemon hands over to the node daemon only at start, and only when a step of the start before the `started` line fails. `hand_over` lives in a module of its own, `notify/hand_over.rs`, so that its order (stop check, close, keep the lock, exec) is one function with tests of its own. It first looks at whether a stop was requested: if one was, the process ends as a stop ends it (the lock released, exit 0, and no `stopping` line, because that line is written once a start has settled and this one failed) and nothing is exec'd. Otherwise it logs `handing over to the node service: <why>` with the error of the failed step, closes what the follower and the watches hold, removes `events.on`, keeps `notify.lock` held, and replaces its process with `node <root>/packages/notify/dist/main.js run` with the environment it had. The exec keeps the pid and the lock, and `holds` (`packages/notify/src/service.ts:164-171`) treats a lock held by its own pid as not held, so the node daemon takes the lock over and the hand-over has no window in which a manual `run` could take it and the exec'd daemon exit with `another notify service holds`; node's own takeover of a stale lock (`takeLock`, `packages/notify/src/service.ts:203-217`) removes the file and loops to create it, which does have such a window. The lock is released only on the exit paths: a stop, a deliberate exit, a failure that is not handed over, and an `exec` that fails. When the node program cannot be started the line is `<ISO time> could not hand over to the node service: <why>` and the process exits 1, the lock released first: the why is the text of `node_program` when `packages/notify/dist/main.js` is not there (a `git clean` with no `pnpm build`), which fails before any exec, and the operating system's text through `node::io_message` when the exec fails.

The steps before `started` (`service.ts:377`), in node's order: create the state directory, take the lock (a held lock is the deliberate exit 0 and not a failure), read the options (which never fails: a missing or unreadable file is the defaults, see above), pick the backend (`none` and a system without a backend are deliberate exits), start the follower (open or create `events.tsv`, arm its watch, create `events.on`) and arm the engine from the state rows. A failure of any step but the options hands over: the node daemon then either runs or fails by its own rules and writes its own `the notify service stopped:` line (through `ctx.log`, without a timestamp: `packages/notify/src/plugin.ts:382`, `packages/core/src/cli/plugin-run.ts:132`), and launchd does not restart a defect of the new code every 300 seconds. The options-directory watch is not one of them: a watch that cannot be armed logs `options watch failed <dir> <why>` and the service runs without a reload, as node does (`service.ts:233-247`). A failure after `started` is not handed over: an exec there drops the events queued in the engine, the follower of the new process starts at the end of the file (`packages/core/src/agent-events.ts:261`) so every event written before it is armed is lost, and `warnedAt` of the engine (`packages/notify/src/engine.ts:365` and `:385`) starts empty, so a cache notice could be sent a second time.

Reason: a function that finds the node program next to the binary and `exec`s it is the least machinery that keeps a machine's notices when new code fails to start. `front_door.rs` has it as `exec_node(relative, args)` (`front_door.rs:115-135`), which finds the program with `node_program` (`:93-111`), but the hand-over cannot call it as it is: on a failure it prints its own `tagents-core: cannot find …` or `tagents-core: cannot run …` line and returns exit 2, 126 or 127, where the hand-over writes `could not hand over to the node service: <why>`, releases the lock and exits 1, and a missing `packages/notify/dist/main.js` fails in `node_program` before any exec. Task 5.5 therefore splits `exec_node` in two. The deciding part, which finds the program with `node_program` and replaces the process, and returns only a failure as a value (`node::exec(relative, args) -> ExecFailure`: the text of the missing program, or the `io::Error` of the exec, with the exit code the front door uses for each) and prints nothing, moves to `crates/tagents-core/src/node.rs`, where `node::io_message` already lives (`node.rs:69-83`). The printing part stays in `front_door.rs` as `exec_node`, calls `node::exec` and keeps every byte and exit code it has now (the requirement "When the node CLI cannot be run" of `core-front-door` and its tests stay as they are). `hand_over` calls `node::exec`, so `notify` uses `node` and never `front_door`, and the module that calls `notify::run` is not a module `notify` calls back (no cycle). The hand-over is the second caller that task 1.4 waits for, so the split lands with it.

Rejected: an exec after `started` (the queue and `warnedAt` above).

```rust
// notify/hand_over.rs
pub fn hand_over(why: &str, stop: &Stop, lock: Lock) -> !;   // stop requested: end as a stop ends, with no `stopping` line; else log, close, keep the lock, replace the process through node::exec (NODE_NOTIFY, &["run"]); no build or exec failed: release, log `could not hand over to the node service: <why>`, exit 1
```

### The child with input and a deadline, and the ending, are lifted out of `mcp`

Decision: the program-with-a-deadline code of `mcp/run.rs` moves to `child.rs`, and the cancellation token and the signal thread of `mcp/server.rs` and `mcp/mod.rs` move to `ending.rs`. `mcp` calls them and nothing about what `mcp` does changes: the same constants, the same tests, the same `tests/rust-mcp-parity.sh` result. What moves: `Capture`, `read_stream`, `complete_end`, `spawn_thread`, `launch`, `wait_for_exit` (`waitid` with `NOWAIT`), `supervise`, `signal_group`, `group_of`, `duplicate`, `readable` and the `Event`, `Stream` and `Reason` types to `child.rs`; `Stop` to `ending.rs`, next to `on_signals(f)`, the thread that registers SIGTERM, SIGINT and SIGHUP with `signal-hook`, calls `f` once with the name of the signal as node spells it (`"SIGTERM"`, `"SIGINT"`, `"SIGHUP"`) and ignores later signals. The daemon's callback does with that name what the section on the engine below says, and `mcp` ignores it. What stays in `mcp/run.rs`: `call_tool`, `Runner`, the JSON body of a result, the outcome names.

```rust
// child.rs
pub struct Policy {
    pub input: Option<Vec<u8>>,            // written to the child's stdin, which is then closed
    pub timeout: Duration,
    pub kill_grace: Option<Duration>,      // Some: SIGTERM at the timeout, SIGKILL after the grace (mcp); None: SIGKILL at the timeout (notify)
    pub drain: Duration,
    pub cap: usize,                        // bytes kept per stream, cut at a character
}
pub struct Finished { pub code: Option<i32>, pub stdout: String, pub stderr: String, pub stdout_cut: bool, pub stderr_cut: bool, pub reason: Option<Reason> }
pub fn run(command: Command, policy: &Policy, stop: &Stop) -> Result<Finished, io::Error>;   // Err: the program could not be started

// ending.rs
pub fn on_signals(f: impl FnOnce(&'static str) + Send + 'static) -> io::Result<()>;   // f gets the name of the signal as node spells it: "SIGTERM", "SIGINT" or "SIGHUP" (ending.rs:52)
```

The notify calls are four: the helper's `post` and `withdraw` (stdin the notice JSON for `post`, five seconds, SIGKILL at the deadline, as `execText` in `packages/notify/src/exec.ts`), the tmux probe (two seconds), and `/bin/ps -o lstart= -p <pid>` for the lock (two seconds, with `LC_ALL=C TZ=UTC` as the whole environment). None passes a stop that trips: the node daemon lets the post in flight finish when it stops, so the Rust one does too, and the end of a daemon is bounded by the helper's five seconds. The notify calls use the process group as `mcp` does, so a SIGKILL at the deadline reaches a helper's own children, which `execFile` does not do (a known difference).

Reason: the repository's rule is one pattern per problem, and spawn-and-kill with a drain and a cap is the problem `mcp/run.rs` already solved, including the cases that took rounds of review there (the group, the holder outside it, the zombie, output left in a pipe at the exit). A copy for notify would have to be fixed twice.

Rejected: calling `mcp::run::call_tool` (it takes a contract tool and writes the MCP result body); a second spawn function in `notify` (the duplication above); `std::process::Child::wait_with_output` (no deadline, no group, no drain).

### The watch is one module over inotify and kqueue, and it never follows a symlink

Decision: `watch/` is a small module with two functions behind one type, `Watch::start(sink)`, `watch.dir(path, key)` and `watch.file(path, key)`, and a thread of its own that blocks until something happens and sends `key` to the sink, which is a channel of the engine. Linux is `rustix::fs::inotify` and `rustix::event::poll` (features `fs`, `event`). macOS is the `kqueue` crate (`Watcher::add_file`, `add_fd`, `remove_file`, `watch`, `poll_forever`, `poll`; `add_filename` opens the path itself and follows a symlink, so the file is opened here with `O_NOFOLLOW`, which refuses a symlink, and `O_NONBLOCK`, which keeps the open of a FIFO from waiting for a writer and so from holding the watch thread, and handed to `add_file`), because `rustix` declares `kevent` unsafe and the workspace forbids `unsafe` (the crate's own call sites are safe). A pipe whose read end is in the poll set or the kqueue wakes the thread when the engine adds or drops a watch (`pipe` feature of `rustix`). The thread sends `Heard::Fired(key)` for a key whose watch fired and, when its wait fails, one last `Heard::Ended(error)` before it ends (`crates/tagents-core/src/watch/mod.rs:50`), so `Watch::start` is generic over `T: From<Heard>` (`:105`) and the sink is a channel of the engine's `Message` (the section on the engine below). On macOS an event that the `kqueue` crate cannot decode is skipped, as an interrupted wait is, and is not an `Ended` (`benign` is defined at `watch/macos.rs:140` and used in `wait` at `:127`).

What is watched, and why it is two things on macOS. A kqueue vnode watch on a directory fires when an entry is added, removed or renamed and not when a file in it is written, whereas node's `fs.watch(dir)` is backed by FSEvents on macOS and sees a write too (libuv uses FSEvents for directories and kqueue for files). So the options file is watched as a directory (the entry changes: an editor that saves through a rename, `ln -sf`, the first creation) and as a file opened with `O_NOFOLLOW` and `O_NONBLOCK` (an edit in place). The pinned behaviour of `packages/notify/test/service.test.ts` ("a symlinked notify.toml is noticed when the link is replaced, not when its target is edited") holds because a symlink is not opened: on macOS `O_NOFOLLOW` fails with `ELOOP`, and on Linux the path is looked at with `symlink_metadata` first, because inotify takes a path and `IN_DONT_FOLLOW` would put the watch on the link itself; either way there is no file watch for a link, and the directory watch sees the link replaced and never sees a write to a target in another directory. On Linux the directory watch of inotify reports a write to a file in it. A file watch sits on an inode, so a save through a rename leaves it on a file that is gone: the thread opens the path again, before it reports the key, whenever the directory reports anything and whenever the file's own watch reports a delete, a rename or a revoke, and on Linux also `ATTRIB` and `IGNORED` (`FILE_GONE` in `watch/linux.rs:27-30`; a rename over the file sends `ATTRIB` first, and `DELETE_SELF` only when the last descriptor of the replaced inode closes). A re-arm that fails because the file is gone or is a symlink is "nothing to watch", as it is at the first arming; a re-arm that fails for another reason (the inotify watch limit, `EMFILE`) ends the watch with `Heard::Ended` and the error, and the daemon fails as it does for any `Ended`. The options directory is `realpath(<configDir>/plugins)`, because `~/.config/tagents` is usually a symlink into a dotfiles repository and a watch on the link sees nothing; with no `plugins` directory the real config directory is watched for the name `plugins`, and when it appears the watch moves to it and the file is read once more; with no config directory the line `options reload is off: <dir> does not exist` is logged and the service runs on (`watchDir` and `adopt` in `packages/notify/src/service.ts`). A directory event carries no name on kqueue, and node filters the options directory's events by name (`packages/notify/src/service.ts:314-316`; its test, `packages/notify/test/service.test.ts:452-470`, pins no reload beside an unrelated file), so the Rust daemon cannot filter by name. An event on the options directory instead makes it read the options file and apply it, as node's `apply` does (`packages/notify/src/service.ts:265-282`), only when what it read differs from what is in force (the bytes of the file, its absence, or the failure of the read): an unchanged file logs nothing and changes nothing, so an unrelated file written in the directory costs one read and no line. The one difference that remains is a symlinked `notify.toml` whose target was edited: the edit does not by itself cause a reload in either daemon and takes effect at the next reload, which the Rust daemon makes at the next event in the options directory of any name (its read follows the link and the bytes differ), where node's next reload needs an event named `notify.toml` (a known difference below, next to issue #39).

On Linux two keys may share one directory or file: each key on a shared inode hears its events (`crates/tagents-core/src/watch/linux.rs:77-88`), and a watch descriptor is removed only when its last key leaves (`watch/linux.rs:50-57`). A removed descriptor is no longer armed, so the `IN_IGNORED` the kernel queues for it after the last key leaves reaches no key (`read` in `watch/linux.rs` matches an event only to the armed descriptors); `IN_IGNORED` reaches a key only when the kernel drops a watch that is still armed, and for a file watch it is one of the events that make a re-arm (`FILE_GONE`). A key therefore means "look again" and is never proof that something changed: the events file is read to the end whatever the key says, and the compare of the bytes above makes a key for the options directory harmless.

The events file is watched as a file. The follower is `followAgentEvents` (`packages/core/src/agent-events.ts`) ported function by function: it opens `events.tsv` (creating the directory and the file, mode 0600) and starts at the current end, reads to the end in 64 KiB chunks on every wake, keeps the bytes of a partial line, drops a line of fewer than 13 fields, or whose time is not a number or whose event is not one the hook writes, tolerating a trailing `\r` and ignoring fields beyond the 13th as `parseEventLine` does (`packages/core/src/agent-events.ts:91-97`, `openspec/specs/event-stream/spec.md:153`), restarts at 0 when the file is shorter than the offset, reopens from 0 when the path names another inode, and rotates at 1 MiB (rename to `events.tsv.1`, a fresh file, the old one kept open for 2 seconds to be read to its end). `events.on` is created with the first follower and removed with the last; the daemon has one. A dead follower is followed again after 1 second, doubling to 5 minutes, back to 1 second when the dead one heard an event or lived longer than the wait that preceded it (`REFOLLOW_MIN_MS`, `REFOLLOW_MAX_MS` in `packages/notify/src/engine.ts`).

The lost wake: an edge-triggered watch raises nothing for a write that lands between the last read and the arming. Every arming is therefore followed by a read to the end, and every wake by a read to the end; `agent-events.ts` documents the same race for libuv. The options watchers do the same (`apply(load())` right after arming, as `service.ts` does).

Reason: no Rust code in the tree watches a file, `std` has no API for it, and the spec says the service polls nothing. A polling fallback would be a second mechanism with its own timing, and the `notify` crate would bring its own thread, its FSEvents backend (which follows symlinks differently) and a larger tree.

Rejected: the `notify` crate (above); `rustix` for kqueue (`kevent` is unsafe to call, so every call site would need `unsafe`); `FSEvents` through a binding (a run loop and a C framework for a daemon that has one directory to watch); watching the resolved file (it fails the pinned symlink test).

```rust
// watch/mod.rs
pub enum Key { Events, Options }
pub enum Heard { Fired(Key), Ended(io::Error) }   // Ended: the wait failed, the thread ends after sending it
pub struct Watch { /* thread, wake pipe, command channel */ }
impl Watch {
    pub fn start<T: From<Heard> + Send + 'static>(sink: mpsc::Sender<T>) -> io::Result<Watch>;
    pub fn dir(&self, path: &Path, key: Key) -> io::Result<()>;
    pub fn file(&self, path: &Path, key: Key) -> io::Result<()>;   // a symlink is Ok(()) and no watch (macOS: O_NOFOLLOW and ELOOP; Linux: symlink_metadata and IN_DONT_FOLLOW)
}
```

### One engine thread, wall-clock deadlines, and what the log says

Decision: three threads and no runtime. The main thread is the engine: it owns the follower, the options, the deadlines and the notifier, and loops on `Receiver::recv_timeout` for a `Message` or for the next due time, whichever comes first, so events and due deadlines run one at a time as the promise chain of `engine.ts` runs them, and a post that takes five seconds holds the loop for five seconds while the other two threads keep queueing. The order is node's: one FIFO queue of jobs, and at each wake the follower's lines are ingested (each becomes a job at the back of the queue) and the deadlines swept (each due key becomes a job behind them) before the first due job runs, as `engine.ts:399-408` sweeps at every event, behind the event in the chain, "so a prompt that cancels a key is seen first". A prompt that arrives while a post is in flight therefore cancels the cache notice of its session before that notice's job runs, where a loop that ingested one line, ran its due jobs and then read the next would send it. This holds for a prompt line that is in the file when the post ends. Node orders by arrival: its deadline timer enqueues the due job when it fires (`deadlines.ts` `wake`, `:64`; `engine.ts:207-209`), so a deadline that passes during a post runs before a prompt line that arrives later in the same post, and node posts. The Rust engine, blocked in the post, cannot order the two after the fact (a known difference below). The watch thread sends wakes. `Message` is the one type of that channel, `enum Message { Wake(Key), Ended(io::Error), Stop }` with `Key::Events` or `Key::Options` in a `Wake`, and `impl From<Heard> for Message` (`Heard::Fired(key)` becomes `Wake(key)`, `Heard::Ended(error)` becomes `Ended(error)`), so `Watch::start::<Message>` takes its sender. The loop is a function of its own, `fn serve(messages: Receiver<Message>, …)` in the service module, which the run function of the service calls after it has started the watch with the sender of that channel: the tests of the service send `Message` values on a channel and need no real watch. A `Message::Ended(error)` from the watch is a failure of the service, after `started` and so not handed over: it is the signal stop with the reason `watch failed: <why>` (the error through `node::io_message`), and exits 1 where a signal stop exits 0, so launchd's `KeepAlive` starts it again (a known difference below). The engine thread is the only reader of the channel and is blocked inside `child::run` while a post is in flight, so it reads `Ended` only after the post ends, and the `Ended` stop is written when the engine reads it: wakes queued ahead of `Ended` are served first, in channel order, like any wake. The order is: the post in flight finishes (its `notice` line), the wakes queued before `Ended` are served, then `stopping (watch failed: <why>)`, then the rest of what a signal stop writes after `stopping` (`drain failed <why>` when the drain fails, `events.on` is removed, the lock is released last), then exit 1. The failed watch has no line of its own. The signal thread (`ending::on_signals`, whose callback receives the signal's name) is started before anything else. Once start has settled it logs `stopping (<signal name>)` and then trips the stop, so the line precedes the `notice` line of a post in flight, as node writes it synchronously in its signal handler before it closes the watchers and lets the post finish (`packages/notify/src/service.ts:387-399`); an engine thread blocked in a post could not write it first. A signal that comes during start is remembered, as node remembers it (`packages/core/src/service.ts:131-137`, acted on once the start has settled at `:178-191`): the thread records the name, trips the stop and writes nothing, and the main thread writes `stopping (<name>)` after it has written `started`, when the start succeeded, and then stops as above, so the log has `started` and then `stopping (SIGTERM)`, as node's has (`packages/notify/src/service.ts:377` and `:390`), and `started` stays the last line of a start. When the start fails no `stopping` line is written: the failing start's own lines stand, and the stop that was requested ends the process as the stop during a failing start does. A deliberate exit during start (a held lock, backend `none`, a system without a backend) writes no `stopping` line either: the line belongs to a service that has logged `started`. Which thread writes is decided by one value that both read under a lock, a small type of the service module, `StartGate`, which is `Starting(Option<name>)` until start settles and `Running` after, with two methods: `signalled(name) -> bool` is called by the signal thread and returns true when start has settled, so that the caller writes `stopping` itself, and false when it has only recorded the name (the first name only: a second signal before start settles is ignored); `settled() -> Option<&'static str>` is called once by the main thread when start settles, sets `Running` and returns the name recorded during start, for which the main thread writes `stopping`. The type is tested without a process, one unit test per interleaving, because a real-process test cannot signal inside a start of a millisecond. The deadline scheduler (`deadlines.ts`) is a map and a minimum: the next wake is the earliest due time read from the wall clock (`SystemTime`), capped at five minutes, and re-read on every wake. A monotonic clock stops during sleep on macOS, so a Mac that slept through a deadline wakes within one cap of it, as node's timer does. What the service holds when idle: three threads (the engine, the watch, the signals), plus the reader threads and the writer of a child call only while one runs (`child.rs`); no timer object, because the engine's one timed wait ends at the earliest of the cache deadline, the re-follow time (only while the follower is dead) and the end of the 2 second grace of a rotated events file; and the watch's descriptors, which are the inotify descriptor and the two of the wake pipe on Linux, and the kqueue descriptor, the two of the wake pipe and one open descriptor for each of the events file, the options directory and the options file (when it is a regular file) on macOS. The requirement "Resource use" of `notify-service` is modified to say so.

The log is the node daemon's: `<ISO time with milliseconds> <parts joined by a space>` on stderr (`date::iso`), and nothing on stdout. The vocabulary is the list of the requirement "The log is the node service's" (`specs/rust-notify/spec.md`, built on "The log lines of the service" of `notify-service`), which enumerates every line `service.ts`, `engine.ts` and the log backend write; the lines the Rust daemon adds are two, `handing over to the node service: <why>` and `could not hand over to the node service: <why>`; the stop of a failed watch is the stop's own line, `stopping (watch failed: <why>)`. The line `the notify service stopped: <why>` is not one of the Rust daemon's: node writes it from `plugin.ts:382` through `ctx.log`, without a timestamp (`packages/core/src/cli/plugin-run.ts:132`), and in Rust the one path that reaches it hands over to node, which writes it. On the `log` backend a withdrawal prints `withdraw <id>` twice, once from the backend (`packages/notify/src/platform/log.ts:25`) and once from the engine (`packages/notify/src/engine.ts:288`), and the Rust daemon writes both. The operating system's text inside a line (a failed lock release, a failed watch, a failed post, a feed error) is written by `node::io_message` (`crates/tagents-core/src/node.rs:69`) from the error and the syscall, and a text it cannot reproduce for an error number that differs between the two systems is a known difference below. `boot_ms`, for judging a lock that has no recorded start, is `now - uptime` read once at start (`/proc/uptime` on Linux, `sysctl -n kern.boottime` through `child::run` on macOS, zero when neither can tell, which counts every lock file as written after boot). `os` in `no notification backend for <os> yet` is node's name: `darwin` for macOS, `win32` for Windows, `std::env::consts::OS` otherwise. The host name is `rustix::system::uname().nodename()`.

Reason: the engine is a sequence by design, so one thread removes every question about two events touching one state, and the three threads only move wakes. Rejected: a thread per child (the child module has its own); `EVFILT_SIGNAL` in the watch (`signal-hook` is already the signal mechanism of the crate).

### The node daemon is the oracle: a differential suite

Decision: `tests/rust-notify-parity.sh` and its driver start the node daemon (`node packages/notify/dist/main.js run`) and the Rust daemon (`target/debug/tagents-core notify run`, or `$TAGENTS_CORE_BIN`) one after the other on identical scratch state and compare what they leave. The scratch has its own `HOME`, `TA_STATE_DIR`, `TAGENTS_CONFIG_DIR`, `TAGENTS_LOCALE`, `TMUX_TMPDIR`, a `PATH` of a `tmux` shim followed by `/usr/bin:/bin`, and `TA_NOTIFY_APP` pointing at a stub helper (a POSIX script at `<app>/Contents/MacOS/tagents-notify` that records its arguments and stdin and answers one JSON line). The driver waits for the `started` line, appends events to `events.tsv`, writes state rows, labels, history and a transcript, waits for the posts it expects, sends SIGTERM and prints the transcript. The script compares the two after replacing the timestamp and the pid. Short `after` and `ttl` (`1s`, `3s`) make a deadline fall due in seconds.

What the scenarios cover: every row of the verdict table; the question-then-permission window; kinds switched off; `skip_visible` with a tmux shim that shows the pane, hides it, fails, times out and says there is no such pane; a notice that is replaced and one that is withdrawn; the cache deadline, armed from an event and from state rows at start; the transcript body; both locales; a stub helper that answers `shown: false`, fails, prints garbage, exits slowly past five seconds and is not there (macOS only, because `pickPlatform` returns the helper only on darwin: the suite prints how many scenarios it skipped, and the macOS job of CI runs them); the `log` backend on both systems; each document of the bad-options set, at start and as a reload, with the line of each and `options reloaded`; a symlinked options file whose link is replaced (the edited target is #39, below); an unrelated file written in the options directory, which logs nothing in either daemon; a late `plugins` directory; a missing config directory; the lock (a second daemon of the other kind exits 0 with its line; a stale lock, a lock of a reused pid and a lock with a bare pid are taken); backend `none`; a start that cannot take the state directory; SIGTERM, SIGINT and SIGHUP with a post in flight, with the exit code, the lock and `events.on` left behind; rotation at 1 MiB; a truncated and a replaced events file; two thousand events in a tight loop with none lost.

The case of a symlink whose target is edited is not compared until issue #39 is settled: the node daemon's own test of the rule (`packages/notify/test/service.test.ts:452`) sometimes sees a reload after the target is edited on macOS (https://github.com/SkuratovichA/tagents/issues/39), so a comparison would fail on node's side at random. The Rust daemon pins the case with its own test of the watch (`a_symlink_has_no_file_watch_so_its_target_edited_is_not_heard_and_the_link_replaced_is`, task 2.3), and the scenario "a symlinked options file edited and replaced" above compares the replaced link only.

Tripwires assert on the node transcript alone, so a scenario that stopped provoking what it exists for fails instead of passing for nothing. `PARITY_ONLY=<text>` runs the scenarios whose label holds the text. The mutation list is in `tasks.md`.

Reason: the node daemon is the specification of the behaviour and it is in the same checkout, so running both on one script says more than describing the behaviour twice. Rejected: recorded transcripts (they rot and do not say which side moved); comparing only the `log` backend (it does not reach the helper boundary).

### Where the two are known to differ

Each of these is listed in `docs/architecture/rust-core.md` under "Where the two are known to differ", and none is a scenario of the suite.

- A file that is not TOML: the line is `<file>: Invalid TOML document: <reason>` in both, but smol-toml's reason ends with a code excerpt (`1:  x = 1`, a pointer line) and its wording is its own, and the `toml` crate's is another. The prefix, the one-line count of problems being one, and the defaults that apply are equal; the rest is not. An integer beyond 2^53 is a TOML error in node (`integer value cannot be represented losslessly`) and is checked for in Rust, with that reason and no excerpt.
- A document that one TOML parser accepts and the other refuses. Both implement TOML 1.1.0; the vectors cover a corpus of edge cases (underscores, signs, `0b`, `0o`, exponents, local dates, `1e400`) and the rest is unverified.
- A failed start hands over to node: from the exec on, the process is node, and its lines are node's own, among them `the notify service stopped: <why>` without a timestamp. The Rust daemon writes `handing over to the node service: <why>` before it, which node never writes, and `could not hand over to the node service: <why>` when the exec fails.
- A symlinked `notify.toml` whose target was edited: the edit does not by itself cause a reload in either daemon, and it takes effect at the next reload. The Rust daemon reloads at the next event in the options directory of any name, because its read follows the link and the bytes differ, where node reloads only for an event named `notify.toml` (issue #39 is the node side of the same case).
- A prompt line that arrives during a post after the deadline of the same session passed during that post: node posts the cache notice, because its deadline timer enqueued the job before the prompt arrived, and the Rust engine, blocked in the post, takes in the prompt and sweeps before it runs the job, so the notice is not posted. The differential suite does not drive that interleaving.
- A stop during a failing start: the Rust daemon exits 0, and node exits 1 with `the notify service stopped:` for a failure the two share.
- A failed watch: node keeps running when a watch fails. The options watcher logs `options watch failed <dir> <why>` and closes, so the reload stops and the following goes on (`packages/notify/src/service.ts:238-241`), a follow that fails logs `follow failed <why> trying again in <n>s` and tries again (`packages/notify/src/engine.ts:425-431`), and an events watcher that dies logs `feed follower died <message> following again in <n>s` and follows again (`packages/notify/src/engine.ts:443-452`, raised from `packages/core/src/agent-events.ts:323`). The Rust daemon has one watch for the options directory and the followed files and never polls, so when that watch ends nothing would be heard again: it writes `stopping (watch failed: <why>)` and what a stop writes after it, and exits 1. The LaunchAgent plist's `KeepAlive` is `SuccessfulExit` false with a `ThrottleInterval` of 300 seconds (`packages/notify/src/platform/macos/launchd.ts:61-67`), so launchd starts it again after any non-zero exit, at most once in 300 seconds, and `install.sh` has no `KeepAlive`; the daemon starts again as whichever program the wrapper then chooses.
- `plugins/notify.toml` without read permission (mode 000): arming its file watch fails with `EACCES`. At start the Rust daemon writes `options watch failed <path> <why>` beside the `options:` problem line and `(invalid)` of the unreadable file, and runs on without that file watch; the directory watch still hears a replacement. A later re-arm that fails with `EACCES` is not a missing file, so it ends the watch and the daemon stops with exit 1 (on Linux a chmod itself makes a re-arm, because `ATTRIB` is in `FILE_GONE`); launchd starts it again, and the new start takes the start path above. Node reads the file, reports the problem and goes on.
- `plugins` is a regular file: node's `fs.watch` on it succeeds, the Rust `dir()` fails with `ENOTDIR` (`a_directory_that_is_a_symlink_is_followed_and_a_file_is_not_a_directory`, `crates/tagents-core/src/watch/tests.rs:293`, asserts the failure), so the daemon writes `options watch failed <dir> <why>` and runs without options reload.
- The operating system's text inside a log line (a failed lock release, a failed watch, a failed `ps`) for an error number that is not the same on Linux and macOS: `node::io_message` names the numbers that are, and any other error prints what Rust says.
- The spawn failure text of the helper: the Rust daemon writes node's `spawn <file> <CODE>` for each error number of `node::ERRNOS` (the ten whose number is the same on Linux and macOS, `crates/tagents-core/src/notify/helper.rs:147`); any other error is the operating system's text as Rust words it.
- A SIGKILL at a deadline reaches the whole group of the child, not the child alone.
- A helper that writes more than 1 MiB: node's `execFile` (which sets no `maxBuffer`, `packages/notify/src/exec.ts:35`, so the default of 1 MiB applies) fails with `ERR_CHILD_PROCESS_STDIO_MAXBUFFER` and no `signal` or `killed` on the error, `exec.ts` hands back the first 1 MiB of stdout with `timedOut` false, and `helper.ts` fails with `unreadable output from the notification helper: stdout <the first 200 characters>, stderr <...>` (`packages/notify/src/platform/macos/helper.ts:59-62`); the Rust call keeps the first 1 MiB, cuts the stream with an `[output cut at <n> bytes]` marker and ends in the same unreadable-output line.
- The boot time is zero when it cannot be read, where node always has `os.uptime()`.
- The age of a lock is its modification time rounded to the millisecond (`node::mtime_ms`, `crates/tagents-core/src/node.rs:72`), where node compares the fractional `mtimeMs` (`packages/notify/src/service.ts:121`), so a lock written within a millisecond of the boot can be judged the other way.
- A failed removal of the temp file after the lock is linked is ignored (`crates/tagents-core/src/notify/lock.rs:154`), where node's `finally` would throw it.
- A symlink as `events.tsv`: the follower reads through the link, but the watch does not follow a symlink, so a write to the target raises no wake until the directory reports something, where node's `fs.watch` follows the link (`packages/core/src/agent-events.ts:319`).
- A client pid that tmux reports above `u32::MAX` is skipped (`crates/tagents-core/src/notify/screen.rs:79`), where node keeps it as a float and no real pid is that large.
- A job that panics writes `error <why>` as a failed job does in node, and the default panic hook writes its own line to stderr before it, which node has no counterpart of.
- The `tagents` script a click runs, when `TA_NOTIFY_TAGENTS` is unset and no `tagents` is on `PATH`: node always names the checkout's script (`packages/notify/src/paths.ts:35`), and the Rust daemon names `<root>/tagents` when that file exists, where the root is three levels above the binary (`crates/tagents-core/src/node.rs:177-187`), and else the bare name `tagents`.
- A lone surrogate in the assistant text of a transcript: node sends it to the helper as the escape `\ud800`; a Rust `String` cannot hold it, so `json.rs` reads it as U+FFFD (`crates/tagents-core/src/json.rs:384`) and the helper receives that character. The vectors have no case with one; the unit test of `json.rs` pins the reading.
- Not a difference, found while checking the premise: `JSON.stringify` and `serde_json` both leave U+2028 and U+2029 unescaped, and both escape a control character in lower-case `\u00xx`, so a title and a duration message are written the same.

### Version and release

Decision: the change ships in three pull requests. (a) This proposal with task groups 1 and 2. (b) Groups 3, 4, 5, 7 and 8, where the `["notify","run"]` entry of `spec/cli/tagents-core.json` and the arm of `front_door.rs` (task 5.6) are the last task of group 5, after the engine, the lock and the service, because until the arm exists `notify run` is forwarded to node; the suite of group 7 runs against it before (b) is marked ready, and (b) is merged whole. (c) Groups 6 and 9 and the archive of this change, merged after (b) and after `rust-mcp` is archived (it is, on `main`: `openspec/specs/rust-mcp/spec.md`). Groups 1 to 5 change inputs of the binary (`is_input` in `.github/scripts/core-release.sh:18-23`: `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `crates/*/Cargo.toml`, `crates/*/build.rs`, `crates/*/src/*`, `spec/cli/*`), so (a) and (b) each raise the workspace version one minor step above their merge base, as the gate requires, and a pull request that rebases onto a version another one raised raises it again, because two that bumped to the same step cannot both pass `core-release.sh gate`. Group 6 changes `install.sh`, `plugin.ts`, `tests/` and documents, none an input, so (c) raises nothing. None cuts a tag. A managed copy that updates to such a commit finds no release for the version, removes the older binary and says so, and keeps running node for the CLI, the MCP server and the daemon, exactly as after any bump before its tag. The version the last pull request that raises it carries is the one that is tagged, when Sasha says so; the versions between are never released. `pnpm plugin:gen` moves the plugin's version and digest where the contract or references change, and the generator, not a hand, writes them. The watch of (a) is not called by the binary until (b), so its `dead_code` lints are checked in (a) by clippy with `-D warnings`, and the kqueue dependency is built by the macOS job.

Reason: the release path is built so that an install never runs a binary of another version, and this change does not weaken it to get there sooner.

## Risks / Trade-offs

- [A defect in the daemon silences every notice] → the suite and the ported tests run on every change to either daemon; the wrapper falls back to node when the binary is gone and a start that fails before `started` hands over to node; `TAGENTS_NO_NATIVE=1` at the next install, or removing `target/release/tagents-core`, returns a machine to node.
- [A lost wake on kqueue or inotify drops an event] → every arming is followed by a read, every wake reads to the end, the suite appends two thousand events in a tight loop, and a mutation that drops the read after arming must fail it.
- [The kqueue directory watch misses what FSEvents reported] → the options file is watched as a file as well; the suite edits it in place, through a rename and as a symlink.
- [The node daemon's own symlink test is flaky on macOS, issue #39] → the differential suite does not compare the case of an edited target; the Rust watch has its own test for it, and the suite compares the replaced link.
- [Two TOML parsers disagree on a document] → the vectors cover a corpus and the rest is a known difference.
- [`recv_timeout` stops while the Mac sleeps] → deadlines are wall-clock times and the sleep is capped at five minutes, so a missed deadline fires within one cap.
- [A node and a Rust daemon run together while a machine switches] → they share the lock file and its format, and the suite starts one of each on one state directory.
- [Threads and process groups behave differently on Linux and macOS] → the suite and the tests run in CI on both, and the release job builds all three targets.
- [A reader thread stays blocked on a pipe a helper's child holds] → it holds a capture of at most the cap and ends with the holder; the drain keeps the call itself from waiting on it, as for `mcp`.

## Migration Plan

1. Merge the three pull requests of "Version and release" in order. No release exists for any of the new versions, so every machine keeps running node for the daemon.
2. When Sasha tags the last version, the next daily update of a managed copy installs the binary and rewrites the `tagents-notify` wrapper to name it for `run`, and `tagents notify install` writes the plist that names the wrapper. A daemon that is already running stays node until the agent is booted out and in (`tagents notify install` does) or the next login.
3. Check with `tagents notify status` (the service is running, the stream is on, the options are valid) and `footprint <pid>`.
4. Rollback is `TAGENTS_NO_NATIVE=1` on one machine (the binary goes at the next install), removing the release (the next install finds none and removes the binary), or editing nothing: the wrapper falls through to node at the next start.
5. The node daemon stays. A later change may retire it, with the suite, the vectors and the wrapper's native branch.
